---

pykrete is a strict superset of Python that adds a type layer for dataframes. Define a schema as a class, annotate a dataframe with `SparkFrame[Schema]` (or `PandasFrame[Schema]`), and pykrete checks every column you touch — at edit time, before your job runs. The runtime is plain Python; the type layer never executes. It's the same idea TypeScript brings to JavaScript, applied to dataframe code. (`DataFrame[Schema]` still works as a deprecated alias — it emits D0090; prefer the dialect-specific form.)

## Install

macOS / Linux:

```bash
brew install amirnaderi93/pykrete/pykrete
```

Windows: the [latest release](https://github.com/amirnaderi93/pykrete/releases/latest) ships an MSI installer. Other options — prebuilt binaries, `cargo install` — are in the [install guide](https://amirnaderi93.github.io/pykrete/getting-started/install/).

Each install gives you two binaries: `pykrete` (the checker, for CLI and CI) and `pykrete-lsp` (the language server for your editor).

## What you get

- **Typos caught as you type** — every column reference, against the schema in scope, with a _did you mean_.
- **Checks that follow the data** — `select` / `filter` / `withColumn` / `drop` / `join` / `groupBy` + `agg` / `pivot` / `union` and the rest; a reference to a column three transforms after it was dropped is still caught.
- **Schema visibility** — hover a `SparkFrame[…]` or `PandasFrame[…]` parameter to see its columns; go-to-definition jumps to the schema.
- **TypeScript-style schema composition** — `Pick`, `Omit`, and `Merge` build derived shapes without redeclaring columns.
- **Column-name autocomplete** in string arguments.
- **Inline SQL checked too** — identifiers inside `filter("…")`, `selectExpr(...)`, `spark.sql("SELECT …")`.
- **Zero runtime cost** — `.pyk` is a strict superset of Python; the deployed job is ordinary Python.

## Reliability and trust

Pykrete is a development-time checker, not a runtime dependency. Your `.pyk` files transpile to plain Python — Spark runs the same Python it always did. **Pykrete cannot break a production pipeline because pykrete is not in the production pipeline.**

What this means in practice:

- **Static analysis runs in your editor, pre-commit hook, or CI.** The `pykrete` binary never ships to production hosts.
- **The transpile step is small and well-defined.** It prepends `from __future__ import annotations` and strips the pykrete-only `.cast(SparkFrame[Schema])` re-anchor calls — these exist purely to help the checker; PySpark's `DataFrame` has no `.cast` method, so the call would `AttributeError` at runtime regardless. Everything else is copied verbatim, line numbers preserved. Run `pykrete transpile path/to/file.pyk` and diff against the source to see exactly what changed.
- **Adopting pykrete is reversible.** Run `pykrete transpile` once to bake the `.pyk` → `.py` rewrite into your repo, commit the result, and you've vendored your way off pykrete. No runtime dependency to remove (there isn't one), no binary on production hosts (there never was one).

### How we earn confidence

We hold pykrete to PySpark's standard because that's the standard that matters:

- **Cross-tested against the real PySpark and pandas stack on every release.** The [pykrete-tests](https://github.com/amirnaderi93/pykrete-tests) repo vendors **`171 fixtures` from `17 donors`** (58 annotated + 113 deliberately-corrupted under `probes_negative/`). The 10 PySpark donors — Apache Spark itself, Delta Lake, Apache Iceberg ([iceberg-python](https://github.com/apache/iceberg-python)), Apache Hudi, MLflow, Feast, Kedro ([kedro-plugins](https://github.com/kedro-org/kedro-plugins)), [quinn](https://github.com/MrPowers/quinn), [dbt-spark](https://github.com/dbt-labs/dbt-spark), and [python-deequ](https://github.com/awslabs/python-deequ) — cover the dominant Spark stack. The 10 pandas-coverage donors split into three honest scoping classes: **3 hybrid** (MLflow, Feast, iceberg-python) carry pandas fixtures on top of their existing Spark coverage; **3 direct-dispatch** ([prophet](https://github.com/facebook/prophet), [seaborn](https://github.com/mwaskom/seaborn), [yfinance](https://github.com/ranaroussi/yfinance)) annotate the actual upstream library code where pykrete's dispatched-shape recognizers match real call sites; **4 canonical-fixture-only** ([scikit-learn](https://github.com/scikit-learn/scikit-learn), [statsmodels](https://github.com/statsmodels/statsmodels), [pandera](https://github.com/unionai-oss/pandera), [Great Expectations](https://github.com/great-expectations/great_expectations)) ship user-pattern fixtures inspired by each library's API — the upstream code itself operates at numpy / metric layers above raw pandas dispatch, so the fixtures stand in for what a real user writes at the pandas boundary. Each donor's PySpark or pandas code is preserved verbatim under `upstream/`, paired with an `annotated/` companion that adds the pykrete schema declarations an adopter would write; pykrete runs against the annotated form. Each push rebuilds pykrete from the catalog-pinned source commit (`scripts/diagnostic_catalog.json`'s `pykreteSourceCommit`), re-runs `pykrete check` against every fixture, and JSON-diffs the output against the committed golden — a new false positive on real Spark or pandas code blocks the release before the tag goes out.
- **Schema tracking is verified, not assumed.** On top of the golden-diff suite, we run **`312 probes`** that assert pykrete is actually tracking columns through real transforms. The probes cover the 170 probe-bearing fixtures of the 171 vendored (57 annotated + 113 negative; the one remaining annotated fixture is a probe-free streaming fixture with no typed-DataFrame slot to anchor to): `195 positive` probes verify columns resolve cleanly after `.select` / `.filter` / `.withColumn` and the pandas analogues, AND that dtype claims on `SparkFrame[X]` / `PandasFrame[X]` parameters survive dispatched chains (24 `PROBE-TYPE-IS` markers across 10 of the `17 donors` — the v1.2 Spark side and the v1.4 pandas side, closing pykrete-tests#14); `117 negative` probes across the 113 deliberately-corrupted fixtures verify specific diagnostics — D0030 `unknownColumn`, D0040 / D0050 / D0051 (cross-codebase coverage added in v1.7), D0060 `missingJoinKey`, D0073 `transformInputMismatch` (cross-codebase coverage added in v1.8 per pykrete-tests PR-P1 #30), D0080 `returnTypeMismatch` (cross-codebase coverage added in v1.12 per pykrete-tests PR-P1 #42, closing the longest-standing gap since v1.6), D0081 `nonNumericArithmetic` (v1.4 widens it to subscript-on-name receivers), D0082 `crossTypeComparison` (v1.4 widens correspondingly), D0083 `nullabilityMismatch` (cross-codebase coverage added in v1.8 per pykrete-tests PR-P1 #30), D0084 `enumValueMismatch`, D0090 `deprecatedDataFrameAlias`, and D0091 `crossDialectMethodMismatch` (cross-codebase coverage added in v1.9 per pykrete-tests PR-P1 #32 on pandera + delta, extended in v1.10 PR-P1 with D0091 strict-mode escalation + bare-attribute + shape-changes probes on `mlflow` / `dbt-spark` / `pandera` / `delta`, extended again in v1.11 PR-P1 #39 with 8 new D0091 property probes covering the v1.10 PR-D1 surface) — actually fire. Together, these verify four properties on every release: **column resolution + diagnostic firing + Spark type tracking + pandas type tracking**. We verify enum value vocabularies in 3 of `17 donors`: Delta CDC `_change_type` (`{"insert", "update_preimage", "update_postimage", "delete"}`), Hudi `_hoodie_operation` (`{"I", "-U", "U", "D"}`), and MLflow run status (`{"RUNNING", "FINISHED", "FAILED", "KILLED", "SCHEDULED"}`). **New in v1.12**: D0080 `returnTypeMismatch` cross-codebase trust coverage lands (pykrete-tests PR-P1 #42), closing the longest-standing gap since v1.6. The CI-side release-gate wiring tracked for v1.12 ships too — the auto-label workflow now dispatches `release-gate.yml` via the `actions.createWorkflowDispatch` API, bypassing GitHub's GITHUB_TOKEN cross-workflow no-trigger rule so the release-gate fires non-skipped on labeled PR events end-to-end. Pandas `pivot_table(aggfunc=)` literal-form recognition lands as informational scaffolding against an 11-string allowlist (`sum` / `mean` / `count` / `min` / `max` / `median` / `std` / `var` / `first` / `last` / `nunique`); recognition is informational (no diagnostic; result schema unchanged) and primes v1.13+ aggfunc-driven inference. Multi-line ack-marker rationale blocks (`# pykrete: ack-deprecation` shape b) now extend acknowledgement to the entire contiguous comment block above the anchor (spec §6.1.4) — adopters with ack-deprecation tooling that depended on v1.10's strict-single-line semantic should update. **New in v1.13**: D0080 `returnTypeMismatch` gets its **dialect-on-return checker arm** — the longest-standing 7-cycle correctness gap closes. A function annotated `-> SparkFrame[X]` returning a `.toPandas()` chain (or any expression resolving to `PandasFrame[…]`) now fires D0080 with a dedicated dialect-mismatch message. Pandas `pivot_table(aggfunc=)` graduates from informational allowlist recognition to **Derived-schema synthesis** — the first observable aggregate-semantics-informed schema inference: `count` / `nunique` → int64, `mean` / `std` / `var` / `median` → float64, `sum` / `min` / `max` / `first` / `last` preserve the receiver column's type. The **backtick-preservation tripwire** prevents the 2-cycle backtick-strip regression class from recurring, and the **dispatched-run required-status-check** retires the v1.12 polling-step workaround. **Adopters with code that incorrectly cross-converts dialects at function boundaries, or that accidentally accessed non-`values=` columns post-`pivot_table`, will see new D0080 / D0030 fires.** **New in v1.14**: D0080's constructor carve-out closes — `-> SparkFrame[X]` returning `pd.DataFrame({...})`, or `-> PandasFrame[X]` returning `spark.read.parquet(path)`, now fires D0080, and `spark.createDataFrame(rows, schema=<Schema>)` fires when the dialect disagrees with the annotation. When both dialect and column-type mismatches land on the same return, D0080 emits a single multi-clause message rather than two stacked fires (one fire, two clauses) — CI greps for "two D0080 fires at the same range" need to adjust. Pandas `df.groupby(...).agg({col: aggfunc})` synthesizes a `Derived` envelope mirroring the v1.13 `pivot_table(aggfunc=)` arm: `count` / `nunique` → int64; `mean` / `std` / `var` / `median` → float64; `sum` / `min` / `max` / `first` / `last` preserve. `pykrete check --deprecation-report --compare-to=<prior.json>` emits a SIMPLE three-bucket diff (`added` / `removed` / `unchanged`) with exit-nonzero on `added`; mutually exclusive with `--ack` / `--snapshot` / `--fail-on-nonempty`. The envelope round-trips a v2 provenance pair (`pykreteSourceCommit` + `generatedAt`) so CI snapshot artifacts carry author-pinpointing metadata. **New in v1.15**: pandas chain-depth extends through `groupby.agg().reset_index(drop=True)` — the synthesized `Derived` envelope now survives a `.reset_index(drop=True)` call, so a downstream `result["typo"]` after `pdf.groupby("k").agg("sum").reset_index(drop=True)` fires D0030 against the keys + aggregate columns instead of degrading to Unknown. `pdf.set_index([literal-keys])` removes the named literal-key columns from the accessible schema — a downstream `result["literal_key"]` fires D0030. **Adopters who incorrectly accessed non-aggregate columns after `groupby.agg().reset_index(drop=True)`, or who accessed literal keys after `set_index([keys])`, will see new D0030 fires** — align downstream code with the synthesized schema or access keys via `.index` (not modeled). The v1.15 cycle also closes the v1.14 PR-P1 synthesis-arm cross-codebase coverage gaps with positive probes against `groupby.agg` and negative probes against D0080 constructor returns on real-library fixtures, lands the `resolve_override_ty` primitive that helper-consolidates the dtype-override family in preparation for the window-aggregation arms (the `Windowed` lattice variant was evaluated and rejected in v1.16 in favor of direct-chain recognition; deferred to v1.17), and ships the marketing-table gate v3 fence-vs-claim discipline. D0082 `crossTypeComparison` keeps its falsifiability through raw-mutation fixtures in the test suite until dedicated synth shapes ship. Numeric-subtype distinguishability (`int` vs `long` vs `short`) and `withColumn` output enum-constraint preservation are carried forward in the polish backlog. **New in v1.16**: pandas reshape modeling extends to time/window aggregation — `resample.agg` synthesizes a Derived schema by the aggregate-to-dtype table, `rolling.agg` aggregates numeric columns to Double (and honestly declines to Unknown on any frame with a non-numeric column), and dict-form / callable `groupby.agg` synthesize Derived schemas. These window-aggregation arms have **no cross-codebase probes yet — they are unit-tested in-crate, with cross-codebase coverage deferred to v1.17**. The cross-codebase corpus grows to `312 probes` across `171 fixtures` via the v1.15-mandated `reset_index(drop=True)` + `set_index([key])` chain probes plus `groupby.agg` donor widening (pykrete-tests PR-P1 #54); those reset_index / set_index probes verify column-**name** tracking (that the chain stays non-Unknown), while dtype-correctness on the chains is carried by the golden-diff suite, not the probe suite. **Adopters who chained off an `inplace=True` `reset_index` / `set_index` result were relying on a schema pandas never returns** — drop `inplace=True` and rebind. Adopters who accessed columns dropped by a dict-form `groupby.agg` will see new D0030 fires. v1.16 also removes a false positive that had been live since v1.14: named-aggregation `groupby(k).agg(out=(col, fn))` synthesized a keys-only schema, dropping the named outputs and firing a bogus `returnColumnsMismatch` on correct code; it now declines to Unknown, with precise per-output-column modeling deferred to v1.17. CI fails if any probe asserts the wrong outcome. See the [pykrete-tests README](https://github.com/amirnaderi93/pykrete-tests#schema-tracking-probes-v14) and [`scripts/PROBES.md`](https://github.com/amirnaderi93/pykrete-tests/blob/main/scripts/PROBES.md) for the methodology; per-donor matrix and pinned commits live in the [donors table](https://github.com/amirnaderi93/pykrete-tests#the-donors).
- **`2094 tests` in CI across the analyzer, LSP, and wasm crates.** Every release has to pass the full suite, plus per-D-code snapshot tests that pin every error message — wording drifts fail the build until explicitly accepted.
- **JSON output is a stability contract from v1.0.0.** Field names, types, semantics, and D-code identity will not change without a SemVer-major bump and a corresponding `schemaVersion` bump. See [Production readiness → JSON output stability contract](https://amirnaderi93.github.io/pykrete/about/production-readiness/#json-output-stability-contract).
- **No-false-positives policy.** When pykrete cannot determine a schema or a type with confidence, it stops checking that subtree rather than guessing. A static checker that cries wolf gets switched off.
- **Pre-major-release audit cycle.** Every X.0.0 bump runs three independent fresh-eyes audits (architecture, Spark coverage, docs sync) before the tag. Findings ship in the release notes.
- **One-command v2.0 migration, plannable AND archivable in CI.** With v1.7, **v2.0 is one command away**: `pykrete migrate src/` previews; `pykrete migrate --apply src/` rewrites. With v1.8, **v2.0 readiness is measurable**: `pykrete check --deprecation-report src/` emits a JSON envelope listing every D0090-firing site with its adjudicated dialect and suggested rewrite. With v1.9, **v2.0 migration is plannable**: the envelope bumps to `deprecationReportVersion: "2"` with per-site `migrationStatus` (`pending` / `acknowledged`) driven by a `# pykrete: ack-deprecation` comment marker, plus a `--ack=<pending|acknowledged>` filter that narrows the envelope to one cohort for CI gating. With v1.10, **v2.0 migration is archivable**: `pykrete check --deprecation-report --snapshot=<path>` writes the v2 envelope to disk so CI can persist a prior-report cache and diff between releases, and `--fail-on-nonempty` exits non-zero when `sites` is non-empty — drop `pykrete check --deprecation-report --fail-on-nonempty src/` into CI to fail on any unacked site without the `jq | test` boilerplate. With v1.11, **the v1.10 D0091 8-property surface is cross-codebase-covered** (pykrete-tests PR-P1 #39) and the audit-tooling block ships (`trust-claim-sweep-checklist.sh` + `changelog-cite-check.sh` + auto-label workflow). With v1.12, **D0080 returnTypeMismatch is cross-codebase-covered** (pykrete-tests PR-P1 #42) — the longest-standing trust gap since v1.6 closed — and the v1.11 calendared GITHUB_TOKEN promise lands: the auto-label workflow now dispatches `release-gate.yml` via the `actions.createWorkflowDispatch` API so the release-gate fires non-skipped on labeled PR events end-to-end. With v1.13, **D0080 gets its dialect-on-return checker arm** and the `pivot_table(aggfunc=)` Derived synthesis ships, plus the backtick-preservation tripwire and dispatched-run required-status-check. With v1.14, **D0080's constructor carve-out closes** (cross-dialect constructor returns now fire), `groupby.agg` Derived synthesis lands as the sibling to v1.13's `pivot_table(aggfunc=)`, and `--compare-to` ships a SIMPLE three-bucket snapshot diff (exit-nonzero on `added`) with the envelope schema v2 provenance pair (`pykreteSourceCommit` + `generatedAt`). With v1.15, **pandas chain-depth extends through `reset_index(drop=True)` + `set_index([literal-keys])`** so the v1.14 `groupby.agg` synthesis survives one more transform, the v1.14 synthesis-arm cross-codebase coverage gaps close (positive probes on `groupby.agg` and negative probes on D0080 constructor returns landed in pykrete-tests PR-P1 #50), the dtype-override family consolidates behind a shared `resolve_override_ty` primitive in preparation for the window-aggregation arms (the `Windowed` lattice variant was evaluated and rejected in v1.16 in favor of direct-chain recognition; deferred to v1.17), and the audit-tooling block gains marketing-table gate v3 (fence-vs-claim discipline for `<num> <key>` markdown-table cells). With v1.16, **pandas reshape modeling reaches time/window aggregation** — `resample.agg` + `rolling.agg` + dict-form/callable `groupby.agg` synthesize Derived schemas (the window-agg arms are unit-tested in-crate; cross-codebase coverage is tracked for v1.17), the named-aggregation `groupby(k).agg(out=(col, fn))` false positive is fixed by declining to Unknown, and the §9.2 centralized-bump mechanism is repaired via corrected cycle-0 sequencing (the marker file is retired; enforcement keys on the `chore(release):` release-PR title). The envelope deliberately ships without `targetVersion` / `removalVersion` / `shipDate` — pykrete tracks per-site migration progress; the user picks the v2.0 ship date. `DataFrame[X]` is a deprecated alias slated for removal in a future pykrete v2.0. v1.6 shipped `pykrete migrate` — it walks each binding's downstream usage, classifies it as Spark / pandas / ambiguous via call-graph adjudication, and rewrites the annotation in place to the dialect-tagged canonical name (atomic per file, token-preserving). v1.7 flips the default to `--check` (preview verdicts on stdout) and adds `--apply` as the opt-in for the in-place rewrite. Under `"typeCheckingMode": "strict"`, D0090 escalates from warning to error so strict-mode projects gate on the migration; v1.9 lands the same strict-mode escalation for D0091 `crossDialectMethodMismatch`. Non-strict modes keep the warning unchanged. See [Migrating to v2.0](https://amirnaderi93.github.io/pykrete/cookbook/#6-migrate-dataframex-to-the-v20-dialect-tagged-names) for the cookbook recipe.

If pykrete is wrong on your code, [open an issue](https://github.com/amirnaderi93/pykrete/issues) — false positives are triaged ahead of everything else.

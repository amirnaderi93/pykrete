and Microsoft's pyright runs alongside it in a Web Worker — the same
engines the VS Code extension uses. No code leaves your machine.

## What you're seeing

Every keystroke (debounced ~300 ms) runs the source through pykrete's
single-file analyzer **and** pyright in `typeCheckingMode: 'standard'`
— the same mode the VS Code extension configures. Diagnostics from
both engines show up as squiggles in the editor and as one-liners in
the panel below — pykrete's keep their `D\d\d\d\d` codes; pyright's
are prefixed `py:`.

The playground multiplexes both engines into Monaco for every IDE
feature, the same way the LSP server does for the VS Code extension:

- **Hover.** Hover a Schema class name to see its fields; hover any
  Python identifier to see pyright's type information. When both
  engines have something to say, the popup stacks pykrete's content
  on top, then a horizontal rule, then pyright's. Schema hovers
  suppress pyright's "(class) Foo" echo (same rule as the VS Code
  extension — the schema heading already covers it).
- **Completion.** Type a column name inside `col("…")` to get
  pykrete's column suggestions; type `pri` at the top level to get
  pyright's `print` (with its standard-library signature); inside a
  `DataFrame[…]` slot you get every Schema declared in the source;
  inside any function call, pyright supplies argument-name and
  keyword completions for the Python standard library and any
  imports you reference. Pykrete suggestions come first.
- **Go-to-definition.** Cmd/Ctrl+click (or F12) on a `DataFrame[X]`
  reference to jump to `class X(Schema):`; jump to any in-file `def`
  or `class` via pyright when pykrete doesn't know the symbol.
- **Python type checking.** pyright runs in standard mode and
  publishes type errors as you type. Same diagnostic list, prefixed
  with `py:` so you can tell them apart from pykrete's.

The wasm playground is single-file only: no cross-file resolution, no
project config, no `.pyk-import` declarations. Pyright also only sees
the one file you're editing — third-party packages declared via
`import` resolve against pyright's bundled typeshed stubs (so
`import numpy as np` and hovering `np.array` works), but anything
that needs cross-file project analysis needs the CLI.

## Limits

- **No share-via-URL yet.** Refresh discards your edits. Bookmarkable
  snippet URLs are on the roadmap.
- **Desktop-first.** Monaco editor is hard to use on a phone; the
  diagnostics list is still useful on small screens, but typing is
  not.
- **Single-file analysis only.** Multi-file imports, project
  configuration, and the `.pyk-import` mechanism need real file
  system access — use the CLI for those.
- **Cold-start bundle is large.** Monaco loads from a CDN (~2 MB);
  pykrete-wasm and pyright-browser are each a few MB and load on
  demand when this page mounts. Other pages on the docs site are
  unaffected.

## Want it locally?

```bash
pip install pykrete
pykrete check path/to/your/file.pyk
```

The [Install](/pykrete/getting-started/install/) page walks through
the full editor setup (LSP for autocomplete and hover, the VS Code
extension, project configuration).

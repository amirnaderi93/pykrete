## The bug that reaches production

Rename a column. Mistype it once, three transforms downstream. Nothing stops you — not the interpreter, not the linter, not your tests, unless one happens to assert on that exact name.

The job runs. It returns an empty dataframe, a column of nulls, a number that's quietly wrong. You find out later — in a scheduled run, a blank dashboard, a metric nobody trusts anymore.

pykrete catches it while you type.

<EditorShowcase />

Tell pykrete the shape of a dataframe — a `Schema` class, a `SparkFrame[Sale]` (or `PandasFrame[Sale]`) annotation — and it checks every column you touch, the whole way down the chain. (`DataFrame[Sale]` is a deprecated alias for `SparkFrame[Sale]`, still accepted through the v1 line.)

## Start with one file

You don't convert a codebase. You convert a file.

<Steps>

1. **Rename it.** `mv sales.py sales.pyk` — `.pyk` is a strict superset
   of Python, so the file runs exactly as it did.

2. **Declare the schema.** A short class naming the columns you already
   know.

3. **Annotate a function.** Add `SparkFrame[Sale]` (or `PandasFrame[Sale]`)
   to one parameter. That function is now checked, end to end.

</Steps>

That's the whole investment. The rest of your repo stays plain Python — pykrete only checks what you've annotated. Add the next schema when it earns its place, not before.

## Proven on real code

Every release is regression-tested against **233 schema-tracking probes across 93 fixtures from 17 real codebases** — the 10-donor PySpark core (Apache Spark, Delta Lake, Apache Iceberg, Apache Hudi, MLflow, Feast, Kedro, quinn, dbt-spark, python-deequ) covering the dominant Spark stack, and 10 pandas-coverage donors covering the dominant pandas stack (ML preprocessing, stats / econometrics, schema validation, data quality, forecasting, visualization, financial market data). The pandas donors split into three honest scoping classes: 3 hybrid carry-overs from v1.3 (MLflow, Feast, iceberg-python), 3 direct-dispatch (prophet, seaborn, yfinance — annotated against actual upstream code where pykrete's dispatched-shape recognizers match), and 4 canonical-fixture-only (scikit-learn, statsmodels, pandera, Great Expectations — modeling user-pattern fixtures inspired by each library's API, since the upstream code operates at numpy / metric layers above raw pandas dispatch). The probes don't just check that pykrete stays quiet on real code; they assert it actually tracks columns through real transforms, that the diagnostics we promise actually fire on deliberately-broken fixtures, that dtype claims on `SparkFrame[X]` / `PandasFrame[X]` parameters survive dispatched chains, and — new in v1.5 — that schema rides cleanly across the Spark↔pandas boundary (`.toPandas()` re-tags `SparkFrame[X]` to `PandasFrame[X]`; `spark.createDataFrame(pdf)` re-tags back when a schema source is present).

## Get started

[Installing pykrete](/getting-started/install/) takes a minute. The [quickstart](/getting-started/quickstart/) gets a real function under checking in five.

PySpark is supported today; pandas check-site coverage shipped in v1.3, v1.4 added depth on pandas (7 new pandas-heavy donors + pandas type-tracking), and v1.5 adds the cross-dialect handoff between Spark and pandas (`.toPandas()` / `spark.createDataFrame(pdf)`, dialect-gated `.head` / `.tail` / `.first`, `.loc[:, "col"]` literal-form, plus a `--report-aliases` JSON envelope for sizing the v2.0 `DataFrame[X]` migration). Next up: `pykrete migrate` paired with D0090 strict-mode escalation, broader `.loc` / `.iloc`, `.query` / `.eval` mini-DSLs, pandas reshape, and polars — see the [roadmap](/about/roadmap/) (with the [pandas roadmap](/about/pandas-roadmap/) breaking down the pandas-specific direction across v1.6+ and v2.0).

## The bug that reaches production

Rename a column. Mistype it once, three transforms downstream. Nothing stops you — not the interpreter, not the linter, not your tests, unless one happens to assert on that exact name.

The job runs. It returns an empty dataframe, a column of nulls, a number that's quietly wrong. You find out later — in a scheduled run, a blank dashboard, a metric nobody trusts anymore.

pykrete catches it while you type.

<EditorShowcase />

Tell pykrete the shape of a dataframe — a `Schema` class, a `DataFrame[Sale]` annotation — and it checks every column you touch, the whole way down the chain.

## Start with one file

You don't convert a codebase. You convert a file.

<Steps>

1. **Rename it.** `mv sales.py sales.pyk` — `.pyk` is a strict superset
   of Python, so the file runs exactly as it did.

2. **Declare the schema.** A short class naming the columns you already
   know.

3. **Annotate a function.** Add `DataFrame[Sale]` to one parameter.
   That function is now checked, end to end.

</Steps>

That's the whole investment. The rest of your repo stays plain Python — pykrete only checks what you've annotated. Add the next schema when it earns its place, not before.

## Proven on real code

pykrete runs against annotated snapshots of real PySpark codebases — Apache Spark's own test suite, MLflow — on every change, in CI. It's tested where the dataframes are messy, not just on tidy examples.

## The bug that reaches production

Rename a column. Mistype it once, three transforms downstream. Nothing stops you — not the interpreter, not the linter, not your tests, unless one happens to assert on that exact name.

The job runs. It returns an empty dataframe, a column of nulls, a number that's quietly wrong. You find out later — in a scheduled run, a blank dashboard, a metric nobody trusts anymore.

pykrete catches it while you type.

<EditorShowcase />

Tell pykrete the shape of a dataframe — a `Schema` class, a `SparkFrame[Sale]` (or `PandasFrame[Sale]`) annotation — and it checks every column you touch, the whole way down the chain. (`DataFrame[Sale]` is a deprecated alias for `SparkFrame[Sale]`, still accepted through the v1 line.)

## Start with one file

You don't convert a codebase. You convert a file.

<Steps>

1. **Rename it.** `mv sales.py sales.pyk` — `.pyk` is a strict superset
   of Python, so the file runs exactly as it did.

2. **Declare the schema.** A short class naming the columns you already
   know.

3. **Annotate a function.** Add `SparkFrame[Sale]` (or `PandasFrame[Sale]`)
   to one parameter. That function is now checked, end to end.

</Steps>

That's the whole investment. The rest of your repo stays plain Python — pykrete only checks what you've annotated. Add the next schema when it earns its place, not before.

## Proven on real code

Every release is regression-tested against **`261 probes` across the probe-anchored fixtures of `120 fixtures` from `17 donors`** — the 10-donor PySpark core (Apache Spark, Delta Lake, Apache Iceberg, Apache Hudi, MLflow, Feast, Kedro, quinn, dbt-spark, python-deequ) covering the dominant Spark stack, and 10 pandas-coverage donors covering the dominant pandas stack (ML preprocessing, stats / econometrics, schema validation, data quality, forecasting, visualization, financial market data). The pandas donors split into three honest scoping classes: 3 hybrid carry-overs from v1.3 (MLflow, Feast, iceberg-python), 3 direct-dispatch (prophet, seaborn, yfinance — annotated against actual upstream code where pykrete's dispatched-shape recognizers match), and 4 canonical-fixture-only (scikit-learn, statsmodels, pandera, Great Expectations — modeling user-pattern fixtures inspired by each library's API, since the upstream code operates at numpy / metric layers above raw pandas dispatch). The probes don't just check that pykrete stays quiet on real code; they assert it actually tracks columns through real transforms, that the diagnostics we promise actually fire on deliberately-broken fixtures, that dtype claims on `SparkFrame[X]` / `PandasFrame[X]` parameters survive dispatched chains, that schema rides cleanly across the Spark↔pandas boundary (`.toPandas()` re-tags `SparkFrame[X]` to `PandasFrame[X]`; `spark.createDataFrame(pdf)` re-tags back when a schema source is present), and — new in v1.10 — that D0091 `crossDialectMethodMismatch` strict-mode escalation, bare-attribute path, and shape-changes hint all hold on deliberately-corrupted cross-codebase fixtures (6 new negative probes from [pykrete-tests PR-P1 #34](https://github.com/amirnaderi93/pykrete-tests/pull/34) on `mlflow` / `dbt-spark` / `pandera` / `delta`).

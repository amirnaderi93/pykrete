## 2. Pillar A — `workflow_dispatch` API call from auto-label (1 PR: A1)

The cycle's calendared closure on the v1.11.0 trigger-boundary
promise. v1.11 PR-A2 shipped the auto-label workflow correctly;
post-merge observation surfaced that the `GITHUB_TOKEN`-issued
`addLabels` API call does NOT trigger downstream workflows (this
is documented GitHub Actions behavior — supply-chain protection
against runaway recursion). v1.12 PR-A1 closes the gap.

### 2.1 PR-A1 — `workflow_dispatch` API call (option (c))

Extend `.github/workflows/auto-label-release-pr.yml` so that after
the `addLabels` call succeeds, the workflow ALSO calls
`actions.createWorkflowDispatch` against `release-gate.yml`,
passing the PR number as a workflow input. The release-gate
workflow then runs as if a human had clicked "Run workflow," with
PR context recovered from the dispatched input.

#### 2.1.1 Why option (c), not (a) or (b)

- **Option (a) — switch the auto-label trigger to
  `pull_request_target`**: REJECTED. `pull_request_target` runs
  in the BASE-repo context with WRITE permissions on the base
  repo, which would let an external PR author's malicious commit
  exfiltrate secrets. This is the documented GitHub supply-chain
  crack pattern; we hard-reject it.
- **Option (b) — use a PAT (personal access token) to write the
  label**: REJECTED. PAT rotation is a manual maintenance burden;
  the token would have wider scope than the workflow needs; and a
  leaked PAT compromises the user's entire GitHub account, not
  just the repo. Net cost outweighs the value.
- **Option (c) — keep `GITHUB_TOKEN`-issued `addLabels`, ALSO
  call `workflow_dispatch` against `release-gate.yml` from the
  same workflow**: ACCEPTED. `workflow_dispatch` from
  `GITHUB_TOKEN` IS permitted (it's not a supply-chain risk
  because the workflow being dispatched is in the same repo and
  was already authorized to run on its own triggers). The dispatch
  call hands `release-gate.yml` the PR number; `release-gate.yml`
  re-fetches PR context via `gh pr view` and runs as if labeled.

#### 2.1.2 Permission bump

The current `auto-label-release-pr.yml` declares
`permissions: pull-requests: write`. PR-A1 ADDS
`actions: write` (required for the `createWorkflowDispatch` API
call). No other permissions change.

#### 2.1.3 Why not modify `release-gate.yml` to also trigger on `workflow_dispatch`

It already does — `release-gate.yml` has a `workflow_dispatch`
trigger (verifiable via grep on the file at HEAD). The change is
on the auto-label side only; the release-gate accepts the
dispatched event unchanged.

#### 2.1.4 Sibling-arm grep before declaring scope (v15-rule 4 / v1.12 §13)

```
grep -rn 'workflow_dispatch\|createWorkflowDispatch\|release-gate\|auto-label' \
  .github/workflows/
```

Implementer enumerates per-symbol counts (not aggregate across
siblings) on HEAD and reports post-PR delta in the PR body.
Per-symbol convention codified in §13.

#### 2.1.5 Negative-space tests MANDATORY per v14-rule 4

- A PR with a commit `chore(release): v1.12 PR-F — trust-claim
  migration…` opens → auto-label applies `release-ready` →
  `release-gate.yml` is dispatched → release-gate runs the full
  sweep. End-to-end observed on PR-F's `labeled` event (per
  §12 dispatched-event verification standing rule).
- A PR with a non-`release-ready` discriminator → label NOT

- The `actions: write` permission is observed in the workflow's

## 3. Pillar A — release-gate runner perf investigation (1 PR: A2)

Per v1.5 retro architectural-heterogeneity rule (Rust + Bash/CI
land in separate PRs). A2 is workflow-perf; A1 is workflow-trigger
— same surface (`.github/workflows/`), but separable concerns and
separable verifications.

### 3.1 PR-A2 — Release-gate runner perf investigation

v1.11 PR-F observed the release-gate workflow stuck 25+ minutes
on `CHANGELOG grep gate — full live extract`. Expected runtime is
under 5 minutes (the previous cycles' observed range). A2
investigates the regression and fixes the root cause(s).

#### 3.1.1 Hypotheses to investigate

The CHANGELOG grep gate's full live extract includes (per
`scripts/changelog-grep.sh` and its sub-tools):
1. **Cargo cache warm-up** — cold cargo cache adds significant
   compile time on the first `cargo test` invocation per run.
   v1.11 may have pulled in a heavier transitive crate.
2. **Python startup** — the live-extract uses
   `python3 scripts/probes.py extract`. Cold Python + first-import
   of pyspark / pandas can add seconds; if probes.py grew its
   dependency graph in v1.10 / v1.11, the cold-start cost grew.
3. **Sibling-checkout I/O** — the live-extract clones pykrete-
   tests into a sibling working dir. If the sibling-checkout shape
   uses a full clone rather than a shallow clone, I/O dominates.
4. **GitHub-hosted runner I/O** — `ubuntu-latest` runners have
   bursty I/O; the issue MAY be a runner-side artifact rather
   than our script.

#### 3.1.2 Approach

PR-A2 ships in two passes:

1. **Pass 1 — instrumentation**: add per-step `time` reporting
   to `scripts/changelog-grep.sh` and the release-gate workflow's
   sub-steps. Run the gate 3-5 times against v1.11 PR-F's diff
   shape to identify which sub-step dominates wall-clock. Report
   findings in PR-A2's body.
2. **Pass 2 — fix**: depending on Pass 1 findings, ship one or
   more of: cargo-cache prune (drop cached build artifacts older
   than N cycles); shallow-clone of pykrete-tests sibling; lazy-
   import of pyspark / pandas in `probes.py` (if the cold-import
   is the dominant cost); runner upgrade flag (e.g., switch to
   a larger runner if I/O is the bottleneck).

#### 3.1.3 Scope guardrail

PR-A2 ships ONLY the fix that Pass 1 identifies. If Pass 1 shows
the wall-clock is evenly distributed across all 4 hypotheses
(unlikely but possible), A2 ships the instrumentation + ONE
representative fix, and the rest goes to v1.13 backlog. The PR
body documents the rationale either way.

#### 3.1.4 Sibling-arm grep before declaring scope (v15-rule 4 / §13)

```

  scripts/ .github/workflows/
```

Implementer reports per-symbol counts on HEAD.

#### 3.1.5 Negative-space tests MANDATORY per v14-rule 4

  wall-clock measured.
- Post-fix: release-gate workflow runs on v1.12 PR-F's diff →

## 4. Pillar D — pandas `pivot_table(aggfunc=)` literal-form arm extension (1 PR: D1, ARM EXTENSION, NOT NEW DISPATCH)

### 4.1 PR-D1 — pandas `pivot_table(aggfunc=)` literal-form

**Receiver gate**: PandasFrame[X] only. Same arm as v1.6 PR-D1
(`pivot_table`); the receiver gate is unchanged.

**Recognized `aggfunc` literal forms**:
- A literal string from the allowlist: `"sum"`, `"mean"`,
  `"count"`, `"min"`, `"max"`, `"median"`, `"std"`, `"var"`,
  `"first"`, `"last"`, `"nunique"`. Allowlist sourced from
  pandas docs' canonical aggfunc string set.
- A literal list of strings from the allowlist (e.g.,
  `aggfunc=["sum", "mean"]`).

**Falls through silently** (no inference contribution; result
schema follows the existing v1.6 PR-D1 path) on:
- A callable (`aggfunc=np.sum`).
- A dict (`aggfunc={"a": "sum", "b": "mean"}`).
- A non-literal string (`aggfunc=some_var`).
- A literal string NOT in the allowlist (`aggfunc="exotic_thing"`).

**Why allowlist not deny-list**: the allowlist is the pandas-
documented canonical set. A string outside the set is either a
user-defined aggregation registered via pandas' agg registry (rare;
fall through to Unknown is honest) or a typo (in which case
silence is preferable to a false D0030 — pandas itself raises a
KeyError at runtime, and we don't model that). TypeScript-style
"narrow when you can, widen when you can't" applies.

**Why this is NOT a new arm**: the `pivot_table` arm already
dispatches on `PandasFrame` receiver + `pivot_table` method name.
v1.12 PR-D1 extends the SAME arm's kwarg-recognition branch to
include `aggfunc`. Per v1.5 retro rule 2 (dual-arm dispatch
load-bearing): the v1.6 arm's dispatch position is unchanged; only
the kwarg-recognition body is extended. NOT a sibling-arm
restructure.

**Inference logic** (extension to v1.6 PR-D1):
- When `aggfunc` is a literal allowlist string → the result
  schema's value-columns inherit the dtype from the pivoted
  value-column UNCHANGED for v1.x. The v1.4 pandas-support.md
  §5 carve-out (index modeling out-of-scope) constrains the
  result schema to "remaining columns" with the value column
  re-emitted; aggfunc choice doesn't influence which columns
  survive.
- When `aggfunc` is a literal list of allowlist strings → result
  schema is computed per the v1.6 PR-D1 multi-value behavior; the
  aggfunc list doesn't add columns at the schema-tracking level.
- Anything else → fall through to the existing v1.6 PR-D1 path
  unchanged.

Per v1.4 retro rule 4 + v1.8 retro rule 9 + v1.10 retro carry.
Even though this is an EXTENSION not a NEW arm, the recognition

## 6. Pillar V — multi-line ack-marker shape (b) rationale block (1 PR: V1, alias_report.rs)

The cycle's V-pillar work. NOT an LSP-side change; the V pillar
is "v2.0 deprecation runway" surface (per v1.8 → v1.11 pillar
mapping), and the multi-line ack-marker rationale block is a
deprecation-runway UX feature.

### 6.1 PR-V1 — multi-line marker block (shape (b))

`alias_report.rs::line_above_has_ack_marker` (last extended in
v1.11 PR-D2) currently checks the SINGLE line directly above the
annotation for `# pykrete: ack-deprecation`. v1.12 PR-V1 extends
this to walk past CONTIGUOUS comment lines above the annotation
looking for the marker. The first contiguous comment line that
matches `# pykrete: ack-deprecation` → site is acknowledged.

Pattern enabled:
```python
# pykrete: ack-deprecation
# rationale: legacy code, will migrate in Q3
x: DataFrame[X] = ...
```

#### 6.1.1 Why this shape

v1.9 v2 envelope already supports `--ack` filtering on the report
side; v1.10 added `--snapshot` for archival. The dev-side
workflow surfaced by users (informal feedback channels) is that
acknowledging without WHY is a fragile signal — six months later
nobody remembers why the marker was placed. The rationale block
solves the "WHY" problem WITHOUT requiring a separate registry
file.

#### 6.1.2 Walk semantics

`line_above_has_ack_marker` walks UP from the annotation byte
offset, line-by-line. For each line:
- If the line matches `# pykrete: ack-deprecation` (with the
  existing tolerance — leading whitespace OK, trailing comment-
  body OK) → return `acknowledged`.
- If the line is a `#`-prefixed comment but does NOT match the
  marker → keep walking.
- If the line is NOT a comment (blank line, code line, decorator,
  anything else) → STOP walking; return `pending` (no marker
  found in the contiguous comment block).

The walk's upper bound is "first non-comment line." In practice,
a rationale block of 1-3 comment lines is the dominant case; the
walker accepts any number of comment lines but stops at the first
non-comment.

#### 6.1.3 What shape (a) and (c) cover (out of scope)

- **Shape (a) — multi-line def signature**: ALREADY shipped in
  v1.10 PR-A1 R2 + v1.11 PR-D2. The walker already crosses
  multi-line def signatures correctly. v1.12 V1 doesn't touch
  this.
- **Shape (c) — multi-statement assignment**: out of scope for
  v1.12. Pattern like:
  ```python
  # pykrete: ack-deprecation
  x = (
  ```

#### 6.1.4 Comment-not-matching-followed-by-marker semantic

The walker MUST be consistent: if the line directly above the
annotation is a NON-matching comment, AND the line above THAT
is the marker, is the site acknowledged or pending?

**Decision**: acknowledged. The walker walks past ANY contiguous
comment block; the marker can appear ANYWHERE in the block.
Rationale: this is the only consistent semantic for the
rationale-block pattern. The dominant case is "marker above
rationale" but some users will write "rationale above marker";
both should work.

Test fixtures:
- 2-line block: marker on line N-1, rationale on line N-2 →
  acknowledged.
- 2-line block: rationale on line N-1, marker on line N-2 →
  acknowledged.
- 3-line block: any of the three lines is the marker →
  acknowledged.
- 3-line block: NONE of the three lines is the marker →
  pending.
- Comment block then blank line then marker → blank line breaks
  the contiguous walk; site is pending. Negative-space coverage
  for the "contiguous" requirement.

## 13. Sibling-arm grep convention — per-symbol counts (v1.11 D2 R2 NEW STANDING)

**NEW STANDING RULE**: per-symbol counts in audit reports + PR
bodies (not aggregate across siblings). When a developer or
auditor runs a sibling-arm grep (per v15-rule 4), the report
enumerates the hit count PER symbol, NOT an aggregate.

**Example** (v1.12 PR-A1 §2.1.4):

```
grep -rn 'workflow_dispatch\|createWorkflowDispatch\|release-gate\|auto-label' \
  .github/workflows/
```

Audit report format MUST be:
```
workflow_dispatch:        12 hits on HEAD, +2 post-PR
createWorkflowDispatch:    0 hits on HEAD, +3 post-PR
release-gate:              5 hits on HEAD, +2 post-PR
auto-label:                3 hits on HEAD, +2 post-PR
```

NOT:
```
sibling-arm grep: 23 hits total
```

**Why this rule exists**: v1.11 PR-D2 R2 audit surfaced a case
where the dev's aggregate sibling-arm count was inconsistent
with the auditor's; per-symbol decomposition would have caught
the discrepancy in one read. The aggregate format hides the
per-symbol delta that's load-bearing for the audit.

**Why this is standing**: future audits + PR reviews benefit
from the per-symbol granularity, and adopting the convention
universally is one-line cost per audit (the grep command's
output is naturally per-line; reporting needs to preserve, not
collapse).

## 2. Pillar A — trust-claim sweep checklist gate (1 PR: A1)

The cycle's mechanical-discipline closure. v1.6 → v1.10 each
surfaced a PR-F miscount at audit time. v1.10 PR-A2 closed the
prose-paragraph drift class via the grep gate v3 (the v3 scanner
finds drifting numbers in unstructured prose). The remaining
residual is dev-side: PR-F dev forgets to run the gate locally, or
runs it after pushing rather than as a pre-open gate. v1.11 PR-A1
ships the bash gate that BLOCKS PR-F open without proof of the
sweep.

### 2.1 PR-A1 — trust-claim sweep checklist (bash gate)

New `scripts/trust-claim-sweep.sh`. Acts as a pre-open gate for
PR-F: the script runs the full v2 + v3 CHANGELOG gate, the
README test-count refresh, the docs-site numeric extract, AND the
spec-text reconciliation in one invocation. Exits 0 only when ALL
sub-checks pass; exits non-zero with a checklist-style failure
report otherwise.

#### 2.1.1 Sub-checks bundled

The script runs (in order):

1. `scripts/changelog-grep.sh` — full v2 + v3 (no `--skip-live-
   extract`). Verifies CHANGELOG numeric claims against live
   extract.
2. `scripts/changelog-cite-check.sh` (paired with PR-A2; see §3.3)
   — verifies CHANGELOG cites resolve to spec text or live source.
3. README test-count grep — extracts every `N tests` / `N probes`
   / `N fixtures` claim in README.md and verifies against live
   extract.
4. Docs-site numeric extract — same scan applied to
   `docs-site/src/content/**/*.md`.
5. Spec-text reconciliation — every numeric claim in
   `docs/design/v1.11-spec.md` that's also surfaced in PR-F's
   CHANGELOG entry must agree with the spec. PR-F dev runs the
   script after writing the CHANGELOG; the script fails if the
   spec says "16 probes" and the CHANGELOG says "12".

Each sub-check that fails prints a one-line summary identifying
the failing surface + the drift. PR-F dev fixes the drift, re-runs
the script until it exits 0, THEN opens the PR.

#### 2.1.2 Why a bash gate and not a CI check

The release-gate workflow (v1.10 PR-A2) runs on PR open and on
push to `release/v*` branches. By the time the CI gate runs, the
PR is already open; if a sub-check fails, the dev has to push a
fix commit AND wait for the workflow to re-run AND re-request
review. The pre-open gate runs locally, BEFORE PR open — drift is
caught before the PR exists. Cycle-time saved is on the order of
10-30 minutes per failed sub-check (CI wait + re-request review).

Across 5 cycles (v1.6 → v1.10), the average miscount-fix cycle was
1-2 rounds of CI / re-review. v1.11 PR-A1 collapses this to zero
rounds (the gate catches the drift before the PR opens at all).

#### 2.1.3 Why a checklist and not a single regex

The drift class spans 5+ surfaces (CHANGELOG, README, docs-site,
spec, the CI workflow that triggers the live extract). A single
regex would either over-fire (matching legitimately-historical
numbers) or under-fire (missing surfaces it doesn't know about).
The checklist composition makes each sub-check independently
auditable; a sub-check that needs to evolve (e.g., a new docs-site
section to scan) is a one-line addition.

The v1.10 PR-A2 grep gate v3 escape hatch (single-backtick wrap)
applies to PR-A1's sub-checks unchanged: a number wrapped in
backticks is intentional-historical and passes the gate.

#### 2.1.4 Sibling-arm grep before declaring scope (v15-rule 4)

```
grep -rn 'changelog-grep\|release-gate\|trust-claim\|sweep-checklist' \
  scripts/ .github/
```

Implementer reports current hit count on HEAD and the post-PR
delta in the PR body. Verifies that the new gate sits alongside
the existing changelog-grep entry-points (not in conflict with
them).

#### 2.1.5 Negative-space tests MANDATORY per v14-rule 4

- All sub-checks pass on `main` at v1.10.0 head → exit 0.
- Inject a fixture-CHANGELOG with a v3-drifting prose number →
  sub-check 1 fails; the full sweep fails.
- Inject a fixture-README with a stale test count → sub-check 3
  fails.
- Inject a fixture-docs-site with a drifting probe count →
  sub-check 4 fails.
- Inject a fixture-CHANGELOG with a numeric claim that doesn't
  agree with the spec → sub-check 5 fails.
- A CHANGELOG number wrapped in single-backticks → all sub-checks
  ignore it (escape hatch honored).
- PR-A2's `release-ready` label is auto-applied on PR open (see
  §3.2) → the release-gate workflow runs the script in CI mode as
  a secondary verification.

#### 2.1.6 Severity check (v16-rule 13)

A1 is a CI / bash tooling addition. No D-code changes. No catalog-
pin refresh needed. PR-F dev workflow gets one new step (run the
gate before opening PR-F); rest of the cycle is unchanged.

**Closes the 5-cycle PR-F-miscount pattern (v1.6 / v1.7 / v1.8 /

### 3.2 Auto-apply `release-ready` label (closes v1.10 audit "release-gate trigger boundary")

New `.github/workflows/auto-release-ready-label.yml`. Triggered on
PR open + sync. The workflow inspects the PR's commit subjects for
`PR-F` (case-insensitive, as a discriminator) and auto-applies the
`release-ready` label. The release-gate workflow (v1.10 PR-A2)
then fires on the labeled PR as designed.

#### 3.2.1 Discriminator: PR-F subject prefix

The auto-label trigger looks for any commit on the PR whose subject
line starts with `chore(release):` AND contains `PR-F`. This is
the canonical PR-F subject shape used by v1.6 / v1.7 / v1.8 / v1.9
/ v1.10. If a PR's commits don't match (e.g., a non-PR-F PR that
incidentally bumps a number), the label is NOT auto-applied. The
dev can always apply the label manually as an override.

#### 3.2.2 Why auto-label rather than auto-trigger

The release-gate workflow expects the `release-ready` label as
its conditional. Auto-triggering the workflow without the label
would shortcut the workflow's existing conditional and require
workflow-trigger logic duplication. Auto-labeling stays inside
the existing trigger mechanic; the workflow doesn't need to
change.

```

  .github/workflows/
```

Implementer reports current hit count on HEAD in the PR body.

- A PR with a commit `chore(release): v1.11 PR-F — trust-claim
  migration…` → label auto-applied.
- A PR with a commit `feat(checker): v1.11 PR-D2 — walker polish`

- A PR with NO commit matching the discriminator → label NOT

## 4. Pillar D — pandas `unstack(level=)` arm (1 PR: D1, NEW INFERENCE ARM)

The cycle's pandas reshape continuation. User picked `unstack` at
committee r3 over `groupby.agg` + `pivot_table aggfunc=`. Mirrors
v1.10 PR-D2 (`stack`) shape directly — `unstack` is the inverse of
`stack` and the dispatch reuses the same receiver-gate mechanic.

### 4.1 PR-D1 — pandas `unstack` literal-form arm

**Receiver gate**: PandasFrame[X] only. Spark has no DataFrame-
method `unstack` (spark's reshape vocabulary is `pivot` + `stack`-
the-column-function), so receiver-dialect gate handles routing
unchanged from v1.10 PR-D2.

**Recognized kwarg**:
- `level` — `int | str | list-of-int | list-of-str | None`.
  Selects the row-index level to unstack into the columns. Default
  is `-1` (the last level) per pandas.
- `fill_value` — `scalar` (optional, default `None`). Doesn't
  affect schema; ignored for inference but recognized for parse-
  correctness.

**Inference logic**:
- When `level` is a literal (int / str / None) OR a literal list
  thereof → infer the result columns from the receiver's schema by
  EXPANDING each non-stacked column into per-stacked-value columns.
  Because pykrete's PandasFrame schema doesn't model index levels
  (v1.4 pandas-support.md §5 carve-out), `unstack` on a single-
  level frame produces a result schema with the SAME columns and
  the same dtypes (the stacked level became a new column-level the
  schema model doesn't track). Same logic as v1.10 PR-D2's `stack`:
  the schema-level result is "remaining columns" with index
  modeling stubbed out.
- When `level` is a dynamic expression → fall through to Unknown.
  Mirrors v1.10 PR-D2 `stack_arm` precedent.

**Literal column validation**: when `level` references column
names as a literal list of strings (`level=['a', 'b']`), validate
each against the receiver schema. Unknown name fires D0030 with
the v1.4 "did you mean" suggestion shape. Mirrors v1.6 / v1.7 /
v1.10 patterns.

**Result schema construction**:
- `level=int` / `level=str` / `level=None` → receiver columns,
  unchanged. The unstacked level becomes a column-level the schema
  doesn't track.
- `level=list-of-int` / `level=list-of-str` → receiver columns,
  unchanged. Same reasoning.
- `level=-1` (the default) → receiver columns, unchanged.
- Any dynamic shape → Unknown.

**Why this mirrors `stack` rather than computing a richer result**:
the v1.4 pandas-support.md §5 carve-out (index modeling out-of-
scope for the v1.x lifetime) constrains both `stack` and `unstack`
to schema-level "remaining columns" semantics. v1.x ships honest
silence for what the schema doesn't model.

**Negative path — Spark receiver**: a Spark receiver invoking
`.unstack(...)` MUST NOT trigger D0091 from the `unstack` arm
specifically (Spark has no DataFrame `unstack` method; the arm's
gate doesn't fire). If a Spark receiver invokes `.unstack`, the
arm's gate doesn't fire; dispatch falls through to the existing
attribute-arm path (which may itself fire D0091 from the v1.10
PR-D1 pandas-direction property arm, depending on the receiver
shape).

## 5. Pillar D — walker polish (1 PR: D2, alias_report.rs)

### 5.1 PR-D2 — alias_report.rs walker polish (3 closures + counter-semantics comment)

Three independent closures bundled into one PR. Each sub-item
names the v1.10 audit finding it closes.

#### 5.1.1 Mixed-indentation enclosing-def walk (closes v1.10 audit-D2-1)

`find_enclosing_def_line_start` (v1.10 PR-A1 R2) walks back from
the annotation byte offset to find the enclosing `def`/`async def`
by indentation comparison. If the def line uses 4-space indent and
a continuation line uses a leading tab character (or mixed tab+
space prefix), the walk's indent comparison treats them as
unrelated indents and walks past the actual enclosing def. The
marker-line check then reads a stale "line above" position.

**Fix**: normalize tab/space prefixes to a count-of-characters
before comparison. The comparison no longer cares whether the
prefix is `    ` or `\t` or `\t   `; the walker counts characters
and treats equal-character prefixes as same-indent. This isn't
PEP 8 compliant — PEP 8 says don't mix tabs and spaces — but real-
world code does, and the marker-walker should be robust to it.

**Why count-of-characters and not "normalize tabs to 4 spaces"**:
tab-width is editor-configured (2 / 4 / 8 are all common). Picking
4 is opinionated; counting characters is content-agnostic and
correct for the marker-walker's specific use case (we care about
"same nesting level," not visual width).

#### 5.1.2 Decorator-with-comment edge (closes v1.10 audit-D2-2)

`walk_past_decorators` recognizes a line starting with `@` as a
decorator. The recognition stops at the first non-`@` line. A
line like `@deco  # comment explaining why` is still a decorator
line, but if the comment runs past the decorator's expression
(e.g., the source-level whitespace + comment make the line look
syntactically unusual to a naive line-prefix check), the walker
may misclassify it.

**Fix**: the recognizer matches `^\s*@\w` (whitespace + `@` +
identifier-start), accepting any tail (the rest of the line can
be anything — a call, a comment, anything). The marker-line check

## 6. Pillar V — LSP test isolation (1 PR: V1, pykrete-lsp)

The cycle's LSP-side hardening. NOT a "LSP polish bundle" — v1.10

### 6.1 PR-V1 — tempdir-per-test for two project.rs tests

Two `pykrete-lsp::project::tests` tests share fixture state via
the test workspace directory:

- `malformed_pykrete_json_suppresses_repeat_warning_on_unchanged_mtime`
- `warm_sweep_refreshes_only_touched_files`

Both touch the same `pykrete.json` path inside the shared workspace.
If `cargo test` ever reorders (or a new test in the same module
touches the same path), an intermittent failure can surface as a
shared-state race. The v1.10 audit flagged this as a latent risk;
v1.11 closes it.

#### 6.1.1 Fix shape — tempdir-per-test

Each test creates its own `tempfile::TempDir`, writes its fixture
files there, and runs against that isolated workspace. No more
shared workspace paths between tests.

The `tempfile` crate is already a workspace dev-dependency (used
elsewhere); no new dependencies introduced.

#### 6.1.2 Why NOT `--test-threads=1`

`--test-threads=1` would mask the underlying isolation defect AND
slow the whole crate's test run. v1.6 retro rule 12 carries
forward: address the root cause (shared state), not the symptom
(parallel races). `--test-threads=1` is also CI-config drift —
each crate's `Cargo.toml` would need to opt in, and contributors
wouldn't reliably run it locally.

Tempdir-per-test is the structural fix; parallel test runs stay
unchanged, and the regression-guard test verifies the isolation
holds.

#### 6.1.3 Sibling-arm grep before declaring scope (v15-rule 4)

```
grep -rn 'pykrete\.json\|TempDir\|test_workspace' \

```

Implementer reports current hit count on HEAD in the PR body.

## 12. Marker file mechanism (§9.2 cross-reference)

**This PR (PR-S1) commits `.github/centralized-bump-cycle.marker`
with the content `v1.11`.** The marker's presence on the branch
is the version-guard suspension mechanism: the
`extension-version-guard.yml` workflow honors the marker, allowing
Wave 1 PRs (A1, A2, D1, D2, V1) to skip the extension-version
check. PR-F then bumps the version in one place at cycle close.

**Why commit the marker in PR-S1, not PR-F**: v1.10 retro rule 5
identified the gap. v1.10 PR-F (the preceding cycle's close) had
to DELETE the v1.10 marker as part of cycle cleanup, leaving
`main` without it. v1.10 PR-S1 didn't re-add the marker; Wave 1
devs branched off S1's HEAD and inherited "no marker" — 4 of 6
forgot to add the marker themselves, hitting CI guard failures
that required emergency commits. v1.11 PR-S1 (this PR) re-adds
the marker AT THE TOP of the cycle, so every Wave 1 branch
inherits the marker by default.

**Lifecycle**:

1. Cycle N PR-S1 commits the marker with content `vN`.
2. Wave 1 PRs branch off S1, inherit the marker.
3. extension-version-guard CI honors the marker, skips the
   per-PR version-bump check.
4. PR-F bumps the version centrally.
5. PR-F (or the cycle's final cleanup PR) DELETES the marker
   in preparation for the next cycle's PR-S1 to re-add it.

The marker's content (`v1.11`) is a per-cycle stamp; the
workflow reads it for the cycle name. The presence of the file
is the gate; the content is informational.

**Why retain the marker mechanism for future cycles**: a future
cycle may need per-PR bumps (external publication coordination,
multi-package synchronized release, etc.). The marker is a safety
valve; deleting it re-enables per-PR bumps. v1.10 §11.10 → v1.11
inherits the mechanic unchanged.

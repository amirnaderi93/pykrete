## 2. Pillar A — audit-debt closure (2 PRs: A1, A2)

### 2.1 PR-A1 — shared-list extract: `PANDAS_ONLY_SIGNALS` + `PANDAS_INHERITED_ARMS`

The v1.6 architecture audit Important #3 finding. Two
semantically-distinct lists today live in two places without a
shared module — they have different concerns and a unified file
would conflate them (committee r2 caught this; the original TM
preliminary was a single `dialect_signals.rs` module).

**The two lists**:

1. **`PANDAS_ONLY_SIGNALS`** — binding-classification signals.
   Methods that, when called on a binding, tag the binding as
   Pandas. Today at `crates/pykrete/src/alias_adjudicate.rs:64-89`
   (named `PANDAS_DISCRIMINATORS`). Consumed by the call-graph
   adjudicator at `alias_adjudicate.rs:286,295` to settle a
   `DataFrame[X]` alias as Pandas. **These names must be
   pandas-only**: `head`/`tail`/`first`/`take`/`drop`/etc. exist on
   BOTH dialects and are deliberately excluded — they can't
   classify a binding.

2. **`PANDAS_INHERITED_ARMS`** — shared-with-Spark methods routed
   by `receiver_is_pandas_inherited` in `operations/expr.rs`. Today
   open-coded inline at `expr.rs:873,1078,1130` (`head | tail | first
   | take`, `assign`, `pivot_table`). These are the method names
   that have a pandas-specific dispatch arm in `analyze_method_call_inner`,
   guarded by the inherited-dialect tag from `inherited_dialect`
   at `operations/driver.rs:121`. **These names CAN overlap with
   Spark**: `head`/`tail`/`first`/`take` appear here because pandas
   semantics differ (row-sliced DataFrame, not terminal `list[Row]`).

**Design**: extract a new module
`crates/pykrete/src/dialect_signals.rs` (or similarly named) that
exports BOTH lists as `pub const`. `SPARK_DISCRIMINATORS` at
`alias_adjudicate.rs:28-55` moves too, for symmetry. The
`alias_adjudicate.rs` consumers import from the shared module; the
`operations/expr.rs` arms switch from inline `matches!(method, "head"
| "tail" | "first" | "take")` to a `PANDAS_INHERITED_ARMS.contains(method)`
membership check (or equivalent — the implementer picks the shape
that compiles cleanly with the existing match-arm cascade).

**Semantic split is load-bearing**: the two lists MUST stay separate.
If `head`/`tail`/`first`/`take`/`drop` leak into
`PANDAS_ONLY_SIGNALS`, every Spark codebase that calls `df.head()`
suddenly classifies the binding as Pandas — false positive on D0090
adjudication. Conversely, if `assign` / `pivot_table` / pandas-only
shape methods drop OUT of `PANDAS_INHERITED_ARMS`, pandas chains
silently lose their dispatch arm.

**CI-guard cross-consistency test (atomic with the extract)**:
new test in `alias_adjudicate.rs` tests module (or a new test file)
that asserts:

- Every method `M` appearing in an `if receiver_is_pandas_inherited
  && matches!(method, ...)` (or its post-A1 equivalent) arm in
  `operations/expr.rs` is either in `PANDAS_INHERITED_ARMS` OR
  explicitly excluded via an inline allow-list in the test (for the
  rare arm that's intentionally not in the named list).
- Every method `M` in `PANDAS_ONLY_SIGNALS` is NOT in
  `PANDAS_INHERITED_ARMS`. Disjointness — a method either tags the
  binding or shares the dispatch surface; it can't do both. (This
  is the false-positive guard surfaced by Strategist at committee
  r2.)

The guard mechanism: the test parses the source of `expr.rs` and
greps for arm patterns. Alternative shape (committee did not
mandate): require every new `receiver_is_pandas_inherited` arm to
call a helper `pandas_arm_dispatched(method)` that membership-checks
the shared list; the test then asserts every arm goes through the
helper.

**Sibling-arm grep before declaring scope** (v15-rule 4 / v16-rule
8 sibling-arm-grep mandate):

```
grep -rn 'SPARK_DISCRIMINATORS\|PANDAS_DISCRIMINATORS\|receiver_is_pandas_inherited\|receiver_is_spark_inherited' \
  crates/pykrete/src/
```

**Surface for PR-A1 author** — the `receiver_is_spark_inherited`

**Negative-space tests MANDATORY per v14-rule 4 / v16-rule 8**:
- `df.head()` where `df: DataFrame[X]` (pre-adjudication) →

- `pdf.head()` where `pdf: PandasFrame[X]` → expr-side dispatch
  arm fires (row-sliced DataFrame preserved). Positive regression
  guard: `head` must remain in `PANDAS_INHERITED_ARMS`.
- `sdf.head()` where `sdf: SparkFrame[X]` → Spark terminal
  semantics apply (existing `inherited_dialect` arm short-circuits
  before the pandas-arm matches). Sibling-arm fall-through.
- CI-guard test passes on the v1.6.0 HEAD if hypothetically
  retroactively applied (i.e. the extract preserves current
  behavior exactly).

## 3. Pillar M — migrator UX overhaul (1 PR: M1, atomic)

The cycle's user-facing change. THREE coupled pieces shipped
together because they all hit the same surface (the migrator CLI
+ rewriter) and the release-note callout reads more cleanly as a
single behavior shift.

### 3.1 Part 1 — `--check` becomes default

**User explicitly approved on 2026-06-15.** TS-style `--noEmit`-by-default
posture: `pykrete migrate <path>` no longer rewrites files on
disk. Instead, it runs check-mode (exit 1 if any file would
change, 0 if none). To rewrite, the user now passes `--apply`
explicitly.

Current CLI shape at `crates/pykrete/src/main.rs:67-94`:

```
Modes (mutually exclusive):
        --check    Exit 1 if any file would change, 0 if none. No writes.
        --diff     Print a unified diff of the proposed changes to stdout.
                   No writes.
    (default)      Rewrite each matching file in place. ...
```

Post-M1:

```
Modes (mutually exclusive):
        --apply    Rewrite each matching file in place. One line per
                   modified file is printed to stdout ('rewrote: <path>').
                   Files with no aliases are left untouched. Exits 0 on success.
        --diff     Print a unified diff of the proposed changes to stdout.
                   No writes.
    (default)      Check mode. Exit 1 if any file would change, 0 if none.
                   No writes. (Use --apply to rewrite.)
```

The behavior previously surfaced by `--check` becomes the default;
`--check` itself may stay as an alias for clarity (implementer's
call — TS keeps `--noEmit` as a recognized flag even when it's the
implicit default).

**Release-note callout REQUIRED** at PR-F time. First-time users
on v1.6's docs (which say `pykrete migrate src/` rewrites) will
hit the new exit-1 behavior. The PR-F README + CHANGELOG entry
flags this as a breaking CLI change with the one-line remediation
("pass `--apply` to restore v1.6's rewrite-on-default behavior").

### 3.2 Part 2 — Parse-error surface

Currently the migrate walker silently skips files that fail to
parse. Reviewer-surfaced at v1.6 PR-M3 architecture-audit
Important #7 (the deferred-to-v1.7 finding). The fix:

```
eprintln!("skipped (parse error): {path}", path = path_str);
```

Emitted once per skipped file in the walker, on stderr (so it
doesn't pollute the `--diff` stdout stream). The walker continues
processing remaining files — no early exit.

The release notes for v1.7 don't need to call this out separately
(it's a transparency improvement, not a behavior change for
parse-clean trees).

**Closes v1.6 architecture audit Important #7.**

### 3.3 Part 3 — CRLF marker normalization

Currently the migrator injects `# pykrete: ambiguous` markers
using `\n` line terminators regardless of the source file's EOL.
On a CRLF-line-ended source file, this creates a mixed-EOL file —
git surfaces it as a whole-file change on the next commit even
though only one line was added.

Fix: detect the source file's predominant EOL once (sniff the
first `\n` — if preceded by `\r`, source is CRLF; else LF). Use
the matching EOL for the injected marker line. Round-3 deferral
from v1.6 PR-M3 closed.

The detection is per-file — mixed-EOL source files (rare) inherit
whichever EOL the sniff lands on. Don't over-engineer.

**Closes v1.6 PR-M3 round-3 deferral.**

- `pykrete migrate src/` clean tree → exit 0, no output, no

- `pykrete migrate src/` tree with aliases → exit 1, lists files

## 4. Pillar D — pandas `melt` (1 PR: D1)

Pandas reshape downpayment, second arm after v1.6's `pivot_table`.
**User picked melt over stack on 2026-06-15** from the committee
shortlist (melt, stack/unstack, groupby.agg). Single arm; stack /
unstack / groupby.agg deferred to v1.8 per §9.

**Existing Spark `melt` arm** at `crates/pykrete/src/operations/expr.rs:1145`:

```
if matches!(method, "melt" | "unpivot") {
    return Some(apply_melt(call, &receiver, ctx, source, line_index, diagnostics));
}
```

The Spark arm fires UNGATED on dialect — it predates the dialect
split. Spec author for D1 verifies: pandas `melt` has a different
argument shape from Spark's (Spark uses positional column lists +
`variableColumnName=` / `valueColumnName=` kwargs; pandas uses
`id_vars=` / `value_vars=` / `var_name=` / `value_name=` kwargs).
**Sibling-arm decision**: extend the existing arm to dispatch by
dialect (Spark vs Pandas) OR add a sibling pandas arm that fires
on `receiver_is_pandas_inherited && method == "melt"`. The
implementer picks the shape that minimizes diff — committee did
NOT pre-commit. Whatever the shape, the Spark behavior MUST stay
unchanged (regression guard).

### 4.1 Design

**Scope** — `pdf.melt(id_vars=, value_vars=, var_name=, value_name=)`
literal form only:

- IN: `id_vars=` and `value_vars=` resolve via string literal or
  list-of-string-literals. Both required keyword forms for the
  literal arm to fire; missing either → fall through.
- IN: column-ref validation — every name in `id_vars` and
  `value_vars` must exist on the receiver schema. Typo → D0030
  with "did you mean" suggestion per v1.4 D0030 patterns.
- IN: `var_name=` / `value_name=` accepted as string-literal
  kwargs (default `"variable"` / `"value"` if absent). Opaque
  values (non-literal) → fall through to default names.
- IN: receiver dialect must be Pandas (gate); Spark receivers
  route to the existing arm unchanged.
- IN: output schema = `id_vars + [var_name, value_name]` columns.
  Tracked schema, not Unknown — distinguishes D1 from v1.6
  `pivot_table` (which output Unknown because the column count
  depends on data).
- OUT: non-literal arg shapes (variable, computed `id_vars` /
  `value_vars`) → fall through, no diagnostic.
- OUT: `col_level=` / `ignore_index=` / DataFrame.melt class
  method form → defer to v1.8.

**Inference site**: NEW arm in `analyze_method_call_inner` at
`crates/pykrete/src/operations/expr.rs:1145`-ish, either as an
extension of the existing `melt | unpivot` match or as a new
gated arm above it. The pandas dispatch must precede or be inside
the existing arm so it doesn't fall through to Spark semantics.

**Dual-arm requirement per v1.5 retro rule 2 / v16-rule 1**: every
new pandas-dispatched inference arm fires both at
`analyze_method_call_inner` (for the chained-call surface) AND at
`inherited_dialect` at `operations/driver.rs:121` (for the
result-of-call dialect tagging). For D1, the
`receiver_is_pandas_inherited` chain receiver tag flows through
`inherited_dialect` already — verified at `driver.rs:121-160`,
which recurses via `cursor = &attr.value` at `:154`. Spec author
for D1 verifies BOTH arms with paste-from-source fragments in the
PR body.

**Output schema construction**:

```
id_vars = ["cat", "subcat"]  →  id_vars columns preserved
value_vars = ["sales", "qty"] →  validated against receiver schema
var_name = "metric" (default "variable")
value_name = "amount" (default "value")
→ result columns: ["cat", "subcat", "metric", "amount"]
→ result type = PandasFrame[<synthesized schema>]
```

The synthesized output schema's column TYPES: `id_vars` retain
their original types from the receiver schema; `var_name` is
string; `value_name` is the common type of the `value_vars`
columns if they agree, else `Unknown`. v1.7 D1 author may
simplify: if `value_vars` columns don't all share a type, fall
back to `Unknown` for `value_name`'s type — defer the cross-type
unification logic to v1.8.

## 12. v2.0 throughline

v1.7 advances the v2.0 narrative by making the migrator
production-grade as a remediation tool, not just a one-shot fix:

- **`--check`-default makes the migrator safe to drop into CI**.
  Today's default-rewrite shape is a footgun for first-time users
  who run `pykrete migrate src/` on dirty trees expecting a
  preview. Post-v1.7, `pykrete migrate src/` reports what would
  change without writing — TS-style. CI integrations adopt
  this naturally.
- **Parse-error surface makes large-codebase runs auditable**.
  Real-world codebases have stale fixtures, generated files, and
  vendored sources that don't parse. Silent skip is a trust
  hazard. Post-v1.7, the user sees exactly what was skipped.
- **CRLF normalization makes the migrator git-clean on Windows
  + mixed-EOL codebases**. Today's mixed-EOL output muddies the
  v2.0 transition's diff signal. Post-v1.7, the migration is
  reviewable.

The release-notes trust-claim sentence — **"v2.0 is one command
away"** — surfaces on splash + roadmap. The intent: v2.0's
alias removal is no longer scary because v1.7's migrator is
production-grade. PR-F copy lands this framing in README +
CHANGELOG + roadmap.

## 2. Pillar A — trust-claim-sweep backtick-preservation tripwire (1 PR: A1)

The cycle's automation closure on the 2-cycle backtick-strip
regression class. PR-G v1.11 and PR-G v1.12 both surfaced the
same pattern: a docs edit (commonly a docs-sync-auditor closure
PR) unwraps a `` `1.x.y` `` historical pin in the pykrete-tests
`README.md` migration-status table, the sweep gate then sees the
numeric as a live claim, fails the gate, and the cycle pays a
catalog-pin or re-write round to restore the backticks. v1.13
PR-A1 closes the class mechanically.

### 2.1 PR-A1 — backtick-preservation tripwire

Extend `scripts/trust-claim-sweep-checklist.sh` with a SNAPSHOT
mode + a TRIPWIRE mode. The snapshot enumerates the set of
single-backticked historical version pins currently present in
`pykrete-tests/README.md` (and any other surfaces in the sweep's
surface list that hold historical pins). The tripwire runs on
every sweep invocation and fails the sweep if any snapshotted
pin has been unwrapped on the current revision.

#### 2.1.1 Snapshot format

A plain-text fixture committed alongside the sweep script (e.g.,
`scripts/trust-claim-sweep-checklist.snapshot.txt`) with one
line per snapshotted pin:

```
pykrete-tests/README.md:`1.7.0`
pykrete-tests/README.md:`1.8.0`
pykrete-tests/README.md:`1.9.0`
…
```

The snapshot is refreshed by running the sweep with a `--snapshot`
flag (analogous to the existing `--ack` / `--snapshot` flags
elsewhere) which writes the current state and exits. Cycle-close
PR-F refreshes the snapshot when the new cycle's historical pins
land.

#### 2.1.2 Tripwire semantics

On every non-`--snapshot` invocation, the sweep:
1. Reads the snapshot file.
2. For each `surface:pin` entry, greps the surface on the working
   tree for the EXACT `` `pin` `` byte sequence.
3. If the byte sequence is absent → fail with a structured
   message: `tripwire: pin '1.7.0' on pykrete-tests/README.md was
   single-backticked at snapshot time but is not present on the
   current revision. Restore the backticks or refresh the
   snapshot with --snapshot.`

#### 2.1.3 Why a snapshot file, not auto-derive from git log

Auto-deriving the "historical" set requires the sweep to know
the current cycle's version, which moves the gate's correctness
into the workflow's env (CYCLE_VERSION). A snapshot file is
explicit, reviewable in PR diffs, and survives across cycles
without env-coupling. Cost: one extra commit per cycle in PR-F
to refresh. Benefit: the gate's correctness is self-contained.

#### 2.1.4 Why not extend the existing `text-numeric-historical`
fenced-block convention to the README migration table

The migration-status table is a USER-FACING table in the
pykrete-tests README; wrapping its rows in
`text-numeric-historical` fences would clutter the rendered
README. Single-backticking the pin keeps the rendered output
clean AND is the existing convention (already used across docs).
The tripwire enforces what's already convention; it doesn't
introduce a new convention.

#### 2.1.5 Sibling-arm grep before declaring scope (v15-rule 4 / §13.1)

```
grep -rn 'snapshot\|tripwire\|--snapshot\|historical' \
  scripts/trust-claim-sweep-checklist.sh \
  scripts/changelog-grep.sh \
  scripts/changelog-cite-check.sh
```

Implementer enumerates per-symbol counts (not aggregate across
siblings) on HEAD and reports post-PR delta in the PR body.
Per-symbol convention codified in §13.1.

#### 2.1.6 Negative-space tests MANDATORY per v14-rule 4

- Pin present on working tree + present in snapshot → sweep
  passes.
- Pin absent on working tree + present in snapshot → sweep fails
  with the structured message.
- Pin present on working tree + absent from snapshot (new pin
  not yet snapshotted) → sweep passes (snapshot is additive; new
  pins don't trip the tripwire until they're snapshotted).
- `--snapshot` invocation rewrites the snapshot to match current
  reality and exits 0; does NOT run the tripwire.
- Pin wrapped in DOUBLE backticks (`` ``1.7.0`` ``) — recognized
  as wrapped (the tripwire matches the wrapped pin; the surface
  retains its historical mask). Edge documented in the script's
  comment block.

#### 2.1.7 Severity check (v16-rule 13)

A1 is a sweep-script polish + new test fixture. No D-code
changes. No catalog-pin refresh. PR-F dev workflow gets one
fewer mechanical-restore round per cycle.

**Closes the 2-cycle backtick-strip regression class at PR-G
v1.11 + v1.12.**

## 3. Pillar A — dispatched-run required status check (1 PR: A2)

Per v1.5 retro architectural-heterogeneity rule (Rust + Bash/CI
land in separate PRs). A2 is workflow-trigger + branch-protection;
A1 is sweep-script polish — same surface family (CI), but
separable concerns and separable verifications.

### 3.1 PR-A2 — dispatched-run as required status check

v1.12 PR-A1 shipped the `workflow_dispatch` API call from
auto-label-release-pr, which fires `release-gate.yml` on the
PR's labeled event via dispatch. v1.12 PR-F observed the
dispatched run firing live (the v1.12 retro §12 closure
CONFIRMED). v1.13 PR-A2 converts the dispatched run into a
REQUIRED status check on `main` so a PR can no longer merge if
its release-gate is failing OR pending.

#### 3.1.1 The check-name collision

Branch-protection matches checks BY NAME. The current
`.github/workflows/release-gate.yml` has a single job
(`release-gate-check`) that fires on both `pull_request` and
`workflow_dispatch`. The `pull_request` arm is gated by
`if: github.event_name == 'push' || …` and SKIPS for ordinary
PRs (only fires when the PR carries `release-ready`).

If branch-protection requires `release-gate-check`, the
`pull_request`-arm SKIPPED check ALSO matches the name → the
required check appears as "skipped/pending" on every ordinary
PR → merge is blocked by the skip. We need the dispatched-job's
check-name to be unique to the dispatched arm.

#### 3.1.2 Workflow rewrite (the fix)

Split `release-gate.yml` so:
- The `pull_request`-triggered job has check-name
  `release-gate-check-pr-noop` (or similar). Its only role is to
  exist for the PR event WITHOUT blocking merge. If a PR carries
  `release-ready`, this job fans out to the same full gate; if
  not, it emits a `pass` immediately. Branch-protection IGNORES
  this job (not in the required list).
- The `workflow_dispatch`-triggered job keeps check-name
  `release-gate-check` and runs the full live-extract sweep.
  Branch-protection REQUIRES `release-gate-check`.

#### 3.1.3 Branch-protection JSON

The pykrete repo's branch-protection on `main` is managed via
`.github/settings.yml` (or the GitHub UI; v1.13 PR-A2 chooses
the JSON-in-repo path for reviewability). PR-A2 commits the
required-check entry alongside the workflow rewrite. The PR
body documents the JSON change AND verifies the dispatched
run fires green on PR-A2 itself (per v1.12 §12 standing rule).

#### 3.1.4 Why not delete the `pull_request` arm entirely

The `release-ready`-label path STILL needs to fire on PR events
(per v1.10 PR-A2 design + v1.12 PR-A1 dispatch); deleting the
arm loses the labeled-PR functionality. The fix is to split the
check-name, not to delete the arm.

#### 3.1.5 Spec language prevents R2/R3 reviewer-loop

A rewrite that touches workflow YAML AND branch-protection JSON
risks a partial fix: dev rewrites the workflow but misses the
JSON, or rewrites the JSON but misses the workflow. PR-A2 MUST
ship BOTH halves AND verify the dispatched-event observation
end-to-end (the dispatched run fires green on PR-A2 AND the
required-check appears in the merge-button's checks list AND
the `pr-noop` check is NOT required). Spec mandates the
end-to-end observation as a pre-merge gate.

#### 3.1.6 Sibling-arm grep before declaring scope (v15-rule 4 / §13.1)

```
grep -rn 'release-gate-check\|release-gate\|required\|workflow_dispatch\|pull_request' \
  .github/workflows/ .github/
```

Implementer reports per-symbol counts on HEAD.

#### 3.1.7 Negative-space tests MANDATORY per v14-rule 4

- An ordinary PR (no `release-ready` label) → `pr-noop` job
  passes immediately; `release-gate-check` is NOT triggered by
  the PR event but IS triggered by the dispatched workflow when
  the PR is eventually labeled.
- A `release-ready`-labeled PR → auto-label dispatch fires →
  dispatched `release-gate-check` runs the full sweep → required
  check passes → merge unblocks.
- A `release-ready`-labeled PR with a failing live-extract →
  dispatched `release-gate-check` fails → required check fails →
  merge BLOCKED.
- The `pr-noop` job's existence does NOT count toward the
  required-check list (verified by branch-protection JSON +
  GitHub API readback).
- A direct push to `main` without a PR → branch-protection
  status-check requirements do NOT apply (push protection is
  separate); the release-gate fires on `push: branches:
  release/v*` per the existing v1.10 PR-A2 trigger.

#### 3.1.8 Severity check (v16-rule 13)

A2 is a CI / branch-protection change. No D-code changes. No
catalog-pin refresh. Closes the v1.11 → v1.12 trigger-boundary
chain STRUCTURALLY (the gate is now required by `main`'s
protection, not just dispatched-and-observed).

**Closes the v1.11 → v1.12 trigger-boundary deferral chain
structurally.**

## 4. Pillar D — D0080 dialect-on-return checker arm (1 PR: D1)

The cycle's D-pillar headline. Closes the longest-standing
D0080 correctness gap (the existing arm compares column SETS
and TYPES but NOT DIALECT).

### 4.1 PR-D1 — D0080 dialect-on-return

`crates/pykrete/src/operations/driver.rs:866-936`
`check_return_type` currently compares declared vs actual
column NAMES + TYPES. If a function is annotated
`def f() -> SparkFrame[X]` and the body returns a value with
inherited dialect Pandas (e.g., the body ends with a
`.toPandas()` call), the SET + TYPE comparisons pass (the
columns and dtypes match), and D0080 stays silent. This is
the gap.

`inherited_dialect` is already a callable accessible from
`crates/pykrete/src/operations/driver.rs:126` (the
`inherited_dialect` definition) and called from the unified
`inherited_chain_state` walker at lines 169 / 258. PR-D1
plumbs the dialect of the declared return type AND the
inherited dialect of the actual return expression into
`check_return_type` and compares them.

#### 4.1.1 Declared-side dialect

`SchemaView::Declared(s)` for a return annotation carries its
dialect tag (SparkFrame vs PandasFrame) in the binding. For
`Pick` / `Omit`-derived `SchemaView`s, the dialect is inherited
from the source schema. PR-D1 extracts the declared dialect
from the `SchemaView` at the same site that builds
`declared_label`.

#### 4.1.2 Actual-side dialect

The body's return expression already participates in the
unified `inherited_chain_state` walker. PR-D1 captures the
actual dialect at the call site that produces `actual`
(`SchemaView`) for the return expression and threads it into
`check_return_type` as a new parameter.

#### 4.1.3 Diagnostic message

When the dialects differ AND both dialects are known
(Some(Spark) vs Some(Pandas)), append to the existing D0080
message:
`; declared {SparkFrame|PandasFrame} but body produces
{SparkFrame|PandasFrame}`. The base message structure is
preserved; the dialect mismatch is an additional clause.

If EITHER dialect is None (the inferred expression can't be
resolved to a concrete dialect), the dialect-comparison clause
does NOT fire — honest silence per TypeScript-style "narrow
when you can, widen when you can't."

#### 4.1.4 Why not a new D-code (D0081 / etc.)

The mismatch is the SAME class as the existing D0080
(returnTypeMismatch): the body produces a value that doesn't
match the declared return. The dialect is part of the declared
return type (`SparkFrame[X]` ≠ `PandasFrame[X]`). Splitting
into a new D-code would fragment the user's mental model
("which return-mismatch code do I look for?"). Extending the
existing message keeps the diagnostic taxonomy clean.

#### 4.1.5 Sibling-arm grep before declaring scope (v15-rule 4 / §13.1)

```
grep -rn 'check_return_type\|inherited_dialect\|D0080\|SchemaView\|declared_label' \
  crates/pykrete/src/operations/ crates/pykrete/tests/
```

Implementer reports per-symbol counts on HEAD.

#### 4.1.6 Paired positive + negative tests MANDATORY per v14-rule 4 + v16-rule 8

- **Spark-decl / pandas-body × 4 simple chains** (positive):
  - body returns `pdf` directly (where `pdf: PandasFrame[X]`)
  - body returns `sdf.toPandas()` (Spark → pandas handoff)
  - body returns `df.toPandas().head()` (chained)
  - body returns `pd.DataFrame(...)` (constructor)
- **Pandas-decl / Spark-body × 4 simple chains** (positive):
  - body returns `sdf` directly (where `sdf: SparkFrame[X]`)
  - body returns `spark.createDataFrame(pdf, schema=X)` (handoff)
  - body returns `sdf.select(...)` (chained)
  - body returns `spark.read.parquet(...)` (constructor)
- **Negative-space** (no dialect-mismatch clause fires):
  - Both declared + body are SparkFrame[X] (matches) →
    pre-existing D0080 behavior unchanged.
  - Both are PandasFrame[X] (matches) → pre-existing behavior.
  - Body's inherited dialect is None (opaque receiver) →
    dialect-clause omitted, set/type clauses still fire.
  - Existing schema-only D0080 tests pass unchanged (regression
    guard for the v1.6 → v1.12 D0080 arm).

#### 4.1.7 Severity check (v16-rule 13)

D1 is a Rust checker-arm extension. Behavior delta: previously
silent on dialect-on-return; post-PR, fires D0080 with the
appended clause. This IS a cascade trigger for cross-codebase
fixtures whose return-annotations had silent dialect drift
and post-PR will fire D0080. PR-P1 (parallel pykrete-tests
work) extends donor coverage; the v1.13.0 catalog-pin bump
PR captures the new fires; PR-F catalog-pin auditor verifies.

**Closes D0080's longest-standing correctness gap (since v1.6).**

## 5. Pillar D — `classify_pivot_table_aggfunc` consumer (1 PR: D2)

The cycle's pandas inference-depth work. Consumes the v1.12
PR-D1 primer at `crates/pykrete/src/operations/expr.rs:1345`
(currently `let _ = classify_pivot_table_aggfunc(call);` — the
classifier is wired but its result is discarded).

### 5.1 PR-D2 — aggfunc-driven schema inference

The v1.12 PR-D1 arm extension shipped a `classify_pivot_table_aggfunc`
recognizer that returns the matched allowlist string (or None
on fall-through). v1.13 PR-D2 consumes the classifier's output
to synthesize a result schema with aggregate-driven column
types.

#### 5.1.1 Aggregate-to-dtype mapping

| Aggregate | Result dtype |
|---|---|
| `"count"` | int64 |
| `"mean"` | float64 |
| `"std"` | float64 |
| `"var"` | float64 |
| `"median"` | float64 |
| `"sum"` | preserve receiver column type |
| `"min"` | preserve receiver column type |
| `"max"` | preserve receiver column type |
| `"first"` | preserve receiver column type |
| `"last"` | preserve receiver column type |
| `"nunique"` | int64 |

#### 5.1.2 Synthesized result schema

When the classifier returns a recognized aggregate (Some(_)),
the arm now synthesizes a `PandasFrame[X']` where X' has:
- The pivoted `values` column(s) with types derived per §5.1.1.
- Synthesized schema covers the `values=` columns only.
  `index=` and `columns=` arguments are NOT modeled per the
  v1.4 pandas index-modeling carve-out — adopters who need to
  access the result's index must `.reset_index()` first. The
  pandas runtime places `index=` argument values in the result
  DataFrame's INDEX (not as columns), so synthesizing them
  would be technically wrong and silence legitimate D0030 fires
  on `result.<index_col>` access.

When the classifier returns None (fall-through case from v1.12
PR-D1 — non-literal, callable, dict, mixed list), the arm
preserves the v1.12 behavior: result schema is Unknown.

#### 5.1.3 Why this is the FIRST aggregate-semantics-informed inference

Prior pandas arms (`pivot_table` v1.6, `melt` v1.7, `stack`
v1.10, `unstack` v1.11) all synthesize result schemas based on
COLUMN-IDENTITY transformations (which columns survive, which
get renamed). v1.13 PR-D2 is the first arm where the AGGREGATE
FUNCTION's semantics (`count` → int64, `mean` → float64)
inform the result column TYPES. This is the canonical
convention for v1.14+ aggregate arms (`groupby.agg`,
`resample.aggfunc`, `rolling.aggfunc`, etc.) per §13.

#### 5.1.4 Why list of aggregates is deferred to v1.14+

The v1.12 PR-D1 allowlist permits `aggfunc=["sum", "mean"]`
(a literal list of allowlist strings). The result-schema shape
for a list-of-aggregates is `MultiIndex`-on-columns (pandas
emits `("a", "sum")` and `("a", "mean")` column tuples), which
the pykrete schema lattice doesn't model. v1.13 PR-D2 ships
the SINGLE-aggregate path; list-of-aggregates falls through to
Unknown (negative-space test §5.1.6).

The same MultiIndex-on-columns shape arises for
`values=['x','y']` AND `columns=` non-empty (pandas emits
`(value_col, column_value)` tuples). v1.13 PR-D2 falls through
to Unknown for this sub-case too; same v1.14+ cohort.

## 13. Forward-binding PR-D2 classifier-consumer convention for v1.14+

PR-D2 establishes the pattern: AGGREGATE FUNCTION LITERAL →
OUTPUT COLUMN-TYPE INFERENCE. v1.14+ `groupby.agg` arm consumes
the same pattern when the `Grouped<pandas>` receiver type lands.

**Spec language** (binding for v1.14+ aggregate arms):

> All aggregate-semantics-informed schema inference
> (`pivot_table.aggfunc`, `groupby.agg`, `resample.aggfunc`,
> `rolling.aggfunc`, `expanding.aggfunc`, etc.) follows the
> v1.13 PR-D2 convention: aggregate function literal → result-
> column-type table → synthesized result schema. The aggregate-
> to-dtype mapping in §5.1.1 is the canonical reference for all
> arms; new arms that introduce additional aggregates extend the
> table in a forward-compatible way (additive only — existing
> mappings do not change without a major-version bump).

**Why this binding matters**: the v1.4 / v1.7 / v1.10 / v1.11
reshape arms all synthesize schemas via column-identity
transformations. PR-D2 is the first arm where aggregate
semantics drive column types; the spec binds future arms to the
same convention so we don't accumulate a per-arm dtype-mapping
sprawl. TypeScript's `ReturnType<>` for `Math.sum` vs
`Math.count` is the invoked precedent: the type of the result
follows the function's documented return type, not the input
type.

**v1.14+ impact**: `groupby.agg` (when the `Grouped<pandas>`
type lands) MUST use the §5.1.1 table. `resample.aggfunc`
(when shipped) MUST use the table. A new aggregate (e.g.,
`"sem"` for standard error of the mean) extends the table by
adding a row; the row's dtype follows pandas docs (here:
float64). Reviewer audits future aggregate arms against the
§5.1.1 table.

## 3. Pillar A — audit-debt closure (2 PRs: A1, A2)

### 3.1 PR-A1 — dual-arm helper extract: `cross_dialect_handoff_gate`

The v1.5 architecture audit Important #2 finding. Two helpers
today, both with "Keep in sync" comments — dialect-side at
`driver.rs:174-192` (signature `fn
createdataframe_handoff_dialect(call: &ExprCall, ctx:
&BodyContext) -> Option<Dialect>`) and view-side at
`expr.rs:546-567` (signature `fn createdataframe_handoff_view(call:
&ExprCall, ctx: &BodyContext, source, line_index, diagnostics) ->
Option<SchemaView>`). Both implement identical gate logic — (a)
`schema=` kwarg with a Spark-tagged value, (b) first positional
arg with a Pandas tag — but with different post-gate behavior
(dialect-side returns `Dialect::Spark`, view-side calls
`analyze_expr` on the matched arg). The "Keep in sync" comments at
`driver.rs:170-173` and `expr.rs:543-545` warn that the gate-set
must agree exactly.

**Design**: extract a `cross_dialect_handoff_gate(call, ctx) ->
Option<HandoffGate>` recognizer where:

```rust
pub(crate) enum HandoffGate<'a> {
    SchemaKwarg(&'a Expr),     // gate (a): `schema=` with Spark-tagged value
    PandasPositional(&'a Expr),// gate (b): first positional arg, Pandas-tagged
}
```

Both consumers call the recognizer; the view-side calls
`analyze_expr` on the returned expression to resolve the schema,
the dialect-side returns `Dialect::Spark` unconditionally on any
match. "Keep in sync" comment debt eliminated.

**Surface for PR-A1 author** — IF the recognizer needs more
context than `(call, ctx)` (e.g. takes `source` / `line_index` /
`diagnostics`), flag to TM before opening the PR. Committee
budgeted on the two-argument shape; widening the signature is a
v1.6 risk early-flag.

**Sibling-arm grep before declaring scope** (v15-rule 4):

```
grep -rn 'createdataframe_handoff\|HandoffGate\|inherited_dialect' \
  crates/pykrete/src/
```

Verify exactly 2 consumers exist (dialect-side, view-side) before
opening A1.

**Negative-space tests MANDATORY per v14-rule 4**:
- `spark.createDataFrame(pdf)` where `pdf: PandasFrame[X]` →
  recognizer returns `PandasPositional`; both consumers agree.
- `spark.createDataFrame(rows, schema=sch)` where `sch:
  SparkFrame[X]` → recognizer returns `SchemaKwarg`.
- `spark.createDataFrame(rows, schema=untagged)` → recognizer
  falls through to None; both consumers fall through.
- `spark.createDataFrame(untagged_first_arg)` → recognizer falls
  through to None.

## 4. Pillar D — pandas `pivot_table` (1 PR: D1)

Pandas downpayment. User chose `pivot_table` from the committee
short-list. Single arm; broader reshape (melt, stack/unstack,
groupby.agg, full `pivot_table` schema-tracking) deferred to v1.7
per §9.

**Existing Spark `pivot` dispatch** at `expr.rs:976-1015`. The
arm is gated on `method == "pivot"` (`:976`) AND `receiver` being
a `SchemaView::Grouped { keys, underlying, .. }` (`:984-987`)
— the result of a prior `groupBy(...)`. It validates the literal
pivot-column against `underlying` and carries `after_pivot: true`
forward.

**EXPLICIT non-reuse**: pandas `pivot_table` does NOT route
through this arm. The receiver-state predicate at `:984` is
incompatible — Spark requires `SchemaView::Grouped`, pandas
`pivot_table` takes a DataFrame receiver directly. The
sibling-arm misnomer was caught at committee r1 (both agents
verified the cite); sharing infrastructure across the two reshape
APIs is OUT of v1.6 scope.

### 4.1 Design

**Scope** — `pdf.pivot_table(index=, columns=, values=, aggfunc=)`
literal form only:
- IN: `index=`, `columns=`, `values=` resolve via string literal
  or list-of-string-literals; `aggfunc=` is accepted but its
  value is opaque (any callable accepted).
- IN: column-ref validation — every name in `index`, `columns`,
  `values` must exist on the receiver schema (D0030).
- IN: receiver dialect must be Pandas (gate); Spark receivers
  fall through unchanged.
- OUT: output schema → `Unknown` for v1.6. Full schema-tracking
  (synthesizing the pivoted column layout) deferred to v1.7.
- OUT: non-literal arg shapes (variable, computed) → fall
  through, no diagnostic.

**Inference site**: NEW arm in `analyze_method_call_inner` at
`expr.rs:598`-ish, gated on `method == "pivot_table"` AND
`inherited_dialect(receiver, ctx) == Some(Dialect::Pandas)` AND
receiver resolves to a DataFrame-bound binding.

**Dual-arm requirement per v1.5 retro rule 2**: every new
pandas-dispatched inference arm must fire both at
`analyze_method_call_inner` (for the chained-call surface) AND at
`inherited_dialect` (for the result-of-the-call type tagging).
Spec author for D1 verifies BOTH arms with paste-from-source
fragments in the PR body.

### 4.2 Negative-space tests MANDATORY per v14-rule 4

Per v14-rule 4 (negative-space tests mandatory for every new
inference arm):

- `pdf.pivot_table(index="cat", columns="year", values="amount")`
  all names present in schema → resolves cleanly, no diagnostic,
  result Unknown.
- `pdf.pivot_table(index="typo", columns="year",
  values="amount")` typo in `index` → D0030 fires on
  `"typo"` with "did you mean" suggestion.
- `pdf.pivot_table(index="cat", columns="year", values="typo")`
  typo in `values` → D0030 fires on `"typo"`.
- `pdf.pivot_table(index=["cat", "subcat"], columns="year",
  values="amount")` list form for `index` → each list element
  validated; one typo → D0030 on that element only.
- `sdf.pivot_table(...)` Spark receiver → falls through, no
  diagnostic (gate misses; Spark doesn't have `pivot_table`).
- `helper.pivot_table(...)` unbound receiver → falls through,
  no diagnostic.
- `pdf.pivot_table(index=col_var, columns="year",
  values="amount")` non-literal `index` arg → falls through on
  that arg (literal-only scope); `values`/`columns` still
  validated.
- `pdf.pivot_table()` no args → fall through, no diagnostic
  (we don't enforce required-kwarg shape; runtime catches that).

## 7. v1.5 retro amendments codified in this spec

Per v1.5 retro rule 1 (spec misnomers carry forward to v(N+1),
not v(N)). Three amendments mandatory for v1.6 spec/PR authors:

### 7.1 Inference-site naming — dual-arm pattern

v1.5 spec §2.1/§2.2 named `column_exprs::infer_expr_type` as the
inference site. The actual dual-arm pattern (verified by PR-A1,
PR-A2, PR-C, reviewer-confirmed in v1.5 retro rule 2) is:

- `analyze_method_call_inner` at `expr.rs:598` — chained-call
  arm, fires on `df.method(...)`.
- `inherited_dialect` at `driver.rs:121-160` — result-of-call
  dialect-tagging arm, fires on the LHS binding from
  `result = df.method(...)`.

Both arms fire for the inference to be load-bearing across
chained AND bind-and-use shapes. v1.6 spec authors (D1 in this
cycle, every new pandas arm in v1.7) include a "dual-arm
verification" section in the PR body with paste-from-source
fragments showing both sites.

### 7.2 Blast-radius enumeration — sibling-arm grep mandate

v1.5 PR-B1 enumerated 3 files; the implementation needed 5
(`column_methods.rs` and `two_df.rs` were missed). Every
signature-changing PR in v1.6 includes a `grep -rn <symbol>`
command + expected hit-count in the spec section, and the
implementer re-runs against HEAD before declaring scope. The
wider sweep determines scope, NOT the enumerated list.

Codified in §2.2 (M2 grep), §2.3 (M3 grep), §3.1 (A1 grep), §3.2
(A2 grep). v1.6 PR authors include the grep + hit count + scope
classification table in the PR body.

### 7.3 Extension version-bump strategy — per-PR patch + cycle-close minor

De-facto since v1.3; codify here for v1.6 and onward. Every PR
that touches `crates/pykrete{,-lsp}/**` bumps
`editors/vscode/package.json` by patch (e.g. `0.3.0 → 0.3.1`).
The cycle-close PR (PR-F) bumps the minor (e.g. `0.3.x →
0.4.0`).

Guard mechanic verified at
`.github/workflows/extension-version-guard.yml:87-96` — diff
range is `<latest tag>..HEAD`, NOT per-PR. Per v1.5 retro rule
3, any "CI will catch this" claim in review cites the workflow
file + lines.

This spec PR (PR-S1) does NOT touch `crates/pykrete{,-lsp}/**`,
so no extension version bump is required.

## 8. Joint committee catches — audit findings invalidated

**PR-A2 `inherited_dialect` recursion-depth bound** (v1.5
architecture audit Important #1) — INVALIDATED by joint
code-verification at committee r1. Both Pragmatist and Strategist
independently inspected `driver.rs:121-160` and confirmed the
outer walk is an iterative `loop` (`:126`), not recursion. The
recursive descents at `:150` and `:183`/`:188` walk bounded AST
subtrees (sub-expressions of a single call's arguments), not
unbounded chains. Pathological `df.toPandas().toPandas()...`
chains are walked by the outer `loop`, not by stack frames.

**Do not budget a PR for this finding in v1.6.** The audit
carried a misnomer; the code is correct. Both committee agents
credited +1 valid critique per the planning-committee reward
structure.

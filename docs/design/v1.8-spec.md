### 2.1 PR-A1 — `build.rs`-generated `PANDAS_INHERITED_ARM_METHODS` inventory

The v1.7 retro rule 4 finding. PR-A1 in v1.7 shipped a hand-
maintained inventory in `crates/pykrete/tests/v17_pr_a1_dialect_signals_guard.rs`
to close v1.6 architecture-Important #3 ("three sources of truth").
Within the same cycle, PR-D1 added a new `melt` arm at
`crates/pykrete/src/operations/expr.rs:1172` — the hand-maintained
inventory missed it. The architecture audit caught the drift at
PR-F time, PR-G patched it. v1.7 retro rule 4 codifies: hand-
maintained inventory pins are a v1.8-blocking pattern.

**Design**: a `build.rs` script in `crates/pykrete/` greps
`crates/pykrete/src/operations/expr.rs` at compile time for the two
gating patterns:

- `receiver_is_pandas_inherited && matches!(method, "<X>" | ...)` —
  extract every method-name string literal inside the `matches!`
  arm.
- `receiver_is_pandas_inherited && method == "<X>"` — extract the
  single method-name string literal.

The script emits a generated file (e.g.
`crates/pykrete/src/generated_arm_inventory.rs` or via
`OUT_DIR/arm_inventory.rs` per Cargo convention) containing:

```
pub const PANDAS_INHERITED_ARM_METHODS: &[&str] = &[
    "head", "tail", "first", "take",
    "rename",
    "assign",
    "drop",
    "pivot_table",
    "melt",
];
```

The script reads the live source file at build time, so any future
contributor adding a new `receiver_is_pandas_inherited` arm causes
the generated inventory to update automatically. No hand-edit
required.

**Consumer flip**: the hand-maintained list in
`crates/pykrete/tests/v17_pr_a1_dialect_signals_guard.rs:33-43`
becomes a consumer. The test now asserts BOTH:

1. Each entry in the generated `PANDAS_INHERITED_ARM_METHODS` is
   present in either `PANDAS_ONLY_SIGNALS` or `PANDAS_INHERITED_ARMS`
   (the existing v17 PR-A1 assertion — preserved unchanged).
2. The hand-maintained list and the generated list are byte-equal
   (new for v1.8). This forces a contributor adding a new arm to
   either delete the hand-maintained list (preferred) OR update it
   in lockstep (acceptable interim).

The cleaner end-state is to delete the hand-maintained list entirely
once the generated source is consumable. v1.8 author's call —
deletion vs equality-check — based on what compiles cleanly with
the existing test surface. Committee did NOT mandate; the failure
mode being closed (silent inventory drift within a cycle) is
addressed by either shape.

**Sibling-arm grep before declaring scope** (v15-rule 4 / v17 retro
rule 4):

```
grep -rn 'receiver_is_pandas_inherited\|PANDAS_INHERITED_ARM_METHODS\|PANDAS_INHERITED_ARMS' \
  crates/pykrete/src/ crates/pykrete/tests/ crates/pykrete/build.rs 2>/dev/null
```

Current count on `2df580f`: **11 hits** across `expr.rs` (8 gating
arms), `dialect_signals.rs` (the v17 shared module), and the v17
guard test. Implementer re-runs on their HEAD, reports the delta in
the PR body, and verifies the generator catches every gating arm.

**Negative-space tests MANDATORY per v14-rule 4 / v16-rule 8**:

- Add a synthetic new arm to `expr.rs` (e.g. on a throwaway commit),
  rebuild, verify the generated inventory picks it up. This is the
  build-script equivalent of "does the regex match what we expect."
- Remove an existing arm temporarily, rebuild, verify the inventory
  shrinks. Regression guard for the regex pattern.
- The cross-equality test fails loudly if the hand-maintained list
  and the generated list diverge.

**Closes v1.7 retro rule 4.**

### 2.2 PR-A2 — CI grep gate `scripts/changelog-grep.sh`

The v1.7 retro rule 6 finding. v1.7 PR-F's CHANGELOG quoted a
warning text different from the actual `crates/pykrete/src/main.rs:660`
emission. Headline UX change of the release shipped with doc-vs-code
drift on the very string users would grep for. Architecture auditor
caught it as B2. v1.7 retro rule 6 codifies: any string literal
quoted in CHANGELOG/README that comes from binary output MUST grep-
anchor to source.

**Design**: a new `scripts/changelog-grep.sh` script + a CI job
that runs it. The script:

1. Parses `CHANGELOG.md` for fenced code blocks labeled `stderr`,
   `stdout`, or `text`. Per committee r2 (P R2 + S R2 convergence),
   the input-filter heuristic is:

   ```
   /^```(stderr|stdout|text)?\n([\s\S]*?)^```/m
   ```

   Multiline regex; matches fenced blocks with the three allow-
   listed labels (plus unlabeled — the `?` makes the label
   optional). The captured group `[2]` is the block content.

   **Crucial**: this does NOT match every backtick in CHANGELOG.
   CHANGELOG.md has ~212 inline backticks (verified on `2df580f`),
   most of which are flag names, file paths, code identifiers, and
   prose decoration that are NOT binary-emitted strings. Only fenced
   blocks marked as binary output get grep-anchored.

2. For each extracted block, splits into non-empty lines and grep-
   anchors each line to `crates/pykrete/src/`:

   ```
   grep -rF "<line>" crates/pykrete/src/
   ```

   Exit non-zero if any line isn't found.

3. CI integration: a new workflow step or a new job that runs the
   script. Fails the PR loudly with a list of unanchored lines and
   a one-line explanation linking back to v1.7 retro rule 6.

**Scope boundary**: the gate covers ONLY CHANGELOG.md fenced
binary-output blocks. README, docs site prose, and inline backticks
are out of scope this cycle — they're a noisier surface with more
false positives (TS-style prose decoration, future-tense aspirational
copy, etc). v1.9 candidate: expand to README's fenced blocks once
the heuristic settles.

**Heuristic-acceptance rationale**: the committee P R2 + S R2
convergence settled on the fenced-with-label heuristic because:
- It's grep-anchored, not LLM-anchored — deterministic and fast in
  CI.
- The false-positive rate on a corpus check of v1.5/v1.6/v1.7
  CHANGELOG history is acceptably low. v1.7's specific drift
  (CHANGELOG quoted a stderr that didn't exist) would have been
  caught.
- The false-negative rate (binary-output strings quoted outside
  fenced blocks) is non-zero but documented. v1.9 candidate to
  tighten.

**Sibling-arm grep before declaring scope** (v15-rule 4):

```
grep -c '```' CHANGELOG.md
grep -cE '^```(stderr|stdout|text)' CHANGELOG.md
```

Current count on `2df580f`: roughly **40+ fenced blocks** in
CHANGELOG, of which **~10** are labeled `stderr`/`stdout`/`text`.
Implementer counts on their HEAD and reports the delta in the PR
body. The script must produce a "checked N blocks across M lines"
summary so future PRs can see the gate's surface area.

**Negative-space tests MANDATORY per v14-rule 4**:

- The script run on `2df580f` (v1.7.0 tag HEAD) passes. This is the
  regression guard — v1.7.0 SHIPPED with the drift, so the test
  fixture needs a paired CHANGELOG fix (see below) before the
  script can be green on tip.
- Intentionally introduce a wrong stderr string in a test fixture
  CHANGELOG, run the script, verify failure with the unanchored
  line called out.
- A fenced block labeled `python` (not in the allow-list) is
  SKIPPED — code snippets aren't binary output.

**Paired CHANGELOG fix**: v1.7.0's CHANGELOG drift was patched in
PR-G (`2df580f`), so the v1.8 spec author should verify the script
runs clean against current `main` before assuming the gate is
"on." If any v1.7-era stderr strings still don't anchor, A2's PR
includes a CHANGELOG fix-up commit per the v1.5 retro atomic-pairing
rule.

**Severity check (v16-rule 13 / v17 retro)**: A2 is a CI-gate
addition. No D-code changes, no behavior changes. No catalog-pin
pykrete-tests refresh needed for A2.

**Closes v1.7 retro rule 6.**

## 3. Pillar D — spark-D2 new D-code (1 PR: D1)

The cycle's new D-code. **Warning-only this cycle**, with strict-
mode escalation deferred to v1.9 per §9. Closes v1.7 §10.3 deferral.

### 3.1 The back-compat surface

The shared `column_method_shape` dispatch arm at
`crates/pykrete/src/operations/expr.rs:1245-1283` plus the shape
inventory at `crates/pykrete/src/operations/shapes.rs:46-49`
(`withColumn`) does NOT today gate on receiver dialect. Concretely:
verified on `2df580f`, `pdf.withColumn("status", lit("X"))` — where
`pdf: PandasFrame[X]` — silently typechecks as Spark, because the
arm at `expr.rs:1245` matches any receiver and the shape inventory
exposes `withColumn` regardless of dialect tag.

This is wrong: pandas DataFrames don't have `withColumn`. The
runtime would `AttributeError`. Today's pykrete shrugs and treats
it as a valid Spark column-method call, returning the receiver
schema unchanged.

`melt` and `pivot_table` are NOT in this category — both already
gate on `receiver_is_pandas_inherited` at `expr.rs:1145` and
`expr.rs:1172`, so they dispatch correctly. `withColumn` is the
lead case for spark-D2 because it's the most-used Spark column-
method that pandas users would reach for.

### 3.2 D0091 design (committee-spec'd)

**New D-code**: D0091 (the next free slot after D0090). Name:
`receiverDialectMismatch` or similar (implementer picks; committee
did NOT mandate the rule-name string).

**Firing pattern**: a method call where:
- The receiver dialect is adjudicated as Pandas (per
  `inherited_dialect` at `operations/driver.rs:121`).
- AND the method is on the spark-D2 allow-list (see below).
- AND the arm currently typechecks (i.e. there's no other
  diagnostic that fires first; D0091 is a quality-of-result
  warning, not a parse error).

**Allow-list**: `withColumn` is the lead case for v1.8. The
implementer surveys the `column_method_shape` inventory at
`shapes.rs:42-54` and flags any method that:
- Sits in the shared shape inventory (currently typechecks for
  any dialect).
- Is documented as Spark-only on the PySpark API.
- Has a pandas equivalent users would reach for instead (so the
  diagnostic can carry an actionable "did you mean" suggestion).

Per the shape inventory at `shapes.rs:42-54`, the immediate
candidates are `withColumn`, `withColumnRenamed`. Other column
methods (`select`, `drop`, `dropDuplicates`, `filter`, `where`,
`groupBy`, `dropna`) overlap in semantics with pandas — they're
NOT spark-D2 candidates. The committee did NOT pre-commit beyond
`withColumn` as the lead case; the implementer extends to
`withColumnRenamed` if the diagnostic message and "did you mean"
suggestion compose cleanly.

**Diagnostic message** (committee-spec'd shape; final wording is
implementer's call):

```
D0091: 'withColumn' is a Spark DataFrame method but the receiver
is a PandasFrame. Use '.assign(<col>=<expr>)' for pandas.
```

The "did you mean" suggestion is REQUIRED — D0090's pattern
(actionable rewrite, not a bare scold). For `withColumn(c, v)`,
the suggestion is `.assign(c=v)`. For `withColumnRenamed(old,
new)`, the suggestion is `.rename(columns={old: new})`.

**Severity**: warning-only this cycle. Concretely: the diagnostic
fires at `Severity::Warning`, NOT `Severity::Error`. Strict-mode
escalation (the v1.6 D0090 pattern where strict mode flips it to
error) is **explicitly deferred to v1.9**. Rationale: the back-
compat surface needs in-the-wild observation. Today's silent
typecheck has been the behavior since the dialect split landed in
v1.3; flipping to error in one cycle is high-risk. Ship warning
first, gather signal, escalate in v1.9.

**What "warning-only this cycle" means structurally**: no strict-
mode plumbing change in `crates/pykrete/src/lints.rs` (or wherever
strict-mode severity tables live). D0091 is registered with a
fixed-warning severity. v1.9 ships the strict-mode arm.

**Back-compat preservation**: the existing un-gated arm continues to
typecheck — the receiver schema is returned unchanged, downstream
analysis continues. D0091 fires as warning ALONGSIDE the existing
behavior. No semantic break: a codebase that today has
`pdf.withColumn(...)` calls will still emit the same downstream
inference; users just see a new warning at the call site. This is
the v1.6 PR-M1 atomic-pair model: ship the surface (warning) before
the teeth (strict-mode error).

## 4. Pillar V — v2.0 deprecation runway (1 PR: V1)

### 4.2 Part 2 — `--deprecation-report` JSON envelope

**New flag** on `pykrete check`. Reuses the `--report-aliases`
plumbing pattern at `crates/pykrete/src/main.rs:178` (flag parse)
and `:261` (invocation-only early-exit dispatch). No new CLI
surface beyond the flag itself — same exit-code 0 + JSON to stdout
shape as `--report-aliases`.

**Flag parse**: extend `parse_check_args` at `main.rs:144-192` to
recognize `--deprecation-report` as a boolean flag. Same shape as
the existing `--report-aliases` branch at `:178`.

**Invocation-only early exit**: at `main.rs:261-272`, the
`--report-aliases` branch runs `pykrete::collect_alias_sites` +
`pykrete::adjudicate_alias_sites` + `pykrete::render_alias_report_json`
+ exit 0. V1 adds a parallel branch for `--deprecation-report` that:

1. Runs the same site collection + adjudication.
2. Filters sites to those that adjudicate as D0090-firing.
3. Renders a NEW JSON envelope (not reusing the alias-report one).
4. Prints to stdout, exits 0.

**JSON schema** (committee-spec'd):

```json
{
  "schema_version": 1,
  "pykrete_version": "1.8.0",
  "generated_at": "<ISO-8601 UTC>",
  "sites": [
    {
      "path": "src/example.py",
      "line": 42,
      "column": 12,
      "raw_text": "DataFrame[Schema]",
      "rewrite": "SparkFrame[Schema]",
      "verdict": "spark" | "pandas" | "ambiguous"
    }
  ],
  "summary": {
    "total_sites": 123,
    "by_verdict": {
      "spark": 100,
      "pandas": 15,
      "ambiguous": 8
    }
  }
}
```

**Schema notes**:
- `schema_version: 1` — explicit versioning so downstream CI gates
  can pin. Future schema changes bump this.
- `pykrete_version` — populated from `env!("CARGO_PKG_VERSION")` at
  build time. Lets consumers tell which pykrete generated the
  envelope.
- `generated_at` — ISO-8601 UTC timestamp. Lets CI dashboards diff
  envelopes over time without re-running.
- `sites[].verdict` — mirrors the v1.7 alias_report `verdict` field
  exactly (`spark` / `pandas` / `ambiguous`). Per-site adjudication
  from the call-graph adjudicator. NO new adjudication logic — V1
  reuses the v1.5 PR-D plumbing.
- `summary.by_verdict` — counts pre-computed so dashboards don't
  re-aggregate. Convenience field; the source of truth is `sites`.

**Schema is implementer-committed**: this shape is the v1.8 contract.
Future schema additions can append fields (per JSON-compatible
evolution), but the v1 fields are stable. Document the schema in
the v1.8 docs site under `cli/deprecation-report` or similar.

**Consumer use cases** (cited in the release notes):
- CI gating: "fail the build if `pykrete check --deprecation-report
  | jq '.summary.total_sites' > 0`" — a no-tolerance gate.
- Migration tracking: dashboards diff envelope snapshots over time.
- "What's left before v2.0": a single `jq` query against the
  envelope gives the exact site list, no diagnostic-text parsing.

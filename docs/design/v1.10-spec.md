#### 2.1.1 Ack-marker multi-line signature support (closes v1.9.1 #2 / arch-I1)

Today's `crates/pykrete/src/alias_report.rs::line_above_has_ack_marker`
(line 203) computes "line above" by counting newlines backward from
the annotation's byte offset. Single-line `def f(a: DataFrame[X])`
signatures work. Multi-line signatures break:

```python
# pykrete: ack-deprecation     <-- marker on the line ABOVE def f
def f(
    a: DataFrame[X],
) -> int:
    ...
```

The annotation's byte offset for `a: DataFrame[X]` is on its own
line, not on the `def f(` line. `line_above_has_ack_marker`
reads "line above the annotation" = the `def f(` continuation line,
not the marker line. The marker silently has no effect; the site
emits `pending` instead of `acknowledged`.

**Fix**: walk past `def NAME(` continuation lines when computing
"line above." The walk terminates at the line containing the open
paren of the enclosing `def` (or `async def`). If the line above
that is the marker line, the site is `acknowledged`.

**Why not "scan the whole def body for the marker"**: would
over-fire — a marker on an unrelated annotation deeper in the
signature shouldn't ack the first annotation. The walk is
narrowly scoped: only the def-line's prior line is checked, after
skipping the continuation chain.

**Sibling-arm grep before declaring scope** (v15-rule 4):

```
grep -rn 'line_above_has_ack_marker\|ack-deprecation' \
  crates/pykrete/src/ crates/pykrete/tests/
```

Implementer reports current hit count on HEAD in the PR body.

**Negative-space tests MANDATORY per v14-rule 4**:

- Single-line `def f(a: DataFrame[X]) -> int:` with marker on the
  line above `def f(` → site is `acknowledged`. v1.9 PR-V1
  behavior preserved (regression guard).
- Multi-line `def f(\n    a: DataFrame[X],\n) -> int:` with
  marker on the line above `def f(` → site is `acknowledged`.
  v1.10 PR-A1 closure.
- Multi-line def with marker on the line above `a:` (inside the
  signature, NOT above `def f(`) → site is `pending`. The marker
  must sit at the def-line's prior line, not arbitrarily inside.
- Multi-line def + multi-line annotation (`DataFrame[\n    LongSchemaName\n]`)
  with marker on the line above `def f(` → site is `acknowledged`.
- Module-level annotation (no enclosing `def`) with marker on the
  line above → site is `acknowledged`. v1.9 behavior preserved
  (regression guard).
- A non-def-continuation line above the def (`# unrelated comment`)
  → site is `pending` even if a marker appears earlier. The walk
  terminates at the def line, not arbitrarily upward.

**Closes v1.9 retro item v1.9.1 #2 / arch-I1.**

#### 2.1.2 Property/method tripwire (closes v1.9 arch-I3)

`crates/pykrete/src/dialect_signals.rs` ships `SPARK_DISCRIMINATORS`
(line 71) for method-level Spark discrimination AND
`SPARK_DISCRIMINATOR_PROPERTIES` (line 184) for property-level
discrimination introduced in v1.9 PR-D2. The two lists overlap by
design — properties that are also methods on the API surface
(e.g. `isStreaming`) appear in both. v1.9 arch-I3 surfaced the
silent drift class: adding a new entry to
`SPARK_DISCRIMINATOR_PROPERTIES` without mirroring it in
`SPARK_DISCRIMINATORS` lets the property arm fire D0091 while the
method arm doesn't, or vice versa. Same for pandas:
`PANDAS_INHERITED_PROPERTIES` (line 197) and `PANDAS_ONLY_SIGNALS`.

**Fix**: tripwire test asserting `SPARK_DISCRIMINATOR_PROPERTIES`
is a subset of `SPARK_DISCRIMINATORS`, and `PANDAS_INHERITED_PROPERTIES`
is a subset of `PANDAS_ONLY_SIGNALS`:

```rust
assert!(
    SPARK_DISCRIMINATOR_PROPERTIES
        .iter()
        .all(|p| SPARK_DISCRIMINATORS.contains(p)),
    "SPARK_DISCRIMINATOR_PROPERTIES must be a subset of \
     SPARK_DISCRIMINATORS — property arm and method arm \
     must agree on the discriminator set"
);
```

Mirror for pandas. Add to
`crates/pykrete/tests/v17_pr_a1_dialect_signals_guard.rs` (the
existing dialect-signals tripwire file) or a sibling
`v1_10_pr_a1_property_method_tripwire.rs` — implementer picks; the
committee did NOT mandate.

**Why subset, not equality**: not every method discriminator
makes sense as a property (e.g. `withColumn` is a method, not an
attribute). The asymmetry is intentional; the subset relation
catches "added a property without the method."

**Why this isn't gen'd by build.rs**: build.rs scrapes
`Expr::Call` arms in `expr.rs`; the property arm lives in
`Expr::Attribute` with its own dispatch shape. v1.9 build.rs
inventory holes (carry-forward of v1.8 arch-I1) were intentional
non-scope for v1.9; v1.10 closes the same drift class via runtime
assertion instead of build-script extraction.

**Negative-space tests MANDATORY per v14-rule 4**:

- The tripwire passes on `main` at `4caefb5` (both lists are
  subsets — regression guard).
- Inject a synthetic test (e.g. via a `#[cfg(test)]` mod that
  overrides the const, or a doc-test that constructs a property
  list with an unmirrored entry) → assertion fires. Per v17 retro

#### 2.2.1 Release-gate CI workflow (closes v1.9 arch-I2)

New `.github/workflows/release-gate.yml` workflow triggered on:
- Push to a release branch (`release/v*`).
- PRs labeled `release-ready`.

The workflow auto-runs `scripts/changelog-grep.sh` WITHOUT the
`--skip-live-extract` flag (verifies live extracts before tag).
v1.9 arch-I2 surfaced the gap: the daily CI step runs
`changelog-grep.sh --skip-live-extract` (fast, no Python deps);
the live-extract verification was a manual step at PR-F time. A
PR-F dev who forgot to run it could ship a CHANGELOG with a stale
numeric claim. v1.10 closes this structurally by gating release
branches AND `release-ready`-labeled PRs on the live-extract run.

**Workflow shape** (committee-spec'd):

```yaml
name: Release Gate
on:
  push:
    branches: [release/v*]
  pull_request:
    types: [labeled, synchronize]
jobs:
  release-gate-check:
    if: |
      github.event_name == 'push' ||
      contains(github.event.pull_request.labels.*.name, 'release-ready')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.11' }
      - name: Install pykrete-tests deps for live extract
        run: |
          # PR-A2 author wires the actual checkout/install steps
          # per the existing changelog-grep.sh known-claim table
      - name: Run release-gate (with live extract)
        run: scripts/changelog-grep.sh
```

**Why not "always run live-extract on every PR"**: the
live-extract requires checking out pykrete-tests + running
`probes.py extract cross-codebase` (Python deps + tens of seconds
of execution). Running it on every PR would inflate the daily CI
load 5-10x. The release-gate trigger is the cost-correct point:
run it once per release, not once per PR.

**Sibling-arm grep before declaring scope** (v15-rule 4):

```
grep -rn 'changelog-grep\|release-gate\|--skip-live-extract' \
  .github/ scripts/
```

PR-A2 author reports the hit count on HEAD in the PR body.

**Negative-space tests** (manual at PR-F time, codified in §6):

- A release branch with all CHANGELOG claims matching live
  extracts → workflow exits 0.
- A release branch with a CHANGELOG claim that drifts from live
  extract → workflow fails with the v2-gate MISMATCH line.
- A non-release-branch PR without the `release-ready` label →
  workflow does NOT run. Negative-space guard for the trigger.

**Closes v1.9 architecture audit finding arch-I2.**

#### 2.2.2 CHANGELOG grep gate v3 — prose number scan (closes v1.9 retro rule 12)

v1.9 PR-A2 shipped gate v2 (the `text-numeric` fenced block).
v1.9 PR-F's CHANGELOG shipped "183 + 72" as a prose-paragraph
trust-claim, OUTSIDE any `text-numeric` block. The v2 gate didn't
flag it because v2 only inspects labeled fenced blocks. v1.9 retro
rule 12 codifies: extend the gate to scan unstructured prose
paragraphs for numeric claims.

**Design**: extend `scripts/changelog-grep.sh` with a prose-scan
pass. The scan finds `<digit-sequence> <known-key>` patterns in
prose paragraphs and cross-references the digit against the same
known-claim table the v2 gate uses.

**Pattern** (regex-shaped):

```
\b(\d{2,4})\s+(positive|negative|probes|fixtures|tests|donors)\b
```

For each match, look up the key in the known-claim table. If the
digit differs from the live extract, fail with
`PROSE MISMATCH: <digit> <key> (live: <live>)`.

**Escape hatch — single-backtick wrap**: editors who want a
number NOT auto-verified (e.g. a historical number quoting a v1.8
release; a number from external documentation that pykrete
shouldn't gate) wrap it in single backticks:
`` `106 fixtures` ``. The scanner skips matches inside single-
backtick spans. This is the CHANGELOG editor's "trust me, this is
historical" affordance.

**Scope boundary**: only CHANGELOG.md. README, docs-site prose,
and other surfaces stay out of scope (different drift profile;
v1.11 candidate per §11). The v2 fenced-block gate continues to
cover labeled blocks across CHANGELOG.md + docs/**/*.md
unchanged (regression guard).

**Sibling-arm grep before declaring scope** (v15-rule 4):

```
grep -rn 'changelog-grep\|text-numeric\|known-claim' \
  scripts/ .github/
```

PR-A2 author reports the hit count on HEAD in the PR body.

**Self-verify** (committee-spec'd, mirrors v1.9 PR-A2 §2.2):
emulate v1.9 PR-F's "183 + 72" drift. PR-A2 ships a fixture-
CHANGELOG containing a prose paragraph with `999 fixtures`; the
script's self-test asserts the gate fires `PROSE MISMATCH: 999
fixtures (live: <live>)`. This is the v14-rule 4 negative-space
test for the prose scanner itself.

**Negative-space tests MANDATORY per v14-rule 4**:

- CHANGELOG with prose `"112 fixtures"` matching live extract →
  exit 0 (no PROSE MISMATCH).
- CHANGELOG with prose `"999 fixtures"` (drift) → exit 1 with
  `PROSE MISMATCH: 999 fixtures (live: 112)`.
- CHANGELOG with prose `` "`106 fixtures`" `` (single-backtick
  wrapped) → exit 0 (escape hatch honored).
- CHANGELOG with prose `"3 donors"` matching live extract →
  exit 0. Tests the `donors` key.
- CHANGELOG with prose `"42 something-else"` (unknown key) → exit
  0. Only known keys are gated.
- v2 fenced-block behavior unchanged on every fixture →
  regression guard.

**CI integration**: same workflow step as v2. Gate v3 is an
extension of the same script; no new CI job. The release-gate
workflow from §2.2.1 runs the SAME script with `--skip-live-extract`
off; daily CI runs it with `--skip-live-extract` on (prose scan
still runs against the known-claim table but skips the live
verification — checks syntax only, defers value-check to release
gate).

**Closes v1.9 retro rule 12.**

#### 3.1.3 `--fail-on-nonempty` flag (closes v1.9 arch-I4)

Add `--fail-on-nonempty` to `pykrete check --deprecation-report`.
Default off; when set, exit code is 1 if `summary.totalSites > 0`
AFTER `--ack` filtering. Compatible with `--ack`.

**CI gating use case**: saves the boilerplate

```bash
pykrete check --deprecation-report --ack=pending src/ \
  | jq '.summary.totalSites' \
  | xargs test 0 -eq
```

…with the direct invocation:

```bash
pykrete check --deprecation-report --ack=pending --fail-on-nonempty src/
```

Exit 0 if no pending sites; exit 1 if any. CI step becomes a
one-line invocation.

**Flag parse**: extends `parse_check_args` at
`crates/pykrete/src/main.rs:144-192` to recognize
`--fail-on-nonempty` as a boolean flag. Combinations with `--ack`
are first-class supported; `--fail-on-nonempty` without
`--deprecation-report` exits 2 with stderr error (mirrors v1.9
`--ack` requires `--deprecation-report` enforcement).

**Compatibility with `--snapshot` from V1**: when both
`--snapshot` and `--fail-on-nonempty` are set, the snapshot is
ALWAYS written first (so consumers have the archived state) THEN
the exit code is computed. Even on exit 1, the snapshot file is
on disk. PR-D1 author + PR-V1 author coordinate (briefs reference
each other) so the dispatch order is settled.

## 4. Pillar D — pandas `stack` arm (1 PR: D2, NEW INFERENCE ARM)

The cycle's pandas reshape continuation. User picked `stack` at
committee r3 from the three-way choice `stack` / `unstack` /
`groupby.agg`. Mirrors v1.6 PR-D1 (`pivot_table`) + v1.7 PR-D1
(`melt`) shape. One-per-cycle pattern continues.

### 4.1 PR-D2 — pandas `stack` literal-form arm

**Receiver gate**: PandasFrame[X] only. Spark's `stack` is a
column function (`pyspark.sql.functions.stack`), not a DataFrame
method. The dispatch MUST NOT misroute Spark calls — receiver
dialect gate handles it (`receiver_is_pandas_inherited` from v1.7
PR-D1 / v1.9 §3.2 reused).

**Recognized kwargs**:
- `level` — `int | str | list-of-int | list-of-str | None`.
  Selects the column-level (or index-level on a multi-index frame)
  to stack into the row index.
- `dropna` — `bool` (optional, default `True` per pandas).

**Inference logic**:
- When `level` is a literal (int / str / None) OR a literal list
  thereof → infer the result columns from the receiver's schema
  by removing the stacked level(s). The remaining columns form
  the result schema; the stacked level becomes a new index level
  (pykrete's PandasFrame schema doesn't model index levels — see
  v1.4 pandas-support.md §5 — so the result schema is just the
  remaining columns).
- When `level` is a dynamic expression (a Name, a function call,
  a complex expression) → fall through to Unknown. The arm
  doesn't synthesize; the v1.7 melt pattern at `expr.rs::melt_arm`
  is the precedent.

**Literal column validation**: when `level` references column
names as a literal list of strings (`level=['a', 'b']`), validate
each against the receiver schema. Unknown name fires D0030 with
the v1.4 "did you mean" suggestion shape. Mirrors v1.6 / v1.7
patterns.

**Result schema construction**:
- `level=int` or `level=str` → receiver columns MINUS the stacked
  column. Result is `PandasFrame[ResultSchema]` with a fresh schema
  derived from the receiver MINUS the stacked column.
- `level=list-of-int` or `level=list-of-str` → receiver columns
  MINUS all stacked columns.
- `level=None` → receiver columns MINUS the LAST level (pandas
  default). On a single-level frame, this is "MINUS the last
  column."
- Any other shape → Unknown.

**Why fall-through-to-Unknown is the right default**: pandas
`stack` on multi-index columns has user-defined semantics
pykrete can't reliably model without the index-level concept.
v1.4 pandas-support.md §5 carves out index modeling as out-of-
scope for the v1.x lifetime. The arm covers the common literal
case (the v1.7 / v1.6 precedent) and stays silent on the rest.

**Negative path — Spark receiver**: a Spark receiver invoking
`.stack(...)` MUST NOT trigger D0091 from the `stack` arm
specifically (different concern — `stack` is a column function on
Spark, not a DataFrame method, so there's no Spark-direction
inherited-arm precedent). The receiver dialect gate handles this:
the arm only matches PandasFrame receivers. If a Spark receiver
invokes `.stack`, the arm's gate doesn't fire; the dispatch falls
through to the existing Spark column-function path.

## 5. Pillar V — `--snapshot` file-write (1 PR: V1)

The cycle's user-facing addition. Atomic single-feature:
`--snapshot=<path>` writes the JSON envelope to disk instead of
stdout.

### 5.1 Flag semantics

```
pykrete check --deprecation-report --snapshot=/tmp/migration.json src/
```

The envelope JSON is written to `/tmp/migration.json` and stdout
is empty (or carries the standard pykrete check report — see
§5.4). The envelope is byte-for-byte identical to the stdout
form when `--snapshot` is absent. Compatible with `--ack`:

```
pykrete check --deprecation-report --snapshot=/tmp/pending.json \
  --ack=pending src/
```

filters to pending sites and writes the filtered envelope.

### 5.2 Schema reuse — no envelope bump

The envelope schema is unchanged. v1.9 PR-V1 shipped
`deprecationReportVersion: "2"`; v1.10 PR-V1 keeps `"2"` because
the on-disk form is the same as the stdout form. The schema bump
discipline says "bump when the per-site shape changes or the
value set expands" — neither happens with `--snapshot`. Consumers
pinned to v2 read the snapshot file unchanged.

### 5.3 Plumbing

Reuses `crates/pykrete/src/main.rs:337`
`render_deprecation_report_json(&sites, ack_filter)`. The
difference is the sink: today stdout via `print!`; with
`--snapshot` via `std::fs::write(path, rendered)`.

**Flag parse**: extends `parse_check_args` at
`crates/pykrete/src/main.rs:144-192` to recognize
`--snapshot=<path>` as a string flag taking a filesystem path.
Unknown / malformed values → exit 2.

**Compatibility with `--fail-on-nonempty` from D1**: snapshot is
ALWAYS written first; exit code computed AFTER. Even on exit 1,
the snapshot is on disk. Coordinated with PR-D1 per §3.1.3.

### 5.4 Exit codes

- Exit 0: snapshot written successfully. NO gating; gating is
  D1's `--fail-on-nonempty` job.
- Exit 1: only when `--fail-on-nonempty` is set AND the filtered
  envelope has non-zero `totalSites` (per D1's semantics).
  Snapshot is on disk regardless.
- Exit 2: file write failed (permission denied, path doesn't
  exist, disk full, etc.). Stderr carries the clear error.

### 5.5 CRITICAL CARVE-OUT — NO `--compare-to`

Per v1.9 design author boundary at
`crates/pykrete/src/alias_report.rs:282-284`: `"resolved"` is
consumer-side state. A `--compare-to <snapshot>` flag would
introduce a consumer-state-model surface into pykrete (read prior
snapshot, diff sites, emit `resolved` for sites that vanished).
That's a product fork — the consumer state model is multiple
shapes (sites keyed by file+line vs file+symbol vs file+content-
hash; rename-tracking vs not; etc.), all defensible, none
committee-decideable. v1.11 spec time settles the consumer surface
with user input. v1.10 ships the writer; the reader is product
fork.

This carve-out is load-bearing for the v1.10 trust claim. If V1
ships with `--compare-to`, the trust claim collapses to "pykrete
ships an opinionated consumer model" — and the user hasn't
authorized that shape. PR-V1 implementer + PR-F dev verify no
`--compare-to` landed.

### 5.6 Sibling-arm grep before declaring scope (v15-rule 4)

```
grep -rn '"--deprecation-report"\|deprecationReportVersion\|render_deprecation_report_json\|"--ack"' \
  crates/pykrete/src/
```

Implementer reports current hit count on HEAD in the PR body.
Update flag parse, dispatch arm, and the file-write call site in
lockstep.

### 5.7 Negative-space tests MANDATORY per v14-rule 4

- `pykrete check --deprecation-report --snapshot=/tmp/x.json src/`
  → file `/tmp/x.json` exists with valid JSON, stdout has no
  envelope. Exit 0.
- Snapshot file contents byte-for-byte equal stdout output of the
  same invocation WITHOUT `--snapshot` (with same filter). The
  envelope is identical; only the sink differs.
- `--snapshot=/proc/cannot-write.json` (or any permission-denied
  path) → exit 2, stderr error names the path AND the underlying
  OS error.
- `--snapshot=<path-with-non-existing-parent-dir>` → exit 2.
  Does NOT silently create parents.
- `--snapshot` without `--deprecation-report` → exit 2 with stderr
  error. Mirrors v1.9's `--ack` requires `--deprecation-report`.
- `--snapshot` + `--ack=pending` → file contains the filtered
  envelope. Compatible.
- `--snapshot` + `--fail-on-nonempty` (D1) + pending sites
  present → file written, exit 1. Snapshot persists on exit-1.
  Coordination check with D1.
- `--snapshot` + `--fail-on-nonempty` (D1) + no pending sites
  → file written, exit 0. Coordination check with D1.
- The envelope's `deprecationReportVersion` reads `"2"`
  unchanged. Schema-stability regression guard.
- The envelope contains NO `target_version` field. v1.9 §4.5
  carve-out reaffirmed.
- The envelope contains NO `previous_snapshot_diff` field. v1.10
  §5.5 carve-out (no `--compare-to`) reaffirmed.

### 5.8 Severity check (v16-rule 13)

V1 does NOT change D0090 severity. V1 does NOT add a new D-code.
The envelope schema is unchanged. No catalog-pin pykrete-tests
refresh needed for V1.

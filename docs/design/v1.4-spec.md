## 1. Theme + headline

v1.4 is **depth on pandas**: match the PySpark donor breadth v1.0
established and close the type-tracking gap v1.3 deferred. The
v1.3.0 trust claim is "we check the pandas dispatched operations
end-to-end" — historically "six" (`df[col_list]`, `df[mask]`,
`df["new"] = expr`, `df.rename`, `df.drop(columns=…)`, `df.merge`)
**plus** `df.assign(new=expr, …)` and **plus** `df.melt(...)` /
`df.unpivot(...)` (the shared `apply_melt` dispatcher at
`expr.rs:989`; PR-E counts the modeled-op list via grep per
v13-rule 11 and the live count may resolve to 8 rather than 7).
The two add-columns ops share
the schema-extension helper `add_or_replace_column`
(`column_methods.rs:363`) but route through different code paths:
`df["new"] = expr` is statement-level subscript-assign handled at
`driver.rs:187-215` (enum-sink check + `infer_expr_type` for the
type, NO `report_expr_type_errors` call on the RHS);
`df.assign(new=expr, …)` is a dispatched method call recognized
at `expr.rs:947` and routed via `apply_pandas_assign`
(`column_methods.rs:445-458`) → `apply_add_columns_iter`
(`:335-357`), which DOES call `report_expr_type_errors` per kwarg
value at `column_methods.rs:353`. Round-2/3 spec said
"`df.assign` dispatches via the same piece-(b) path as
`df["new"] = expr`" — wrong; corrected here (I-R3-1). The §3
synth choice depends on this distinction. PR-E docs MUST grep
`crates/pykrete/src/operations/` for the live count (v13-rule 11).
The v1.4.0 trust claim is "we check pandas usage across the
dominant pandas stack — ML, stats, schema validation, data quality,
forecasting, visualization, financial/economic data — and we track
dtypes through those operations."

## 3. PROBE-TYPE-IS extension design

Closes **pykrete-tests#14** AND extends the pykrete checker so the
extension actually fires. Two coupled deliverables shipped under

### 3a. Recognizer extension (`pykrete-tests`)

### 3b. Synth shape (pandas TYPE-IS)

Spark wraps the col ref in `df.select(col("x") + lit(1))` →
D0081 arithmetic checker (scalar: single col's dtype, not a frame
projection). **Decision**: for `PandasFrame[X]`, synth wraps the
subscript-arithmetic *inline inside a dispatched method call* so
it lands in a code path that already feeds `report_expr_type_errors`:

```python
df.assign(__probe=df["x"] + 1)   # synth: dispatched df.assign kwarg value
```

Why this shape and not `result = df["x"]; result + 1`:

- `df.assign(...)` is one of the v1.3 dispatched ops; its kwarg
  values are walked by `apply_pandas_assign` →
  `apply_add_columns_iter` (`column_methods.rs:457` → `:339`), which
  calls `report_expr_type_errors(value, recv, …)` per kwarg at
  `column_methods.rs:353` — exactly the D0081 dispatch we need to
  reach.
- The intermediate-binding shape (`result = df["x"]`) would also
  need an `Expr::Name` lookup in `infer_expr_type` for `result`;
  that table doesn't exist today and would require a new
  per-binding side table on `BodyContext` (fork (b) below) or a
  `TypeCtx` extension (fork (c)). Folding the subscript inline
  removes the intermediate binding entirely.
- The bare-subscript-assign shape (`df["new"] = df["x"] + 1`) does
  NOT reach D0081: the subscript-assign path at `driver.rs:187-215`
  does its own enum-sink check + `infer_expr_type` for the result
  type but does NOT invoke `report_expr_type_errors` on the RHS.
  (I-R3-1 correction — see §3e.)

Spark synth unchanged (`df.select(col("x") + lit(1))`). Both
synths share the principle "wrap the col ref in a dispatched
method-call expression whose value-position arg gets D0081-walked"
— they are NOT the same shape (Spark uses `col(...)`, pandas uses
`df["..."]`), and that asymmetry is the v1.3 dispatch boundary,
not a defect. `df[["x"]]` (list slice) returns a single-col frame
routing through column-projection dispatch — wrong shape for a
scalar marker; multi-col shape is a future marker.

### 3c. `infer_expr_type` Subscript-on-Name arm (`pykrete` checker)

**BLOCKER caught at round 3 (adversarial lens against `main`)**:
the §3b synth was specified before walking the receiving code. On
current `main`, `df["x"] + 1` (whether bare or inside an `assign`
kwarg) does NOT route to D0081 because:

- `crates/pykrete/src/operations/column_exprs.rs:46-50` —
  `infer_expr_type(expr, schema, tcx)` has NO `Expr::Subscript`
  arm. The `Expr::Call` arm handles `col("x")` via `col_reference`
  at L52; everything else falls into the catch-all `_ =>
  python_literal_type(expr)` at L240 which returns `None` for a
  Subscript. The function has no codepath to return a `ColumnType`
  for `df["x"]`.
- `crates/pykrete/src/operations/strict_operators.rs:115-148` —
  the D0081 dispatch calls `infer_expr_type(&b.left, schema,
  tcx)` and `infer_expr_type(&b.right, schema, tcx)`. With both
  arms returning `None` for `df["x"]`, D0081 cannot fire — every
  pandas TYPE-IS probe would be inconclusive (v1.1-style vacuity).
- The frame-walker `Expr::Subscript` arm at `expr.rs:222-253`
  publishes `SchemaView::Derived` only for all-string-literal LIST
  slices (`df[["a", "b"]]`) — irrelevant to scalar-dtype inference.

**Design fork chosen: fork (a)** — extend `infer_expr_type` with
an `Expr::Subscript` arm that mirrors how `col_reference` handles
`col("x")` (trust the shape; rely on the surrounding `schema`
context). Two alternatives, rejected:

- **fork (b)** — per-body `scalar_bindings: HashMap<Name, ColumnType>`
  on `BodyContext`, populated at `result = df["x"]` assignments,
  consulted by infer_expr_type's Name arm. Rejected: requires
  threading `&BodyContext` into `infer_expr_type` (it currently
  takes only `TypeCtx`), touches every infer_expr_type call site
  (~10), and adds a new side table for a single synth shape's
  benefit.
- **fork (c)** — extend `TypeCtx` with a name-to-SchemaView
  lookup. Rejected: `TypeCtx` is `#[derive(Copy)] { schemas,
  registry }` (verified at `context.rs:22-26`); adding a name table
  loses `Copy`, which then cascades to every signature that takes
  `TypeCtx<'a>`. Bigger refactor than the need warrants.

**Fix (PR-A in-scope, fork (a))**: extend
`column_exprs.rs::infer_expr_type` with an `Expr::Subscript` arm
positioned alongside the `col_reference` peel-off at L52. When
`s.value` is an `Expr::Name` AND `s.slice` is a single string
literal, treat the subscript as a column reference: call
`schema.field_type(slice_str, tcx.schemas)` — the same lookup
`col_reference` ultimately invokes. The Name's identity is NOT
verified (parallel to how `col("x")` doesn't verify `col`
resolves to `pyspark.sql.functions.col` — the shape is the
contract). Other receiver shapes (`Expr::Attribute`,
`Expr::Call`, `Expr::Subscript` nested) → arm returns `None` and
flow falls through to the existing branches.

**Lines touched** (PR-A diff surface):
- `crates/pykrete/src/operations/column_exprs.rs:46-242` —
  add `Expr::Subscript(s)` arm inside the existing `match expr`
  block (additive; no signature change). Sizing: ~10-15 LOC plus
  doc comment.

**Spark blast radius**: zero. Spark's canonical column-ref form
is `col("x")` (resolved by `col_reference`), not subscript. The
new arm fires only when an `Expr::Subscript` reaches
`infer_expr_type` — under the current Spark dispatch surface that
happens for the synth shape (pandas-tagged) and for any future
`spark_df["x"]` shape we'd want to recognize anyway (currently
no-op there too: spark_df's schema field lookup is correct
behavior whether we wanted it or not — it's the same `schema`
argument).

**Tests (≥3 in PR-A)**:
1. **Positive (vacuity-falsifying)**: `df.assign(__probe=df["price"] + 1)`
   on `PandasFrame[X]` with `price: Float64` → no D0081
   (arithmetic on numeric is valid). Confirms the arm fires AND
   returns a numeric type.
2. **Negative (vacuity-falsifying)**: same shape with `price:
   String` → D0081 fires (arithmetic on textual is invalid).
   Confirms the arm fires AND returns a type the family check
   rejects.
3. **Bound-respecting**: receiver is `Expr::Attribute` (e.g.,
   `df.assign(__probe=self.df["x"] + 1)`) → `infer_expr_type`
   returns `None` (arm doesn't match), no D0081 fires regardless
   of `x`'s dtype. Documents the v1.5+ extension surface
   (attribute receivers) without claiming it now.

PR-A's brief MUST include a paste-from-binary repro at PR-A-open
proving test 2 currently fails to fire D0081 on `main` (the bug

### Bug 1 — Registry-call §10 widening edge case

**Site**: `is_registry_function_call` gate in
`crates/pykrete/src/operations/expr.rs`. Surfaced as IMP-1 by the
v1.3 architecture auditor (TM-memory cite; not GH-filed because
bundled here).

**Symptom**: `util(df["typo"])` where `util` is registry-tracked
but has no `DataFrame[X]`-typed param silently passes. The bare
`df["typo"]` should fire D0030 (`pandas-support.md` §10), but the
registry-call gate short-circuits first.

**Fix — decision**: **always walk args; make `check_one_call_arg`
idempotent.** Alternative (tighten gate to require ≥1
`DataFrame[X]`-typed param) rejected — shifts silent-skip elsewhere.
Mirrors v1.3 piece (b): walk unconditionally, let per-arg checks
decide. v13-retro rule 8: grep stale comments on old gate.

**Tests**: ≥2 PROBE-EXPECTS — (1) positive `util(df["typo"])`
asserts D0030 fires on `"typo"`; (2) regression-guard
`util(df["valid_col"])` asserts no false-positive. Bug 1 doesn't
exercise bare-DataFrame D0090 paths, so PR-D-d0090 (#99) doesn't
need to land before PR-B.

### Bug 2 — `inherited_dialect` walks Named / walrus receivers (architecture FU-3, narrowed)

**Site**: `crates/pykrete/src/operations/driver.rs:114-130`
(`inherited_dialect` body). Surfaced as FU-3 by the v1.3
architecture auditor.

**Symptom**: `(pdf := build()).rename(...)` loses the
`PandasFrame[X]` tag because the walker only recognizes
`Expr::Name` and `Expr::Attribute`; walrus receivers fall through
to the Spark default.

**Fix**: extend the match to walk `Expr::Named` (walrus, recurse
into `named.value`). v13-retro rule 1: grep all
`inherited_dialect` sites.

**Out of scope for v1.4**: `df_list[0].merge(...)` — Subscript
receivers whose `.value` is a non-frame container
(`list[PandasFrame[X]]`-typed Name). Resolving this needs
container-element-type tracking v1.3's tracker doesn't provide;
deferred to v1.5+ (see §7 deferral list — wholly deferred, no
opportunistic extension). Round-3 wording allowed an
extend-if-found exception that contradicted §7; round-4 removes
it. Any frame-typed-Name-receiver Subscript shape the sweep
surfaces is filed as a v1.5+ follow-up issue, not absorbed into
PR-B.

**Test**: PROBE-EXPECTS for walrus; assert pandas dispatch fires
(e.g., D0030 on `.rename(columns={…})` typo).

### Bug 3 — `df.transform(helper)` dialect preservation

**Site**: `crates/pykrete/src/operations/expr.rs` —
`infer_transform_output` (~L1839); `child.bind_df(param_name,
input, None)` at ~L1859 passes `None` for dialect.
`handle_transform` (~L1783) computes `inherited_dialect` elsewhere
but doesn't thread it into the body-inference bind. Surfaced by
the v1.3 pandas-coverage auditor.

**Symptom**: pandas `.transform(helper)` drops `PandasFrame[X]` on
the helper param; helper sees `Dialect::Spark` default → pandas
dispatch misfires.

**Fix**: capture receiver dialect in `infer_transform_output` (via
`inherited_dialect` on the call OR re-resolve from param
annotation) and pass as third arg to `bind_df`, replacing `None`.
v13-retro rule 1: grep all `bind_df(` sites passing `None`.

**Sibling-callback sweep (in/out)**: callback surfaces are
`.transform`, `.apply`, `.applymap`/`.map`, `.agg(callable)`,
`.groupby().apply`, `.rolling().apply`, `.expanding().apply`,
`.pipe`. Bug 3 targets `.transform` (the only modeled one via
`handle_transform`). Sweep covers any other modeled callback in
`expr.rs`; unmodeled callbacks → v1.5+.

**Test**: PROBE-EXPECTS for `pdf.transform(helper)` where
`helper(p: PandasFrame[Schema])` does a pandas-only op; assert
pandas dispatch fires inside `helper`.

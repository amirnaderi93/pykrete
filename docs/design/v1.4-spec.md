## 1. Theme + headline

v1.4 is **depth on pandas**: match the PySpark donor breadth v1.0
established and close the type-tracking gap v1.3 deferred. The
v1.3.0 trust claim is "we check the pandas dispatched operations
end-to-end" — historically "six" (`df[col_list]`, `df[mask]`,
`df["new"] = expr`, `df.rename`, `df.drop(columns=…)`, `df.merge`)
**plus** `df.assign(new=expr, …)` which dispatches via the same
piece-(b) path as `df["new"] = expr` (verified at
`crates/pykrete/src/operations/expr.rs:947`). PR-E docs MUST grep
`crates/pykrete/src/operations/` for the live count (v13-rule 11).
The v1.4.0 trust claim is "we check pandas usage across the
dominant pandas stack — ML, stats, schema validation, data quality,
forecasting, visualization, financial/economic data — and we track
dtypes through those operations."

Target headline at tag time:

| Metric | v1.3.0 | v1.4.0 target |
|---|---|---|
| Donors in cross-codebase suite | 10 | 17 |
| Donors with pandas coverage | 3 | 10 |
| Total probes (RESOLVES + EXPECTS + TYPE-IS) | 149 | ~200+ |
| Pandas `PROBE-TYPE-IS` markers | 0 | ≥3 per new pandas donor (≥21 total) |

TYPE-IS target = 7 new donors × ≥3 = **≥21**, not ≥30: v1.3 pandas
donors (mlflow, feast, iceberg-python) stay at 0 in v1.4 because

## 3. PROBE-TYPE-IS extension design

Closes **pykrete-tests#14** AND extends the pykrete checker so the
extension actually fires. Two coupled deliverables shipped under
PR-A (see §8 hard-constraint).

### 3a. Recognizer extension (`pykrete-tests`)

**Current state**: `pykrete-tests:scripts/probes.py::_first_dataframe_param`
matches only `DataFrame[X]`. `PandasFrame[X]`-annotated params are
invisible to TYPE-IS, so today there are zero pandas TYPE-IS
probes (deliberate v1.3 deferral per `pandas-support.md` §11).

**Fix**: widen `_first_dataframe_param` to also match
`PandasFrame[X]` and `SparkFrame[X]` — name-set widening parallel
to v1.3 piece (a)'s `dataframe.rs::recognize` extension.
Implementation owns sizing.

### 3b. Synth shape (pandas TYPE-IS)

Spark wraps the col ref in `df.select(col("x") + lit(1))` → D0081
arithmetic checker (scalar: single col's dtype, not a frame
projection). **Decision**: for `PandasFrame[X]`, synth uses the
pandas-native scalar shape:

```
result = df["x"]        # Series-return (single brackets)
result + 1              # arithmetic — off-claim dtype falls through to D0081
```

Mirrors Spark's `col("x") + lit(1)` end-to-end. Spark synth
unchanged. Rationale: TYPE-IS asserts one col's dtype, not a frame
projection. `df[["x"]]` returns a single-col frame routing through
column-projection dispatch — wrong shape for a scalar marker;
multi-col shape is a future marker.

### 3c. `infer_expr_type` Subscript-on-PandasFrame arm (`pykrete` checker)

**BLOCKER caught at round 3 (adversarial lens against `main`)**:
the §3b synth was specified before walking the receiving code. On
current `main`, `result = df["x"]; result + 1` does NOT route to
D0081 because:

- `crates/pykrete/src/operations/expr.rs:222-253` — the
  `Expr::Subscript` arm publishes `SchemaView::Derived` only for
  all-string-literal LIST slices (`df[["a", "b"]]`). Scalar
  subscript returns `None`. The frame-level walker doesn't bind
  `result` to a typed Series.
- `crates/pykrete/src/operations/column_exprs.rs:46-216`
  (`infer_expr_type`) has NO `Expr::Subscript` arm at all. Even if
  the subscript were inspected at column-expr level, the function
  has no codepath to return a `ColumnType` for `df["x"]`.
- `crates/pykrete/src/operations/strict_operators.rs:124-134` — the
  D0081 dispatch calls `infer_expr_type(&b.left, …)` and
  `infer_expr_type(&b.right, …)`. With both arms returning `None`
  for the synth shape, D0081 cannot fire — every pandas TYPE-IS
  probe would be inconclusive (v1.1-style vacuity).

**Fix (PR-A in-scope)**: extend `column_exprs.rs::infer_expr_type`
with an `Expr::Subscript` arm. When the receiver `s.value` is an
`Expr::Name` resolving (via `tcx`) to a `PandasFrame[X]`-bound
slot AND `s.slice` is a single string literal, look up the column
in the bound schema and return its `ColumnType`. Receiver shapes
other than direct `Expr::Name` → return `None` (mirrors the v1.3
piece (b) bound at `expr.rs:237-244`). Sizing: ~20-30 LOC plus
tests. Spark `Expr::Subscript` is not used in the Spark dialect's
canonical column-ref form (`col("x")`), so this arm is a no-op for
Spark and doesn't widen Spark dispatch.

**Tests (≥3 in PR-A)**:
1. **Positive (vacuity-falsifying)**: `result = df["price"]; result + 1`
   on `PandasFrame[X]` with `price: Float64` → no D0081 (arithmetic
   on numeric is valid).
2. **Negative (vacuity-falsifying)**: same shape with `price: String`
   → D0081 fires (string + int is invalid).
3. **Bound-respecting**: receiver is `Expr::Attribute` (e.g.,
   `result = self.df["x"]`) → `infer_expr_type` returns `None`, the
   probe is correctly inconclusive rather than misfiring. Documents
   v1.5+ extension surface without claiming it now.

PR-A's brief MUST include a paste-from-binary repro at PR-A-open
proving test 1 currently passes silently on `main` AND test 2
currently fails to fire D0081 on `main` (the bug being fixed).

### Bug 1 — Registry-call §10 widening edge case

**Site**: `is_registry_function_call` gate in
`crates/pykrete/src/operations/expr.rs`. Surfaced as IMP-1 by the
v1.3 architecture auditor (TM-memory cite; not GH-filed because
bundled here).

**Symptom**: `util(df["typo"])` where `util` is registry-tracked
but has no `DataFrame[X]`-typed param silently passes. The bare
`df["typo"]` should fire D0030 (`pandas-support.md` §10), but the
registry-call gate short-circuits first.

**Fix — decision**: **always walk args; make `check_one_call_arg`
idempotent.** Alternative (tighten gate to require ≥1
`DataFrame[X]`-typed param) rejected — shifts silent-skip elsewhere.
Mirrors v1.3 piece (b): walk unconditionally, let per-arg checks
decide. v13-retro rule 8: grep stale comments on old gate.

**Tests**: ≥2 PROBE-EXPECTS — (1) positive `util(df["typo"])`
asserts D0030 fires on `"typo"`; (2) regression-guard
`util(df["valid_col"])` asserts no false-positive. Bug 1 doesn't
exercise bare-DataFrame D0090 paths, so PR-D-d0090 (#99) doesn't
need to land before PR-B.

### Bug 2 — `inherited_dialect` walks Named / walrus receivers (architecture FU-3, narrowed)

**Site**: `crates/pykrete/src/operations/driver.rs:114-130`
(`inherited_dialect` body). Surfaced as FU-3 by the v1.3
architecture auditor.

**Symptom**: `(pdf := build()).rename(...)` loses the
`PandasFrame[X]` tag because the walker only recognizes
`Expr::Name` and `Expr::Attribute`; walrus receivers fall through
to the Spark default.

**Fix**: extend the match to walk `Expr::Named` (walrus, recurse
into `named.value`). v13-retro rule 1: grep all
`inherited_dialect` sites.

**Out of scope for v1.4**: `df_list[0].merge(...)` — Subscript
receivers whose `.value` is a non-frame container
(`list[PandasFrame[X]]`-typed Name). Resolving this needs
container-element-type tracking v1.3's tracker doesn't provide;
deferred to v1.5+. If the grep-all-sites sweep finds a Subscript
case where `.value` resolves to a frame-typed Name (not a
container), the walker may extend to that narrow shape only.

**Test**: PROBE-EXPECTS for walrus; assert pandas dispatch fires
(e.g., D0030 on `.rename(columns={…})` typo).

### Bug 3 — `df.transform(helper)` dialect preservation

**Site**: `crates/pykrete/src/operations/expr.rs` —
`infer_transform_output` (~L1839); `child.bind_df(param_name,
input, None)` at ~L1859 passes `None` for dialect.
`handle_transform` (~L1783) computes `inherited_dialect` elsewhere
but doesn't thread it into the body-inference bind. Surfaced by
the v1.3 pandas-coverage auditor.

**Symptom**: pandas `.transform(helper)` drops `PandasFrame[X]` on
the helper param; helper sees `Dialect::Spark` default → pandas
dispatch misfires.

**Fix**: capture receiver dialect in `infer_transform_output` (via
`inherited_dialect` on the call OR re-resolve from param
annotation) and pass as third arg to `bind_df`, replacing `None`.
v13-retro rule 1: grep all `bind_df(` sites passing `None`.

**Sibling-callback sweep (in/out)**: callback surfaces are
`.transform`, `.apply`, `.applymap`/`.map`, `.agg(callable)`,
`.groupby().apply`, `.rolling().apply`, `.expanding().apply`,
`.pipe`. Bug 3 targets `.transform` (the only modeled one via
`handle_transform`). Sweep covers any other modeled callback in
`expr.rs`; unmodeled callbacks → v1.5+.

**Test**: PROBE-EXPECTS for `pdf.transform(helper)` where
`helper(p: PandasFrame[Schema])` does a pandas-only op; assert
pandas dispatch fires inside `helper`.

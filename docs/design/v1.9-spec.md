### 2.1 PR-A1 — three Rust audit-debt closures (cargo harness)

#### 2.1.1 `build.rs:176` panic-skip hole (arch-I1)

Today's `build.rs::extract_methods` at line 176 reads:

```rust
if !found_any && !region.contains('=') {
    panic!("build.rs: found `{GATE}` at byte offset {rel} but neither \
            `matches!(method, ...)` nor `method == \"...\"` followed. \
            Update build.rs's extract_methods OR adjust the new arm \
            shape ...");
}
```

The `region.contains('=')` skip-clause was a v1.8 PR-A1 guard
against the `let receiver_is_pandas_inherited = ...` binding line
itself triggering the panic. The clause is too loose: any future
arm shape containing an `=` anywhere in the predicate region
(e.g. `if receiver_is_pandas_inherited && let Some(kw) =
pandas_kwarg(...)`) silently skips the panic AND skips inventory
extraction. The new arm is invisible to the generator; the v17
guard test misses it.

**Fix**: tighten `region.contains('=')` →
`region.contains("let receiver_is_pandas_inherited")`. The
skip-clause now matches the exact binding line that motivated it,
nothing else.

**Negative-space tests MANDATORY per v14-rule 4**:

- Inject an arm shape with `let Some(kw) =` into a synthetic
  fixture (a `build.rs::tests` mod, or a `tests/` integration
  that round-trips a synthesized source). Assert the inventory
  either grows (if the pattern is valid) or panics (if invalid)
  — what we MUST NOT have is silent skip.
- Re-run on `main` post-fix: the existing pandas-inherited arms
  are picked up unchanged; the `let receiver_is_pandas_inherited`
  line still skips correctly.

**Closes v1.8 architecture audit finding arch-I1.**

#### 2.1.2 `operations/driver.rs:121-205` walker dedup (arch-I5)

The two walkers `inherited_dialect` (`driver.rs:121-160`) and
`inherited_is_deprecated_alias` (`driver.rs:174-205`) are near-
line-for-line copies. Both traverse `Name` / `Named` / `Call`-
with-`as_attribute_expr` / `Attribute` arms; both respect the
v1.5 `toPandas` / `createDataFrame` handoff flips; both return
early on the same opaque-receiver cases. The duplication is a
within-cycle drift class: any future handoff arm (e.g. v1.9 V1's
`# pykrete: ack-deprecation` marker mechanic, or a v1.10
`.to_polars()` arm) has to land in both walkers, or the
dialect tag and the deprecated-alias bit silently diverge for
the new arm.

**Fix**: refactor into a single walker returning
`(dialect: Option<Dialect>, deprecated_alias: bool)` tuple. The
two legacy callers project out their respective fields. The walk
happens once.

**Tripwire test**: same chain over a fixture set returns same
answers for both legacy callers. Concretely: a fixture pool of
chained expressions (`pdf`, `pdf.toPandas()`, `<X>.createDataFrame(...)`,
`pdf.filter(...).select(...)`, etc.) is fed to both walkers; the
test asserts `(dialect_a, alias_a) == (dialect_b, alias_b)` on
every fixture. If a future contributor touches the unified walker
and the projection diverges, the tripwire fires.

**Sibling-arm grep before declaring scope** (v15-rule 4 / v17
retro rule 4):

```
grep -rn 'inherited_dialect\|inherited_is_deprecated_alias' \
  crates/pykrete/src/ crates/pykrete/tests/
```

Current count on `f01645e`: implementer re-runs on their HEAD and
reports the delta in the PR body. Every caller must compile
unchanged post-refactor.

**Negative-space tests MANDATORY per v14-rule 4**:

- A chain that flips Spark → Pandas via `.toPandas()` reports
  `Dialect::Pandas` AND `alias=false` (handoff erases the
  originating bit). Existing v1.5 behavior preserved.
- A chain rooted in a `DataFrame[X]`-aliased Name reports the
  alias bit AND the binding's dialect tag (`Spark` for adjudicated
  Spark, etc).
- A chain rooted in an opaque receiver returns `(None, false)`.
- Both legacy callers receive the SAME answer on EVERY fixture.

**Closes v1.8 architecture audit finding arch-I5.**

### 2.2 PR-A2 — CHANGELOG grep gate v2 (bash harness)

**Design**: extend `scripts/changelog-grep.sh` to recognize a
new fenced label: `text-numeric`. Blocks marked `text-numeric`
contain a single number with a description (one line per claim).
For each entry, the script runs a known live-extract command and
compares.

**Block shape** (committee-spec'd):

```
\`\`\`text-numeric
253 probes
112 fixtures
1553 tests
\`\`\`
```

Each line is `<number> <claim-name>`. The script's known-claim

| Claim | Extract command |

| `tests` | `cargo test --release --workspace 2>&1 \| grep -oE '[0-9]+ passed' \| awk '{s+=$1} END {print s}'` |

**Unknown claim handling**: if a `text-numeric` block contains a

#### 3.1.3 Suggestion struct expansion

Today `cross_dialect_suggestion_*` returns `&'static str` — a bare
method name. v1.8 PR-D1's suggestions assume the user can swap
`withColumn` → `assign` mechanically, but the arg shape differs
(Spark's `(col_name, expr)` positional vs pandas's `assign(col=expr)`
kwarg). Bare-name suggestions in cases like
`withColumnRenamed` → `rename` are actively misleading because
Spark's `(old, new)` positional doesn't translate to pandas's
`rename(columns={old: new})` shape.

**Fix**: expand the return type to a struct:

```rust
pub struct CrossDialectSuggestion {
    pub name: &'static str,
    pub shape_changes: bool,
}
```

When `shape_changes` is true, D0091's message text appends `—
note arg shape differs`. Example mappings:

| Source | Target | `shape_changes` |
|---|---|---|
| `withColumn` | `assign` | `true` (positional → kwarg) |
| `withColumnRenamed` | `rename` | `true` (positional → `columns={}` kwarg) |
| `select` | `__getitem__` / `[]` | `true` (call → subscript) |
| `dropDuplicates` | `drop_duplicates` | `false` (rename only) |

Implementer fills in the full table during PR work; the committee
did NOT pre-commit beyond the four examples above.

**Why a struct, not a second `&'static str` for the suffix**: the
suffix would be a UI string; the boolean is a semantic property
of the suggestion (the shape DIFFERS, not "the shape is X").
Future v1.10+ candidates (auto-fix hints, multi-target
suggestions) extend the struct without breaking the API. The
struct shape is the API contract.

### 3.2 PR-D2 — D0091 bare-attribute path (NEW INFERENCE ARM)

v1.8 D0091 fires only on `Expr::Call` arms — method calls with
parens. Property accesses like `pdf.rdd` or `sdf.loc[...]` —
where the cross-dialect mismatch is on a bare attribute, not a
method invocation — silently typecheck. v1.8 spark-audit
finding spark-I1 surfaced this.

**Design**: add a new call site for `cross_dialect_mismatch`
inside the `Expr::Attribute` arm at
`crates/pykrete/src/operations/expr.rs:143`. The arm currently
handles class-qualified constants and column-access; it does
NOT call `cross_dialect_mismatch` today.

**New property tables** (in `dialect_signals.rs`):

```rust
pub const SPARK_DISCRIMINATOR_PROPERTIES: &[&str] =
    &["rdd", "isStreaming", "sparkSession"];

pub const PANDAS_INHERITED_PROPERTIES: &[&str] =
    &["loc", "iloc", "iat", "at"];
```

D0091 fires when an attribute access on a dialect-tagged receiver
names an attribute in the OTHER dialect's property table:
- `pdf.rdd` (Pandas receiver, Spark property) → D0091.
- `sdf.loc[0]` (Spark receiver, pandas property) → D0091.

**Suggestion mapping**: extends the struct from §3.1.3 to
properties. Property → property suggestion (no shape change for
properties, `shape_changes: false` by default; the
`SPARK_DISCRIMINATOR_PROPERTIES` → pandas mapping is the slim
case where `rdd` has no clean target so the entry goes to
`NO_SUGGESTION_ALLOWLIST`).

**Severity**: matches PR-D1's policy — warning by default, error
under strict mode. Both arms (`Expr::Call` from D1 and
`Expr::Attribute` from D2) share the strict-mode flip mechanism
so a future "promote D0091 from strict-only error to default
error" lands in one place.

## 4. Pillar V — `--deprecation-report` v2 envelope (1 PR: V1)

The cycle's user-facing addition. Atomic three-part:
`deprecationReportVersion` `"1"` → `"2"` + new `migration_status`
per-site field + new `--ack` filter flag + comment-marker
scanner. All four ship together because each alone is incoherent:
the envelope bump without the status field is API churn with no
new signal; the field without the marker mechanism has no
source-side opt-in; the marker without the filter has no CI
gating surface; the filter without the bump fails the schema
contract.

### 4.1 Schema bump: `deprecationReportVersion` `"1"` → `"2"`

v1.8 PR-V1 shipped `schema_version: 1` as the envelope contract.
v1.9 V1 bumps to `"2"` because the per-site shape gains a new
required field (`migration_status`). Consumers pinned to
`schema_version: 1` get explicit failure on the bump rather than
silently missing the new field.

### 4.2 New per-site field: `migration_status`

```json
{
  "schema_version": 2,
  "pykrete_version": "1.9.0",
  ...
  "sites": [
    {
      "path": "src/example.py",
      "line": 42,
      "column": 12,
      "raw_text": "DataFrame[Schema]",
      "rewrite": "SparkFrame[Schema]",
      "verdict": "spark",
      "migration_status": "pending"
    }
  ],
  ...
}
```

**Values**:
- `pending` (default) — alias still present in source, no ack
  marker. The site is "still to migrate."
- `acknowledged` — site has `# pykrete: ack-deprecation` comment
  marker on the line immediately above the `DataFrame[X]`
  annotation. Indicates human review without rewrite; the team
  has looked at this site, decided not to migrate yet (or to
  preserve the alias for back-compat with downstream consumers),
  and named the call out.
- `resolved` — for stateful delta tracking by external consumers.
  pykrete itself emits `pending` for every present site and
  `acknowledged` for every marker-tagged site; `resolved` is a
  consumer-side state ("this site was previously in the envelope,
  the alias was removed since the last report"). The pykrete
  binary never emits `resolved`. The value is reserved in the
  schema so consumers can adopt it as a sentinel without a
  future schema bump.

### 4.3 New `--ack` filter flag

```
pykrete check --deprecation-report --ack=acknowledged src/
pykrete check --deprecation-report --ack=pending src/
```

`--ack=acknowledged` filters the envelope's `sites` array to
sites where `migration_status == "acknowledged"`. `--ack=pending`
filters to `migration_status == "pending"`. Without `--ack`, all
sites emit (the v1.8 default).

**CI gating use case**: `--ack=pending | jq
'.summary.total_sites'` returns the un-acknowledged remainder.
The CI gate "all sites must be acknowledged-or-rewritten before
tag" reduces to: zero pending sites.

**Flag parse**: extends `parse_check_args` at
`crates/pykrete/src/main.rs::144-192` to recognize `--ack=<value>`
as a string flag taking `pending` / `acknowledged`. Unknown
values → exit 2.

**Invocation-only**: the flag rides the existing
`--deprecation-report` invocation-only dispatch at
`crates/pykrete/src/main.rs:261-272`. No new dispatch arm; same
exit-code 0 + JSON-to-stdout shape.

### 4.4 Comment-marker scanner: `# pykrete: ack-deprecation`

**Source-side opt-in**: a `# pykrete: ack-deprecation` comment on
the line immediately above the `DataFrame[X]` annotation marks
the site as `acknowledged`.

**Mechanic mirror**: same shape as v1.6's `# pykrete: ambiguous`
marker at `crates/pykrete/src/main.rs::inject_ambiguous_markers`.
v1.6 reads the marker; v1.9 V1 reads the marker AND surfaces it
through the envelope. The reading mechanism (line-above lookup,
whitespace-tolerant comment match) is identical.

**Why "above the annotation," not "on the same line"**: annotations
are often multi-line (`DataFrame[\nLongSchemaName\n]`). A
line-above placement is unambiguous; an inline-comment placement
breaks formatter conventions. Mirroring v1.6's `ambiguous`
marker keeps the user experience consistent.

**Marker MUST NOT alter check behavior** outside of envelope
classification. A site marked `acknowledged` STILL emits D0090
in `pykrete check` text output (with full message). The marker
is a planning instrument, not a suppression mechanism — if a team
wants to suppress D0090, the alias gets rewritten. Marker-as-
suppress is a v1.10+ candidate gated on user signal.

### 4.5 CRITICAL CARVE-OUT — no date marker

Per v1.8 §10.5 (reaffirmed at v1.9 committee r2): **NO
`target_version` field. NO calendar quarter. NO date marker.**
The envelope contains no ship-date commitment. The trust-claim
leverage is "pykrete tracks migration progress site-by-site
without committing to a ship date." That's not a hedge; that's a
product-fork respect. The user owns the ship-date decision; the
envelope is the planning instrument.

This carve-out is load-bearing for the v1.9 trust claim. If V1
ships with a `target_version` field, the trust claim collapses

## 9. Standing constraints

### 9.1 Three-part versions only

Per `feedback_three_part_versions` TM memory. v1.9 releases are
`1.9.0`, `1.9.1`, `1.9.2` etc. — never `1.9.0.N`. Hotfixes take
the next Z and renumber the backlog.

### 9.2 Extension version-bump strategy — **CENTRALIZED IN PR-F (v1.9 cycle trial, load-bearing amendment)**

**§9.2 amendment (v1.9 cycle trial)**: per-PR
`editors/vscode/package.json` bumps are **SUSPENDED** for the
v1.9 cycle. PR-F handles all version bumps at cycle close
(workspace `Cargo.toml` `1.8.x` → `1.9.0` AND
`editors/vscode/package.json` + `package-lock.json` `0.6.x` →
`0.7.0`). Per-PR developers do NOT bump versions; the "extension
version guard" CI check enforces this by requiring exactly one
bump per cycle, at PR-F.

**Rationale**: v1.7 and v1.8 each had 4+ rebase rounds caused by
per-PR bump collisions when parallel PRs all targeted the same
patch number. PR-A1 grabs `0.6.1`; PR-A2 lands on `main` first
and grabs `0.6.1`; PR-A1 rebases to `0.6.2`; PR-D1 lands; PR-A1
rebases to `0.6.3`. The rebase ladder eats developer time and
churns commit history without buying anything. Centralizing
eliminates the ladder structurally.

**What "extension version guard" CI check means**: a new CI step
(or amend an existing version-check step) asserts that the
diff against the cycle baseline (`f01645e` for v1.9) contains
EITHER zero version bumps (every non-PR-F PR) OR exactly one
bump (PR-F itself). The check has two modes — the recognition
mechanic is a label or a `// PR-F: cycle bump` marker on the
commit, OR a path-based heuristic (only PR-F touches both
`editors/vscode/package.json` AND `crates/pykrete/Cargo.toml`
together). Implementer picks; the committee did NOT mandate.
What the check MUST catch: a non-PR-F PR landing a version bump.

**Revert path**: if the trial surfaces failure modes — PR-F dev
forgets the bump (the release ships at an unbumped version);
centralized bump confuses contributors who reach for the patch
slot reflexively; the CI guard misfires on legitimate edits to
`package.json` (e.g. dependency upgrades) — v1.10 §9.2 reverts to
per-PR bumps. Document the failure mode in the v1.9
retrospective.

**v1.8-era practice (now SUSPENDED for v1.9)**: every PR that
touches `crates/pykrete{,-lsp}/**` bumps
`editors/vscode/package.json` by patch; cycle-close PR (PR-F)
bumps the minor; PR-S1 does not bump. v1.9 SUSPENDS this. v1.10
either restores it OR makes the centralized model permanent
based on the trial outcome.

**Standing CONTRIBUTING note**: S R2 contribution adds a
"Version bumps (v1.9+)" sub-section to `CONTRIBUTING.md` under
the existing "Workflow" section naming the centralized PR-F
pattern with a one-liner so a new contributor reading
CONTRIBUTING in 2026-Q3 doesn't wire up the suspended per-PR
mechanic.

## 12. v2.0 throughline

v1.9 advances the v2.0 narrative by making the deprecation runway
**plannable** without committing to a ship date:

- **v2.0 migration is plannable — track progress site-by-site,
  gate on `acknowledged` or `resolved`.** v1.8 made migration
  measurable (the JSON envelope). v1.9 makes it plannable: the
  `--ack` filter lets a team declare a site human-reviewed-but-
  not-yet-rewritten, and CI gates on the un-acknowledged
  remainder. Migration becomes a tracked state machine per site,
  not a count. **No date marker** — per v1.8 §10.5 and v1.9 §4.5
  the ship-date is a product fork the user owns. The envelope is
  the planning instrument; the calendar is the user's call.
- **D0091 matures.** Strict-mode escalation makes
  `pdf.withColumn(...)` an error in strict-mode CI, matching the
  v1.6 D0090 pattern. The bare-attribute arm (`pdf.rdd`,
  `sdf.loc`) closes the silent-typecheck gap on property
  accesses. The suggestion struct expansion surfaces "arg shape
  differs" so users converting `withColumn` → `assign` understand
  the rewrite is not mechanical. The suggestion-drift tripwire
  guards against future degradation. All four close the v1.8
  D0091 audit-debt class.
- **Audit-debt mop-up.** Three Rust closures (build.rs gate hole,
  driver.rs walker dedup, v17 guard test line-number drift) plus
  the bash-side grep gate v2 close v1.8 architecture findings
  arch-I1 / I5 / N1 and v1.8 retro rule 7. v2.0's release ships
  cleaner because v1.9's cycle scaffolding catches drift earlier
  AND on more axes (numeric-claim drift was uncatchable in v1.8;
  v1.9's `text-numeric` block makes it structural).
- **Centralized version bump trial.** v1.7 and v1.8 each spent 4+
  rebase rounds on per-PR version-bump collisions. v1.9 trials a
  centralized bump in PR-F; v1.10 keeps or reverts based on
  outcome. If the trial succeeds, the next two major cycles save
  ~8+ rebase rounds — visible developer-time savings that
  compound toward v2.0.

The release-notes trust-claim sentence — **"v2.0 migration is
plannable — track progress site-by-site, gate on `acknowledged`
or `resolved`"** — surfaces on splash + roadmap. The intent: v2.0
moves from "measurable" (v1.8) to "plannable" (v1.9) without
committing to a date. The calendar stays with the user; the
instrument keeps maturing. PR-F copy lands this framing in
README + CHANGELOG + roadmap.

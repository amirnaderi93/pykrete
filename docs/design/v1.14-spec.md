### 1.i — `--compare-to` SIMPLE output shape (forward-binding amendment)

**User signoff 2026-06-22**: Option A (SIMPLE diff-only). The
5-cycle defer pattern that closed via §12 in v1.13-spec lands its
implementation contract here.

#### 1.i.1 JSON output shape

```json
{
  "snapshot_a": {"sha": "<git-sha>", "timestamp": "<iso8601>"},
  "snapshot_b": {"sha": "<git-sha>", "timestamp": "<iso8601>"},
  "diff": {
    "added":     [<full Site payload>],
    "removed":   [<full Site payload>],
    "unchanged": [<full Site payload>]
  }
}
```

- **`unchanged` payload**: FULL site payload (not just `SiteId`).
  Self-contained snapshot semantics — a consumer reading only the
  diff document has every field of every still-present site
  without needing to re-read either snapshot.
- **`status_changed` handling**: NO separate bucket. The binary
  `MigrationStatus` per `crates/pykrete/src/alias_report.rs:45-48`
  (`Pending` / `Acknowledged`) surfaces transitions as
  remove-from-old-bucket + add-to-new-bucket. A site that flipped
  from `Pending` to `Acknowledged` appears in both `removed`
  (with the old `Pending` payload) AND `added` (with the new
  `Acknowledged` payload). This keeps the diff arithmetic
  symmetric without inventing a third status taxonomy in the
  output schema.
- **Exit code**: nonzero when `added.length > 0` (regression
  signal — new pending or acknowledged sites have appeared since
  the prior snapshot). Plain `removed` + `unchanged` deltas do
  NOT trip the exit code (resolved migrations and steady state
  are both healthy). Mirrors the `--strict-mode` precedent of
  nonzero-on-regression.
- **Document structure**: single JSON document; `snapshot_a` /
  `snapshot_b` envelope at the top + `diff` body. The envelope
  carries provenance (git sha + timestamp) so a consumer reading
  a saved diff document can re-derive which two snapshots
  produced it.
- **Keying**: Option A from v1.13 spec §12 = `SiteId = (file,
  line)`. Already settled at v1.13 spec time; binding here.
  Fragile to formatting changes that shift line numbers — this is
  the accepted tradeoff for shipping the consumer surface in
  v1.14 instead of deferring another cycle on a more elaborate
  keying scheme.

#### 1.i.2 Why SIMPLE and not RICH

Two alternatives were tabled at user-signoff time:

- **SIMPLE (Option A, picked)**: three buckets (added / removed /
  unchanged) with full payloads. Single document. ~150 LoC ship.
- **RICH (rejected)**: per-status buckets (added_pending /
  added_acknowledged / removed_pending / removed_acknowledged /
  status_changed / unchanged) with payload deltas. ~400 LoC ship
  + spec churn on how to represent a payload delta.

The 5-cycle defer pattern was paying for design ambiguity. SIMPLE
ships the contract; RICH can extend it additively in v1.15+ if a
consumer needs finer-grained transitions. The binary
`MigrationStatus` enum (only two values) makes the
remove-from-old + add-to-new pattern unambiguous.

#### 1.i.3 CLI shape

```bash
pykrete check --deprecation-report --compare-to <prior>.json > current_diff.json
```

`--compare-to` takes a path to a previously-emitted
`--deprecation-report` JSON snapshot. The current invocation
emits the diff document defined in §1.i.1 instead of the v1.9 v2
envelope. `--compare-to` is mutually exclusive with `--ack=<val>`
filtering on the same invocation; the diff operates on the full
unfiltered envelope (filtering on a diff is a v1.15+ extension).

#### 1.i.4 Where this binds

`crates/pykrete/src/alias_report.rs:35-48` `MigrationStatus`
remains binary. `crates/pykrete/src/bin/pykrete.rs` (or wherever
`check --deprecation-report` is dispatched in the v1.14
post-rebase tree) adds the `--compare-to <path>` argument and the
diff-emit code path. Schema for the diff document lives next to
`MigrationStatus`. The pykrete binary remains stateless across
invocations per v1.13 spec §12: it accepts a snapshot as input
and emits a diff as output; it does NOT track state on disk.

### 1.ii — Constructor arms recognizer table for `inherited_chain_state` (forward-binding amendment)

`crates/pykrete/src/operations/driver.rs:184-228`. The unified
chain walker descends `Expr::Call → Expr::Attribute → Expr::Name`
recursively until it hits a `Name` (which yields the bound
dialect) or an opaque receiver (which yields `(None, false)`).
The v1.13 PR-D1 dialect-on-return arm catches mismatches where
the body's chain bottoms out at a tagged Name (e.g., `pdf` ->
`.toPandas()` chain handoffs flip the inherited dialect mid-walk).
What it does NOT catch is the bare constructor case:
`spark.read.parquet(...)` and `pd.DataFrame(...)` bottom out at a
literal name (`spark` / `pd`) that pykrete does not have a frame
binding for. v1.14 PR-D2 adds three structural recognizer arms.

#### 1.ii.1 Arms in priority order

| Pattern | Match shape | Returns |
|---|---|---|
| `pd.DataFrame(...)` | `Call(func=Attribute(value=Name("pd"), attr="DataFrame"), ...)` | `(Some(Dialect::Pandas), false)` |
| `spark.read.<format>(...)` | `Call(func=Attribute(value=Attribute(value=Name("spark"), attr="read"), attr=<format>), ...)` — two-level structural | `(Some(Dialect::Spark), false)` |
| `spark.createDataFrame(rows, schema=Schema)` | already handled at line 208 — verify-only | (existing) |

The first two arms slot into the `Expr::Call` branch of
`inherited_chain_state` ahead of the existing `cursor =
&attr.value` recursion. Match order: existing `createDataFrame`
gate (line 208) first; then existing `toPandas` gate (line 216);
then the two new constructor arms; then the existing fall-through
recursion. Priority matters because all five arms structurally
overlap on `Call(func=Attribute(...), ...)` — the more specific
patterns must short-circuit first.

#### 1.ii.2 Literal-name guards

`Name("pd")` and `Name("spark")` are HEURISTIC literal-name
matches, NOT bindings looked up in the symbol table. This is the
deliberate analog to v1.6's structural-match rules for
`pivot_table` and v1.10's structural rules for `stack` /
`unstack`: pykrete checks the user's annotation against the
canonical name the user typed, not against a generalized binding
resolver. Aliased imports (`import pyspark.sql as sp; sp.read...`)
will fall through the heuristic and bottom out at `(None,
false)` — same behavior as the v1.13 baseline. Adopters using
non-canonical aliases for their root frame imports are out of
scope for the v1.14 arm; documented as a known limitation.

#### 1.ii.3 Why no symbol-table resolution

Adding symbol-table resolution for `pd` / `spark` would require
tracking import bindings across modules, which would push v1.14
out of the depth-not-breadth budget. The structural heuristic
catches the ~80% adopter shape that uses `import pandas as pd`
and `from pyspark.sql import SparkSession; spark = ...` by
convention. The remaining ~20% of adopters with custom aliases
get the same silent-pass behavior as today; v1.15+ can extend if
adopter feedback surfaces the limitation.

**Coverage estimate**: D0080 dialect-on-return goes from ~80%
adopter shape coverage (v1.13 handoffs only) to ~95% adopter
shape coverage (handoffs + canonical-name constructor sites).

### 1.iii — `groupby.agg` narrow-arm plumbing list (forward-binding amendment)

`SchemaView::Grouped` at `crates/pykrete/src/schema.rs:586-599`.
Current state of the world (verified against `main` at v1.13.0):

- Pandas `.groupby(...)` ALREADY produces `SchemaView::Grouped`
  via the dialect-agnostic recognizer at
  `crates/pykrete/src/operations/strict_operators.rs:538-560`.
- `handle_agg` at `crates/pykrete/src/operations/expr.rs:2775-2849`
  destructures `Grouped` (Spark-side single-aggfunc Derived
  synthesis is the existing arm).
- The helpers `classify_pivot_table_aggfunc` /
  `pivot_table_aggfunc_result_override` /
  `synthesize_pivot_result_from_aggfunc` at
  `crates/pykrete/src/operations/expr.rs:624` / `:659` / `:687`
  (settled at v1.13 PR-D2) are reusable from the v1.13
  consumer-of-classifier work. The aggregate-to-dtype table from
  v1.13 spec §5.1.1 is the canonical reference per the v1.13 §13
  forward-binding convention.

#### 1.iii.1 Required plumbing

**(i) Add `Dialect` field on `SchemaView::Grouped`.** The variant
becomes:

```
Grouped {
    keys: Vec<&'a str>,
    underlying: Box<SchemaView<'a>>,
    after_pivot: bool,
    dialect: Dialect,
}
```

Default `Dialect::Spark` for backward-compat with all existing
construction sites (the v1.0 `.groupBy` arm); the new pandas
construction site at `strict_operators.rs:538` sets the field to
the receiver's dialect at variant build time. Reviewer audits
every variant construction to ensure the dialect is set
correctly; missed-default sites would silently classify pandas
groupings as Spark and route through the wrong dispatch arm.

**(ii) Consumer pattern-match update list.** Every match on
`SchemaView::Grouped` variant in the listed files MUST be updated
to bind the new `dialect` field (or `_`-discard with a comment if
the consumer is dialect-agnostic):

- `crates/pykrete/src/operations/expr.rs` — `handle_agg` plus
  sibling consumers. Grep:
  `grep -rn 'SchemaView::Grouped' crates/pykrete/src/`.
- `crates/pykrete/src/operations/strict_operators.rs` — the
  construction site at 538-560 AND any other variant
  match-arm.
- Tests using `SchemaView::Grouped` in fixtures or assertions.

Reviewer enumerates per-file per-symbol counts on the PR-D1 R1
diff to verify zero missed match arms.

**(iii) `handle_agg` single-string-aggfunc arm shape**:

1. Detect the single-string-aggfunc argument via
   `classify_pivot_table_aggfunc` reuse (the v1.13 PR-D2
   classifier's allowlist is the canonical reference). When the
   classifier returns `Some(<aggfunc>)` AND the receiver dialect
   is `Dialect::Pandas`, the new arm fires.
2. Enumerate non-key columns from `underlying`. The synthesized
   field list is `keys ++ underlying.field_names() \ keys`
   (every column from the underlying schema except the
   grouping keys, with the keys prepended in their original
   order).
3. Apply the aggregate-to-dtype override table per v1.13 §5.1.1:
   `count`/`nunique` → int64; `mean`/`std`/`var`/`median` →
   float64; `sum`/`min`/`max`/`first`/`last` → preserve receiver
   type. Helper
   `pivot_table_aggfunc_result_override` already encodes this
   table; PR-D1 reuses it without copy-paste.
4. Output synthesized `Derived { fields: keys ++
   value_columns_with_override }`.

When the classifier returns `None` (fall-through: callable,
non-literal, dict, mixed list) OR the receiver dialect is
`Dialect::Spark`, the existing v1.0 Spark-side arm path is
preserved unchanged.

**(iv) Spark-side regression test plan.** Per v1.13 retro rule on
sibling-arm regression risk: PR-D1 author documents current
`pdf.groupby("k").agg("sum")` behavior on the HEAD-before-PR
state (likely silent-empty Derived per the v1.13 PR-P1 R2 §1.1.4
finding), AND proves the AFTER-state does not regress Spark
`.groupBy(col).agg(F.sum("x"))` paths. Include 3+ Spark-side
regression tests:

- `sdf.groupBy("k").agg(F.sum("x"))` → existing Spark behavior.
- `sdf.groupBy("k", "k2").agg(F.count("*"))` → multi-key Spark.
- `sdf.groupBy("k").pivot("p").agg(F.sum("x"))` → existing
  `after_pivot=true` path.

#### 1.iii.2 In-scope for v1.14

- Single-string-aggfunc on the v1.13 PR-D2 allowlist (`"count"`,
  `"sum"`, `"mean"`, `"std"`, `"var"`, `"median"`, `"min"`,
  `"max"`, `"first"`, `"last"`, `"nunique"`).
- Single-string-key: `pdf.groupby("k").agg(...)`.
- List-of-string-keys: `pdf.groupby(["k1", "k2"]).agg(...)`.

#### 1.iii.3 Out-of-scope — deferred to v1.15+

- `dict`-aggfunc: `pdf.groupby("k").agg({"x": "sum", "y":
  "mean"})` (per-column aggfunc; result schema is column-
  pattern-driven).
- `callable`-aggfunc: `pdf.groupby("k").agg(np.sum)` (falls
  through to Unknown).
- `list`-of-aggfunc: `pdf.groupby("k").agg(["sum", "mean"])`
  (MultiIndex-on-columns shape, same v1.13 PR-D2 carve-out).
- `as_index=False` kwarg (changes result shape: keys become
  columns instead of index).
- `observed=` kwarg (affects categorical-key handling).
- `dropna=` kwarg (affects NaN-key handling).
- Named-aggregation kwargs: `pdf.groupby("k").agg(total=("x",
  "sum"))` (pandas 0.25+ named-agg syntax).

The same v1.13 PR-D2 cohort gate applies: list-of-aggregates and
named-aggregation both produce MultiIndex-on-columns shapes the
pykrete schema lattice doesn't model. v1.15+ can ship a
MultiIndex-column extension as a separate atomic PR.

#### 1.iii.4 Why dialect-discriminated dispatch on `Grouped`

The v1.0 Spark `.groupBy` arm produces `Grouped` with implicit-
Spark semantics. v1.4's pandas `.groupby` recognizer also
produces `Grouped`, but its `.agg` semantics differ: Spark's
`.agg(F.sum("x"))` consumes Column expressions while pandas's
`.agg("sum")` / `.agg(np.sum)` consume aggfunc literals or
callables. The two dispatch arms in `handle_agg` would silently
crosstalk if `Grouped` weren't dialect-tagged: a pandas
`.groupby` followed by a Spark-shape `.agg(F.sum(...))` (or vice
versa) would otherwise resolve through whichever arm fired
first.

Tagging `Grouped` with the receiver dialect at construction time
matches the v1.5 PR-A1 `inherited_dialect` discipline — every
intermediate frame-shaped value carries its dialect so dispatch
is deterministic.

## 14. Marker file mechanism (§11.2 cross-reference)

**This PR (PR-S1) commits `.github/centralized-bump-cycle.marker`
with the content `v1.14`.** The marker's presence on the branch
is the version-guard suspension mechanism: the
`extension-version-guard.yml` workflow honors the marker,
allowing Wave 1 PRs (A1, A2, D1, D2, D3, V1) to skip the
extension-version check. PR-F then bumps the version in one
place at cycle close.

**Lifecycle** (unchanged from v1.10 / v1.11 / v1.12 / v1.13):

1. Cycle N PR-S1 commits the marker with content `vN`.
2. Wave 1 PRs branch off S1, inherit the marker.
3. extension-version-guard CI honors the marker, skips the
   per-PR version-bump check.
4. PR-F bumps the version centrally.
5. PR-F (or the cycle's final cleanup PR) DELETES the marker
   in preparation for the next cycle's PR-S1 to re-add it.

The marker's content (`v1.14`) is a per-cycle stamp; the
workflow reads it for the cycle name. The presence of the file
is the gate; the content is informational.

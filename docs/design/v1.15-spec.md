### 1.i — §9.2 promote-to-default (drop marker file mechanism) (forward-binding amendment)

Per v1.14 architecture-auditor recommendation +
`project_v24_retrospective` rule 12. After 6 consecutive cycles
(v1.9 trial → v1.10 promoted-to-standing → v1.11 → v1.12 → v1.13
→ v1.14) of zero collisions on the centralized-bump path, the
`.github/centralized-bump-cycle.marker` mechanism has paid for
itself in operational coverage and now adds no signal. v1.15
drops it.

#### 1.i.1 What this changes

- **PR-S1 does NOT create the marker.** This is the FIRST cycle
  since v1.9 without a marker file at PR-S1 time. Per §14 below
  the §14 marker-mechanism section is removed wholesale (no
  cross-reference left in the spec).
- **PR-F does NOT delete a marker** (none exists). The PR-F
  routine simplifies: bump workspace `Cargo.toml` +
  `editors/vscode/package.json` + `package-lock.json` in one
  commit, no marker-removal step.
- **`.github/workflows/extension-version-guard.yml:86-101`** —
  PR-F removes the marker-related conditional block (the
  `if [ -f ".github/centralized-bump-cycle.marker" ]; then ...
  fi` block at lines 95-101 plus the comment preamble at lines
  82-94). The guard reverts to its pre-v1.9 shape: per-PR
  extension-version check unconditional, no marker bypass.

#### 1.i.2 Why now

- 6 cycles of zero collisions (v1.9 → v1.14). The mechanism's
  failure mode (PR-F forgets to delete the marker; next cycle's
  PR-S1 forgets to recreate it; the per-PR guard's bypass
  persists across cycle boundaries silently) has never fired.
- The 4-of-6 "PR-F forgot to delete the marker" pattern from
  v1.11 retro is mooted: there's nothing to forget.
- The "PR-S1 marker file resolved-at-S1-time" rule (v1.11 retro)
  is mooted: no marker = nothing to resolve.
- Mechanism cost: 6 lines of shell + 3 lines of marker file +
  CONTRIBUTING.md callout + per-cycle author awareness. Annual
  cost (12 cycles) at ~2 cycles/month adds up to non-trivial
  process overhead with zero observed payoff.

#### 1.i.3 Re-instate path if a collision occurs in v1.15+

If a Wave 1 PR in v1.15-or-later attempts a version bump and
the workflow blocks it AND the cycle's spec didn't anticipate the
extension-impacting change, the cycle's PR-F dev re-instates the
marker mechanism in a follow-up PR. v1.15-or-later cycle's
PR-S1 then recreates the marker per the v1.9 → v1.14 protocol.
The drop is reversible; the spec edit at §1.i.1 above is the
single source of truth for which mode the workflow is in.

##### 1.i.3 recovery-taken (post-PR-F amendment, v1.15)

**Recovery WAS taken in v1.15.** During the v1.15 PR-F sequencing,
the workflow-edit ordering interleaved badly with the centralized
bump path: removing the marker block from
`.github/workflows/extension-version-guard.yml` in the same PR as
the centralized version-bump caused the per-PR extension-version
check to fire on PR-F's own diff before the bump completed,
blocking PR-F. The marker mechanism was kept in place for the
v1.15.0 tag and the §9.2 promote-to-default chore re-scoped to
**a cycle-0 chore in v1.16 that lands BEFORE PR-S1** — the
workflow-edit + marker removal sequence ships as a standalone PR
on a clean v1.16-cycle-0 branch, with no concurrent version bump,
no concurrent Wave 1 PR, and the v1.16 spec then references the
post-removal workflow shape as the binding spec.

The lesson: **structural workflow edits to release-machinery
files must NOT interleave with the release PR that triggers
those workflows.** This is now a standing-rule candidate for the
v1.15 retrospective; v1.16 PR-S1 §1 codifies the cycle-0
sequencing as a forward-binding amendment.

The marker file persists in tree as of v1.15.0; the §9.2
promote-to-default work is deferred whole-cloth to v1.16
cycle-0.

#### 1.i.4 Why drop (rather than rename / parameterize)

Three alternatives were considered at committee r2:
- **Drop entirely (picked, §1.i.1)**: simplest. 6 cycles of zero
  collisions justifies the mechanism's removal.
- **Rename to `.github/v15-cycle-marker.txt` and keep**: cosmetic;
  doesn't reduce the per-cycle author awareness cost.
- **Parameterize via env var**: workflow becomes harder to audit;
  the marker file's grep-ability ("does this file exist on
  branch X?") was its main affordance.

The drop is the cheapest path to recovering the mechanism's
operational cost. v1.15-or-later cycles that need bypass machinery
can revisit at their own spec time.

#### 1.i.5 Where this binds

`.github/workflows/extension-version-guard.yml:82-101` — PR-F
removes the marker block. PR-S1 does NOT create the marker file.
PR-F documents the removal in the CONTRIBUTING.md release-cycle
section (drop the marker callout; the per-PR version-bump check
is unconditional again).

#### 1.i.6 Severity check

S1 is a docs-only PR (this spec). PR-F is the load-bearing PR
for §1.i (removes the workflow block + CONTRIBUTING.md update).
No D-code changes. No catalog-pin cascade. Behavioral delta:
none (no v1.15 Wave 1 PR is extension-impacting per the §15
matrix). The drop is a process change with no observable
adopter-facing effect.

### 1.iii — `reset_index(drop=True)` + `set_index([<literal-keys>])` plumbing list (forward-binding amendment)

`crates/pykrete/src/operations/expr.rs:3364-3365` —
`reset_index` and `set_index` are currently in
`NO_SUGGESTION_ALLOWLIST_PANDAS` (D0091 doesn't fire on them on
SparkFrame receivers). They have NO schema-tracking semantics
today: a pandas chain that calls `.reset_index(...)` or
`.set_index(...)` produces `Unknown`, breaking downstream column-
ref checks. v1.15 PR-D2 adds two narrow recognizer arms that
keep the chain Derived-tracked across the index boundary.

#### 1.iii.1 In-scope for v1.15

| Pattern | Match shape | Result schema |
|---|---|---|
| `pdf.reset_index(drop=True)` | `Call(func=Attribute(attr="reset_index"), keywords=[("drop", True)])` | receiver columns minus any synthesized index column (the `Grouped` carve-out from §1.iii.2 below applies here at the chain boundary) |
| `pdf.set_index([<literal-keys>...])` | `Call(func=Attribute(attr="set_index"), args=[List(elts=[<all string-literal>...])])` | receiver columns minus literal-key columns (literal keys move to index, no longer column-accessible) |
| `pdf.set_index("<literal-key>")` | `Call(func=Attribute(attr="set_index"), args=[Str("<key>")])` | receiver columns minus the literal key column |

**Why "drop=True only" for reset_index**: `drop=False` (the
default) preserves the index AS a new column. The new column's
name comes from the prior `set_index` call's argument OR from the
`groupby` keys OR from the default index name (`"index"`).
Today no `groupby` / `set_index` arm tracks which column was
moved to index, so the synthesized name isn't reachable. v1.15
narrowly handles `drop=True` because it's the only form where
the result schema is fully derivable from the receiver columns
alone — no index-state tracking needed.

**Why literal-key only for set_index**: non-literal expressions
(`pdf.set_index(get_key())`) would require expr-eval on the
argument before we can compute which columns to remove from the
result. v1.15 doesn't ship expr-eval; the literal-list / literal-
string arm is what's safe to ship now.

**The `Grouped` carve-out at the chain boundary**: per
`crates/pykrete/src/schema.rs:587-608` the `Grouped` variant
synthesizes an "index column" implicitly post-pivot/groupby.agg.
`reset_index(drop=True)` on a `Grouped`-result receiver unsets
this carve-out (the `Derived` shape after the reset has the
group-keys as plain columns, NOT as a synthetic index). The arm
recognizes the receiver's `SchemaView` variant and dispatches:
`Derived` → identity-with-renames; `Grouped`-result → strip
index carve-out; `Unknown` → fall through (no inference).

#### 1.iii.2 Required plumbing

**(i) Recognizer arm placement.** The two arms slot into
`handle_call` (or the closest equivalent in the v1.15 post-rebase
tree) in priority order:
1. `reset_index(drop=True)` literal-True kwarg match.
2. `reset_index(drop=False)` literal-False kwarg match → fall
   through (out-of-scope).
3. `reset_index()` no-kwargs (default `drop=False`) → fall
   through (out-of-scope).
4. `set_index([<literal-string-list>])` literal-list match.
5. `set_index("<literal-string>")` literal-string match.
6. `set_index(<non-literal>)` → fall through (out-of-scope).

Implementer picks the file location (`expr.rs` likely, alongside
the existing `handle_agg` and `handle_pivot_table` arms) and
helper naming.

**(ii) Receiver-shape dispatch.** For both arms:
- `SchemaView::Derived(fields)`: synthesize new `Derived` with
  the filtered field list (for `set_index`: minus the literal
  keys; for `reset_index(drop=True)`: unchanged column set, the
  drop=True semantics affect index not columns).
- `SchemaView::Declared(schema)`: same as Derived; project the
  schema's column set first.
- `SchemaView::Grouped { keys, underlying, after_pivot,
  dialect }` (the chain-boundary case): for
  `reset_index(drop=True)`, synthesize `Derived` with `keys ++
  underlying.field_names() \ keys` (canonical post-groupby.agg
  shape; same as v1.14 PR-D2's synthesizer output).
  `set_index` on a Grouped receiver isn't a real pandas pattern
  (you'd usually go through `.agg().set_index()` which is
  Derived by then); fall through to Unknown.

**(iii) `NO_SUGGESTION_ALLOWLIST_PANDAS` interaction.** The two
arms fire on a PandasFrame receiver and produce a Derived
schema. The existing entries at
`crates/pykrete/src/operations/expr.rs:3364-3365` stay (D0091 on
SparkFrame receivers continues to fall through silently); the
v1.15 arms ADD schema inference for PandasFrame receivers, they
don't change the D0091 suggestion behavior.

**(iv) Helper consolidation.** Per PR-D1's
`resolve_override_ty` primitive extraction (committee-settled),
PR-D2 reuses the consolidated primitive at any synthesizer call
site rather than copy-pasting. Sequencing: PR-D1 lands FIRST;
PR-D2 builds on the consolidated helper.

#### 1.iii.3 Out-of-scope — deferred to v1.16+

- **`reset_index(drop=False)`** — preserves index AS new column.
  Requires stateful tracking of which column went to index;
  today no `groupby` / `set_index` arm tracks this. v1.16
  candidate paired with a `set_index`-state extension on
  `SchemaView`.
- **`set_index(<expr>)` non-literal** — requires expr-eval for
  column-set membership.
- **`reset_index(level=<key>)` / `reset_index(col_level=<n>)`** —
  MultiIndex-on-rows shape (v1.13 PR-D2 lattice carve-out).
- **`set_index(append=True)`** — MultiIndex-on-rows append shape;
  same lattice carve-out.

#### 1.iii.5 Paired positive + negative tests MANDATORY per v14-rule 4 + v16-rule 8 + v14-rule 8 synthesis-arm-positive-coverage

Per `project_v24_retrospective` rule 8 synthesis-arm positive-
coverage standing rule, every new synthesis arm ships paired:

- **D0030 FIRE on typoed-column post-`reset_index(drop=True)`** —
  positive coverage that the synthesized schema's columns are
  actually checked downstream. E.g., `df.groupby("k").agg("sum").
  reset_index(drop=True)["typo_col"]` fires D0030 with the
  Derived schema's column list in the suggestion.
- **D0030 FIRE on typoed-column post-`set_index(["k"])`** —
  positive coverage that the literal-key column is REMOVED from
  the post-set_index schema. E.g., `df.set_index(["k"])["k"]`
  fires D0030 because `"k"` moved to index.
- **PROBE-RESOLVES on valid-column post-`reset_index(drop=True)`** —
  `df.groupby("k").agg("sum").reset_index(drop=True)["k"]`
  resolves without diagnostic. Positive ground.
- **PROBE-RESOLVES on valid-column post-`set_index(["k"])`** —
  `df.set_index(["k"])["other_col"]` resolves without
  diagnostic.
- **NEGATIVE: `reset_index(drop=False)`** — arm does NOT fire;
  receiver stays `Grouped`/`Derived` per pre-PR baseline; v1.14
  silent behavior holds.
- **NEGATIVE: `reset_index()` no-args** — same as above (default
  `drop=False`).
- **NEGATIVE: `set_index(<non-literal>)`** — arm does NOT fire;
  result is Unknown.
- **NEGATIVE: `set_index([<mixed-literal-and-non-literal>])`** —
  arm does NOT fire; fall through guard for partial-literal
  lists.

**Critical**: per v1.14 retro rule 8, the FIRE tests are the
load-bearing coverage. A PR that only ships PROBE-RESOLVES tests
without a FIRE test on the same synthesis arm fails the
synthesis-arm-positive-coverage standing rule (the arm could be
synthesizing the wrong schema and the PROBE-RESOLVES alone
wouldn't catch it).

#### 1.iii.6 Why narrow

The brief shape (drop=True only, literal-keys only) is the safe-
to-ship slice for v1.15:
- It unblocks the canonical
  `groupby.agg().reset_index(drop=True)` idiom (the v1.14 PR-D2
  `groupby.agg` arm's chain-depth limit observed in pykrete-tests
  catalog-pin) without expanding the `SchemaView` lattice.
- It's a one-cycle ship without forward-binding to v1.16.
- The deferred extensions in §1.iii.3 all need lattice
  extensions or expr-eval and are appropriately one-cycle
  bigger.

### 16.1 Why v1.16 ships them as a bundled pair

v1.16 commits to shipping `resample.agg` + `rolling.agg` +
`groupby.agg` dict-form together as "convention completion" pair:
- All three consume the v1.13 §13 aggregate-to-dtype convention.
- `resample.agg` + `rolling.agg` need a new `Windowed` (or
  similarly-shaped) lattice variant.
- `groupby.agg` dict-form re-uses the existing `Grouped` lattice
  with per-column aggfunc fanout in the synthesizer.
- Shipping them together avoids two consecutive cycles of
  partial lattice changes; the v1.16 budget absorbs the full
  lattice extension and the dict-form fanout in one cycle.

Strategist R2 commitment recorded: **no v1.16 carve-out growth
from bundle deferrals**. The bundle is the v1.16 D-pillar
headline; v1.16 spec time settles the exact lattice shape.

# pykrete v0.1 — Specification

**Status:** **shipped** — v0.1.0 (2026-05-17) → v0.1.2 (2026-05-21). See
[CHANGELOG.md](../CHANGELOG.md).
**Started:** 2026-05-11

This was the contract for the first usable version of pykrete — what the
v0.1 checker accepts, what bugs it catches, what was deliberately deferred,
and what the demo looks like. It is kept as a historical record of how the
project started. **For current capabilities, see
[`docs/roadmap.md`](roadmap.md) and [`docs/design/architecture.md`](design/architecture.md);
v0.1 shipped well beyond this minimum (full DataFrame operation surface,
column-type checking, nested types, embedded SQL, LSP, multi-file analysis).**

---

## 1. Goal

A CLI tool, `pykrete check <file.pyk>`, that statically detects schema-related bugs in PySpark code: column-name typos, missing columns after rename/drop, mismatched schemas at union, wrong join keys, and shape mismatches at function boundaries.

## 2. Demo (v0.1 acceptance)

Three failures detected on a real-shaped `.pyk` file in [../examples/](../examples/):

1. A `col("X")` reference to a column not present in the input schema.
2. A `.unionByName(...)` between two dataframes whose schemas differ.
3. A function annotated to return `DataFrame[Foo]` whose body actually produces `DataFrame[Bar]`.

Each error must report file, line, column, the type names involved, and a clear one-line message in TypeScript style.

Running it:

```
$ pykrete check examples/orders.pyk
examples/orders.pyk:36:13 - error unknownColumn: Column 'Citi' does not exist on schema 'RawOrders'. Did you mean 'City'?
...
```

## 3. The `.pyk` file

A `.pyk` file is **valid Python** with type-system extensions that pykrete understands more deeply than mypy/pyright. No new syntax in v0.1 — every `.pyk` file is parseable by Python's parser. The transpiler is mostly an identity transform; it strips pykrete-only metadata and emits `.py`.

This design lets users adopt pykrete incrementally and lets the rest of the Python toolchain (`black`, `ruff`, `pytest`) keep working unchanged.

## 4. Schemas

Defined as Python classes:

```python
class Orders(Schema):
    place_code: int
    order_date: date
    price: double
```

- Each field is `name: ColumnType`.
- Supported atomic types: `int`, `long`, `double`, `string`, `bool`, `date`, `timestamp`. (Mapped to Spark's `IntegerType`, `LongType`, etc., by the transpiler.)
- Nested structs supported via nested schema classes. *(Exact syntax: open question — see Section 11.)*
- Schemas compose via type operators (Section 6).

## 5. `DataFrame[S]` annotations

A typed dataframe carries its schema as a type parameter:

```python
def prepare_orders(raw: DataFrame[RawOrders]) -> DataFrame[Orders]:
    ...
```

`DataSource` declarations also carry schemas, so reads enter the typed world with a schema attached. *(Exact syntax for the registry pattern: open question — see Section 11.)*

## 6. Supported operations (v0.1)

Tier 1 (must work). Semantics aligned with Spark's Catalyst analyzer.

| Operation | Notes |
| --- | --- |
| `select(*cols)` | pick / rename / cast columns; output schema computed from arguments |
| `filter(expr)` / `where(expr)` | schema-preserving; column existence and expression-type checks |
| `withColumn(name, expr)` | add or replace a column |
| `withColumnRenamed(old, new)` | pure rename |
| `drop(*cols)` | remove columns |
| `groupBy(*keys).agg(*aggs)` | output is `{keys} ∪ {aliased aggregates}` |
| `join(other, on, how)` | both `on="col"` / `on=["a","b"]` and column-expression forms |
| `unionByName(other)` | checked schema equality |
| `dropDuplicates(cols)` | column existence check, schema-preserving |
| `crossJoin(other)` | schema concatenation |

Plus the supporting column expression surface:

- Column references: `col("X")` and attribute access `df.X` (both supported).
- Arithmetic/comparison/boolean operators on columns: `+`, `-`, `*`, `/`, `==`, `!=`, `<`, `>`, `&`, `|`, `~`.
- `.alias(name)`, `.cast(type)`.
- `F.when(cond, value).otherwise(value)`.
- Aggregate functions: `F.sum`, `F.avg`, `F.max`, `F.min`, `F.count`, `F.countDistinct`, `F.median`, `F.percentile_approx`, `F.var_pop`, `F.first`, `F.last`, `F.max_by`, `F.min_by`, `F.coalesce`.
- Scalar functions: `F.lit`, `F.add_months`, `F.sqrt`, `F.exp`, `F.log1p`, `F.pow`, `F.greatest`, `F.least`, `F.round`.

The string-schema literal in `spark.createDataFrame(rows, "city string, country string, population int")` is parsed and lifted into a structural schema type.

## 7. Type operators

TypeScript-style, written as valid Python generic subscriptions. Names match Spark/TS conventions ("everything is named what you expect"):

- `Pick[S, "a" | "b"]` — keep only the named columns.
- `Omit[S, "a"]` — drop the named columns.
- `Join[S1, S2, On["id"]]` — schema of an inner equi-join on the named key.
- `GroupBy[S, "key"]` — schema after a groupBy (keys alone; aggregates added by the actual `.agg()` call).

Note: `GroupBy` rather than TypeScript's `GroupedBy` — matches Spark's API name.

Structural typing: a function can accept "any `DataFrame` whose schema has at least these columns" via a Protocol-style schema declaration. *(Exact syntax: open question — see Section 11.)*

## 8. Error model

- **Style:** TypeScript-style messages — terse, precise, type-name-forward. No prose paragraphs.
- **Position:** every diagnostic carries file, line, column.
- **Severity:** `error` (default), `warning` (e.g. for unsound but allowed `Any` usage in non-strict mode).
- **Codes:** every diagnostic has a stable code (e.g. `D2001` for "Column does not exist on schema"). Catalog lives in [language-reference/](language-reference/) once the checker exists.

## 9. `Any` and `Unknown`

Mirror TypeScript exactly:

- `Any` — opt-out of checking; assignable to and from anything. Useful as a temporary escape hatch.
- `Unknown` — opaque; you can hold it, but you must narrow it (via cast/assertion) before using it as a typed value.
- UDFs, pandas UDFs, raw RDD operations, `toPandas()`, and other operations that exit the typed world return `Unknown` — a **loud** escape hatch, not silent `Any`.

## 10. Strictness modes

Configurable via a `pykrete.json` config file at the project root, mirroring `tsconfig.json`:

- **Non-strict (default):** warnings instead of errors for `Any` flows, missing return annotations, etc.
- **Strict:** errors for everything pykrete can prove unsound; required schema annotations at module boundaries; no implicit `Any`.

## 11. Out of scope for v0.1

What was originally deferred, annotated with how the actual shipped v0.1
turned out:

- IDE / LSP / VS Code extension. **→ shipped in v0.1** (`pykrete-lsp` plus
  the VS Code extension, on the Visual Studio Marketplace and Open VSX).
- Pandas, Polars, DuckDB. **→ still out of scope; see [roadmap](roadmap.md).**
- UDF body checking. **→ still out of scope (UDFs are opaque; their
  return types are tracked).**
- Schema *inference* from runtime data ("auto-detect schema from a CSV").
  **→ still out of scope.**
- Cross-file project-level analysis. **→ shipped in v0.1.**
- Performance tuning. **→ still deferred (see [roadmap](roadmap.md)).**
- Multi-version Python grammar support beyond what `ruff_python_parser`
  already does.

## 12. Open questions (resolved during implementation)

All resolved by the time v0.1 shipped:

- **Nested struct syntax in schemas.** → Bare references to other Schema
  classes (`address: Address`) plus `Array[T]` / `Map[K, V]` /
  inline-structural `{col: type, …}`. See
  [`docs/design/architecture.md`](design/architecture.md).
- **`DataSource` registry pattern.** → Annotated assignments, with PEP
  695 generic methods (`def read[T](source: DataSource[T]) -> DataFrame[T]`).
- **Derived-column auto-aliases.** → Spark-style auto-names are tracked.
- **`pykrete.json` config schema.** → `typeCheckingMode`, `exclude`,
  `rules`. See the architecture doc's `config` section.
- **Multi-file projects.** → Per-project: `check_project` pools every
  Schema/class/constant/function and analyzes each file against the
  pooled view.

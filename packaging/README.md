# Packaging & releasing pykrete

How a pykrete release is cut and how each distribution channel is fed.

## Cutting a release

1. Bump `version` in the workspace `Cargo.toml` (`[workspace.package]`),
   run `cargo build` so `Cargo.lock` picks it up, and add a `CHANGELOG.md`
   entry.
2. Commit, merge to `main`.
3. Tag and push:
   ```bash
   git tag v0.1.0
   git push origin v0.1.0
   ```
4. The [`release.yml`](../.github/workflows/release.yml) workflow builds
   release artifacts for macOS (arm64 + x64), Linux (x64) and Windows
   (x64), publishes them — with `.sha256` checksums — on a GitHub Release
   for the tag, and updates the Homebrew tap.

`release.yml` can also be re-run for an existing tag from the Actions tab
("Run workflow" → enter the tag) — useful after a workflow fix.

## Channels

### Prebuilt binaries

Produced automatically by `release.yml`. macOS and Linux get a `.tar.gz`
of the `pykrete` and `pykrete-lsp` binaries plus `README.md` and
`LICENSE`; Windows gets an `.msi` installer (see below).

### Windows MSI

The Windows job builds an installer with cargo-wix from the WiX source at
[`../crates/pykrete/wix/main.wxs`](../crates/pykrete/wix/main.wxs). It
installs both binaries into Program Files and adds them to `PATH`.

### Homebrew

```bash
brew install amirnaderi93/pykrete/pykrete
```

Installs the prebuilt binaries from the `homebrew-pykrete` tap — no Rust
build needed. The formula is generated by
[`homebrew/render.sh`](homebrew/render.sh), the single source of truth
for its shape; edit the formula there, not in the tap.

Updating the tap is **automated**: the `homebrew` job in `release.yml`
runs `render.sh` with the new version and checksums and pushes the result
to the tap on every release. No manual sha-bumping.

One-time setup:

- Create a GitHub repo `homebrew-pykrete` under the same account (so the
  tap is `amirnaderi93/pykrete`).
- Create a token with `contents: write` on that repo and add it to the
  pykrete repo's Actions secrets as **`HOMEBREW_TAP_TOKEN`**.

### cargo install

pykrete depends on ruff's parser crates via a pinned git revision, and
Astral does not publish those to crates.io — so pykrete itself cannot be
published to crates.io. Installing from the git source works regardless:

```bash
cargo install --git https://github.com/amirnaderi93/pykrete pykrete
cargo install --git https://github.com/amirnaderi93/pykrete pykrete-lsp
```

### VS Code extension (.vsix)

The extension lives in [`../editors/vscode/`](../editors/vscode/). It is
distributed as a `.vsix` file attached to every GitHub Release; users
download it and side-load it (see the [main README](../README.md#editor-integration-lsp)
for the install command). The `vsix` job in `release.yml` builds it on
each release tag — no manual packaging step.

Other distribution paths, when you want them:

- **Open VSX Registry** (<https://open-vsx.org>) — the open-source
  marketplace used by Cursor, VSCodium, Theia, code-server. Free,
  Eclipse Foundation account (no Microsoft, no billing). Publish with
  `npx ovsx publish -p <TOKEN>` from `editors/vscode/`.
- **Visual Studio Marketplace** — Microsoft's marketplace. Requires an
  Azure DevOps PAT and a publisher registered at
  <https://marketplace.visualstudio.com/manage>. Same tooling
  (`npx vsce publish`); just an extra account hurdle.

A JetBrains/PyCharm plugin is planned and will use the JetBrains
Marketplace once it exists.
